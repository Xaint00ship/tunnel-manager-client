# Tunnel Manager Client

Tunnel Manager Client - кроссплатформенное клиентское приложение, которое синхронизирует защищенные маршруты прямо на устройстве пользователя. Цель - убрать региональный gateway-сервер и дать каждому клиенту подключаться напрямую к настроенной tunnel-точке, получая правила маршрутизации из центрального API.

Первый релиз выходит сразу на двух desktop-платформах: macOS на Apple Silicon и Windows 10/11. Обе платформы входят в MVP и релизятся одной версией. Android планируется после отдельного технического spike.

## Важное разделение контуров

Этот проект не заменяет и не удаляет существующий серверный Tunnel Manager. Текущий серверный контур остается рабочим для приватного использования владельцем и доверенными пользователями.

Коммерческий продукт для продажи подписок - отдельное клиентское приложение из этого репозитория. Оно должно работать на устройствах пользователей и подключаться к backend API/control plane, не ломая и не мигрируя существующую серверную установку.

## Связь с существующей системой

Сегодняшняя схема: устройство подключается по IKEv2 или WireGuard к RU-серверу, сервер держит IPsec-туннель к зарубежной точке, а демон [tunnel_manager](https://github.com/Xaint00ship/tunnel_manager) на сервере направляет через него только адреса из списка дашборда. Список - вручную курируемые IP и CIDR по сервисам, доступ выдает Telegram-бот.

Новый клиент заменяет связку «системный VPN-профиль + tunnel-manager демон + RU-сервер как gateway» одним приложением: устройство подключается по WireGuard или IKEv2 напрямую к зарубежному серверу и делит трафик само. Control plane клиента (`client-api`, отдельный репозиторий `tunnel-client-api`) живет на том же зарубежном сервере, забирает список и статусы подписок у дашборда и работает на копии, если RU недоступен. Проверенное поведение демона переносится в клиент (ТЗ, приложение B).

## Цель продукта

Приложение должно:

- подключать устройство пользователя к управляемой tunnel-точке;
- синхронизировать whitelist маршрутов с backend каждые 5-10 минут;
- сохранять последнюю валидную версию whitelist локально;
- направлять через tunnel только настроенные направления;
- не давать защищенным направлениям уходить через обычную сеть, если tunnel недоступен;
- показывать пользователю только понятный статус подключения и простые действия;
- отправлять админам важные ошибки подключения без чувствительных данных;
- работать по WireGuard и по IKEv2, переключаясь автоматически;
- давать новым пользователям пробный период прямо из приложения, срок задает администратор;
- давать администратору панель настроек в самом приложении.

Клиент не должен подключаться напрямую к базе данных. Приложение должно работать через backend API, который проверяет пользователя, состояние подписки, версию приложения и доступ к списку маршрутов.

Подробная диагностика, количество маршрутов, время синхронизации и ручные локальные правила whitelist должны быть скрыты в отключаемом "Режиме эксперта". Обычному пользователю не нужно видеть технические детали, если приложение работает штатно.

## Техническое направление

Рекомендуемый стек:

- Tauri v2 для оболочки приложения;
- React + TypeScript для интерфейса и большей части продуктовой логики;
- TypeScript-пакеты для API-клиента, сравнения маршрутов, локального кеша и состояния приложения;
- небольшие native-адаптеры для интеграции с операционными системами;
- privileged helper там, где ОС требует повышенных прав.

Системное управление tunnel-подключением и маршрутами нельзя безопасно реализовать только на TypeScript. TypeScript остается языком продуктовой логики, а native-код ограничен адаптерами и privileged helper. При этом основной объем риска и трудозатрат лежит именно в native-части: туннель, маршруты, fail-closed, helper, подпись сборок на двух ОС. Поэтому в дорожной карте первым идет walking skeleton native-части, а не оболочка приложения.

## Ключевые решения

Зафиксированы в [docs/decisions/](docs/decisions/) и требуют подтверждения до старта разработки:

- авторизация только через существующего Telegram-бота: приложение открывает бота по ссылке, бот подтверждает вход; запасной вариант - код из бота. Своих логинов, паролей и регистрации у приложения нет;
- транспорты: WireGuard основной, IKEv2 второй с автопереключением; сервер уже терминирует оба, подтверждено по коду;
- на macOS WireGuard-туннель поднимает userspace-реализация внутри privileged helper, NetworkExtension для WireGuard остается запасным путем (ADR-002); IKEv2 на macOS идет через Personal VPN с мостом на Swift (ADR-005), так что native-слой macOS не полностью на Rust;
- whitelist - те же курируемые IP-списки дашборда, клиент работает только с IP; резолва доменов нет ни на одной стороне;
- зарубежный VPN-сервер принадлежит владельцу; на нем работают и WireGuard, и control plane клиента: авторизация, список, отзыв. Клиент общается только с ним, RU-сервер остается источником правды для списка и подписок и клиенту не виден.

## Известные ограничения 1.0

- На время подключения DNS идет через резолвер tunnel-точки, как у сегодняшних пользователей; в режиме эксперта можно оставить системный DNS, тогда подмененные провайдером адреса уйдут напрямую, и режим эксперта покажет причину.
- Разделы админ-панели «Список маршрутов», «Отчеты» и «Состояние» - в 1.1; в 1.0 только «Настройки» и «Пользователи».
- Локальные правила пользователя, экспорт диагностики и подпись route list - в 1.1.
- При падении туннеля DNS возвращается на системный, чтобы интернет вне списка продолжал работать; защищенные адреса остаются заблокированы.
- На одной машине helper обслуживает одну сессию пользователя ОС за раз; второй пользователь видит статус «подключено другим пользователем».

## Планируемые платформы

- macOS Apple Silicon (macOS 13+): входит в MVP.
- Windows 10 21H2+ и Windows 11 (x64): входит в MVP.
- Windows on ARM: после MVP, сборка закладывается в CI сразу.
- Android: после отдельного технического spike по системной модели tunnel-сервиса.

Обе desktop-платформы разрабатываются параллельно против одного контракта native-адаптера. Релиз не принимается, если хотя бы на одной из них не пройдена приемка: платформы равноправны, а не основная и вторичная.
