# ADR-002: Путь поднятия туннеля на macOS - userspace WireGuard в privileged helper

Статус: предложено, подтверждается на walking skeleton (фаза 1)
Дата: 2026-09-01
Связано: ADR-001; ТЗ разделы 8.1, 13.1, 14.3, 19.1

## Контекст

На macOS есть два пути поднять WireGuard-туннель из стороннего приложения:

1. NetworkExtension с packet tunnel provider. Это системное расширение на Swift, требует отдельного entitlement от Apple, собственного bundle и bundling-схемы, которую Tauri из коробки не поддерживает. Расширение само владеет маршрутами и может реализовать fail-closed своими средствами. Обязателен для App Store.
2. Userspace-реализация WireGuard внутри privileged helper: helper с правами root открывает utun-интерфейс, гоняет через него трафик и управляет маршрутами и pf напрямую. Все на Rust, entitlement не нужен, распространение через подписанный и нотаризованный DMG.

Windows-путь (ADR-001) - служба, которая владеет туннелем и правилами. Второй вариант на macOS дает ту же модель: helper владеет всем. Это упрощает контракт `NativeAdapter` и реальный паритет платформ.

## Решение

Для 1.0 - вариант 2: userspace WireGuard на Rust внутри privileged helper через utun, fail-closed через pf в собственном якоре.

NetworkExtension остается запасным путем и переходит в основной, если:

- walking skeleton покажет, что userspace-реализация не проходит leak-тесты L1, L2, L5 или не переживает смену сети и sleep/wake;
- потребуется распространение через App Store;
- Apple ужесточит требования к helper-процессам с сетевыми правами.

## Следствия

- Native-слой на macOS полностью на Rust, без Swift. Диаграмма в ТЗ 8.1 это отражает.
- Helper устанавливается штатным системным механизмом с одним запросом прав и работает как фоновый сервис, отдельный LaunchAgent не нужен.
- Helper обязан снимать свои правила по таймауту, если приложение не выходило на связь (`FR-197`), потому что при аварии приложения helper остается единственным владельцем состояния.
- Производительность userspace-реализации ниже kernel-варианта, но для split-туннеля с whitelist это не критично: через туннель идет малая доля трафика.

## Что проверить на walking skeleton

- открытие utun и передача трафика без падения helper при смене сети;
- восстановление pf-якоря после того, как система перезагрузила правила;
- поведение при sleep/wake: интерфейс либо восстанавливается, либо доступ остается заблокированным;
- время поднятия туннеля укладывается в метрику "p95 <= 8 c" из ТЗ 2.3.

## Альтернативы

- Сразу NetworkExtension: дороже на старте, Swift-компонент, зависимость от entitlement; не дает выигрыша для DMG-распространения. Отложено как запасной путь.
- Внешний WireGuard-клиент, которым управляет приложение: пользователь ставит две программы, обновления и uninstall не под контролем. Отклонено.
