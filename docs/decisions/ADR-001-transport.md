# ADR-001: Транспорт туннеля - WireGuard

Статус: принято, подтверждено по коду серверных репозиториев
Дата: 2026-09-01, ревизия 2026-09-03
Связано: ТЗ разделы 1.5, 13, 14, 15.5, 19; ADR-002; API_SPEC разделы 2, 6, 11

## Контекст

От транспорта зависит вся native-часть: форма privileged helper, способ поднятия интерфейса, реализация fail-closed, набор ошибок и даже язык компонентов. Краткое ТЗ оставляло транспорт открытым вопросом до фазы 3. Это слишком поздно: к фазе 3 helper уже должен быть спроектирован.

Что есть на сервере сегодня (репозиторий `tunnel_manager`, состояние на 2026-09-03):

- **IKEv2 через strongSwan с EAP** (логин и пароль). Основной транспорт: бот выдает mobileconfig для iOS и macOS, `.sswan` для Android, инструкцию для встроенного клиента Windows. Учетные данные пишутся в `ipsec.secrets`, отзыв - через `ipsec rereadsecrets` и `ipsec down`.
- **WireGuard на `wg0`**. Сервер терминирует WireGuard-клиентов; с 2026-08-30 бот выдает peer из карточки пользователя: генерирует ключевую пару на сервере, выделяет адрес из подсети интерфейса, ставит peer через `wg set` и дописывает блок в wg-quick конфиг, отдает пользователю `.conf` с `AllowedIPs = 0.0.0.0/0` и DNS через dnsmasq на tunnel-адресе. Отзыв - при отключении аккаунта и сверкой раз в 5 минут. Выключено по умолчанию (`wg_enabled`), включается в `.env`.
- **Обфускации нет**: чистый WireGuard UDP, порт 51820 по умолчанию.
- Оба транспорта ведут на **RU-сервер**, который сам является IPsec-клиентом внешней точки («import VPN») и делит трафик демоном `tunnel_manager`.

Исходное ТЗ v1.0 говорило про «существующий OS tunnel profile flow» - это IKEv2-профили, и первая редакция ADR-001 ошибочно записала WireGuard как «тот же транспорт, что у сервера», не зная, что сервер поддерживает оба.

## Решение

Для клиентского приложения транспорт - **WireGuard**, на обеих desktop-платформах и на Android. IKEv2 клиентом не поддерживается и остается в приватном контуре как есть.

Почему WireGuard, а не IKEv2, при том что IKEv2 сегодня основной:

1. **Split routing встроен в протокол.** `AllowedIPs` peer = whitelist, и ничего лишнего в таблицу маршрутов не попадает. IKEv2 через системный профиль ставит default route, который потом нужно снимать и удерживать снятым - ровно та работа, ради которой в `tunnel_manager` существуют детекция catch-all, drift repair и половина CHANGELOG. Для клиента этот класс проблем исчезает по построению.
2. **Сервер уже умеет.** Терминирование и динамическая выдача peer есть, логика `bot/wireguard.py` переносится в `client-api` почти без изменений.
3. **Ключи вместо паролей.** Устройство идентифицируется 32-байтным публичным ключом; приватный ключ генерируется на устройстве и не покидает его. IKEv2 EAP требует пароль, который сервер хранит и передает.
4. **Одна модель на трех платформах.** Kernel-драйвер на Windows, userspace в helper на macOS, штатная библиотека на Android - везде helper владеет интерфейсом и маршрутами. IKEv2 на каждой ОС - свой системный клиент со своими ограничениями.
5. **Roaming.** WireGuard переживает смену сети и сон без переустановки сессии; у IKEv2 это зависит от MOBIKE и реализации ОС.

Что теряем: IKEv2 не требует ни драйвера, ни своей реализации туннеля. Но helper для маршрутов и fail-closed нужен в любом случае, так что экономия меньше, чем кажется, а UX установки профиля на macOS хуже.

## Следствия

- Ключевая пара устройства генерируется на клиенте при активации; backend получает только публичный ключ (`API_SPEC` раздел 2). Это отличие от сегодняшнего бота, который генерирует приватный ключ на сервере.
- `AllowedIPs` peer на клиенте = актуальный route list плюс локальные правила, а не `0.0.0.0/0` (`API-055`).
- Helper меняет `AllowedIPs`, таблицу маршрутов и правила fail-closed одной операцией.
- Провизионинг peer остается локальным: `client-api` работает на том же сервере, что `wg0` (ADR-004, ТЗ 15.5). Агент нужен только для второй точки, после 1.0.
- Транспортный слой helper делается заменяемым: при блокировке UDP или сигнатуры WireGuard обфускация добавляется без переписывания маршрутов и fail-closed (риск R17).

## Что остается подтвердить

1. **D4 подтверждено владельцем 2026-09-03.** Зарубежный сервер свой; на нем разворачиваются WireGuard и control plane клиента (ADR-004). Сегодняшний «import VPN» RU-сервера к этому не относится.
2. **Пул адресов.** Бот берет подсеть из самого интерфейса; `client-api` делает так же, но хранит соответствие устройство -> адрес в БД и не выдает один адрес дважды (`API-098`).

## Альтернативы

- IKEv2 через системные профили: сохраняет сегодняшний путь выдачи, но требует снимать default route и воевать с drift на каждой ОС, хранит пароли и дает худший UX установки на macOS. Отклонено для клиента; остается в приватном контуре.
- Поддержать оба транспорта в клиенте: два helper-пути, две матрицы тестов, вдвое больше native-кода ради пользователей, которых клиент и так переводит на WireGuard. Отклонено.
- OpenVPN: тяжелее, медленнее, userspace-only, хуже переживает смену сети. Отклонено.
- Собственный протокол: не переиспользует серверную инфраструктуру, требует аудита. Отклонено.
