# ADR-003: Домены разрешаются в IP на backend, клиент работает только с IP-префиксами

Статус: предложено
Дата: 2026-09-01
Связано: ТЗ раздел 10.6; API_SPEC раздел 5 (`API-045`); OQ-8

## Контекст

Whitelist в ТЗ - список IP-префиксов. Но реальные сервисы, ради которых люди ставят такое приложение, живут за CDN и anycast и меняют адреса. Есть три места, где можно превращать домены в IP:

1. На клиенте: клиент получает домены, резолвит их и строит маршруты сам. Требует DNS-логики на устройстве, дает разные маршруты у разных пользователей, усложняет fail-closed (заблокировать нужно адрес, который еще неизвестен).
2. На backend: администратор ведет доменные списки, backend регулярно разрешает их в IP-наборы по нескольким источникам и публикует готовый route list. Клиент остается IP-only.
3. Гибрид: базовый список с backend, уточнение на клиенте.

Сегодня эту работу выполняет региональный gateway: он знает, какие адреса относятся к каким сервисам. Перенос этой логики на backend - прямое переиспользование, а не новая разработка.

## Решение

Вариант 2. Backend разрешает домены, клиент получает и применяет только IP-префиксы.

Правила для backend (`FR-165`, `FR-166`, `API-045`):

- IP-наборы обновляются не реже TTL route list;
- источники: опубликованные диапазоны провайдеров (там, где они есть), резолв с нескольких географических точек, ручные дополнения администратора;
- агрегация префиксов до публикации, чтобы route list укладывался в `NFR-025`;
- изменения набора видны в админке, чтобы администратор понимал, почему список вырос.

## Известное ограничение и его судьба

Клиент 1.0 не вмешивается в DNS. Если резолвер провайдера подменяет адрес защищенного домена, полученный адрес не входит в whitelist, трафик идет напрямую, сервис не работает, и fail-closed не срабатывает. Это ограничение записано в ТЗ 10.6 и README как известное.

В 1.0 режим эксперта дает проверку домена (`FR-168`), чтобы ограничение было диагностируемым.

В 1.1 DNS для защищенных доменов уходит через туннель (`FR-167`). Backend начнет отдавать список защищенных доменов и адрес резолвера на tunnel-точке; клиент поднимет локальный DNS-прокси только для этих доменов. Механизм - OQ-8.

## Следствия

- Route engine на клиенте остается простым и полностью тестируемым без сети.
- Fail-closed работает по известному набору адресов и не зависит от DNS.
- Качество продукта в значительной степени определяется качеством разрешения на backend, а не кодом клиента. Это должно быть видно в метриках админки.

## Альтернативы

- Резолв на клиенте: разная картина у разных пользователей, сложный fail-closed, DNS-логика на трех платформах. Отклонено для 1.0.
- Маршрутизация по SNI или по ответам DNS в реальном времени: требует перехвата трафика, противоречит запрету на анализ содержимого из ТЗ 3.2. Отклонено.
