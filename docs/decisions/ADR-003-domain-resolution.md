# ADR-003: Whitelist - курируемые IP-префиксы из дашборда, клиент работает только с IP

Статус: принято, исправлено по коду серверных репозиториев
Дата: 2026-09-01, ревизия 2026-09-03
Связано: ТЗ раздел 10.6; API_SPEC раздел 5 (`API-045`, `API-047`); OQ-8

## Контекст

Первая редакция этого ADR исходила из того, что региональный gateway разрешает домены в IP и что backend будет делать то же самое. По коду это не так.

Как список устроен сегодня (`tunnel-dashboard-backend`, `tunnel_manager`):

- Источник правды - таблицы `groups` и `ips` в Postgres дашборда. Группа = сервис («Meta», «Twitter»), запись = IP или CIDR с комментарием. Список ведет администратор руками в веб-UI дашборда и командой `/addip` в боте.
- `GET /api/routes` отдает его текстом: заголовок группы, затем адреса. `tunnel_manager` парсит текст, агрегирует `collapse_addresses` и ставит маршруты.
- Grey list - механизм поиска новых адресов: менеджер и парсер логов сообщают IP, которые «возможно, нужны», администратор решает, добавлять ли.
- Резолва доменов нет ни на сервере, ни у менеджера. Доменные списки (пункт W5 в HANDOFF серверного репозитория) отложены решением владельца.
- В списке около тысячи строк, преимущественно широкие блоки вроде `/16`, что для CDN-сервисов и есть практический ответ на смену адресов: покрывать диапазоны, а не отдельные IP.

## Решение

Клиент работает только с IP-префиксами и получает **ту же таблицу**, что приватный контур, в JSON-проекции: `services` = группы дашборда (`API-047`, `FR-165`). Ничего нового на backend для формирования списка не пишется; агрегация переезжает с менеджера на backend, чтобы клиент получал уже сжатый список.

Домены не резолвятся ни на клиенте, ни на backend. Если владелец когда-нибудь введет доменные списки, это будет новая функция backend, которая порождает те же IP-префиксы; контракт `GET /client/v1/routes` и клиент не меняются.

## DNS

У сегодняшних WireGuard-клиентов сервера DNS идет через dnsmasq, слушающий на tunnel-адресе (`10.8.0.1`), с апстримом за туннелем. Вместе с `AllowedIPs = 0.0.0.0/0` это дает полный туннель, и подмена DNS провайдером их не касается.

Прежнее решение (редакция 2.1, отменено): у клиента со split routing DNS остается системным, подмена адреса провайдером уводит трафик мимо whitelist, и это записывалось как известное ограничение 1.0. Абзац сохранен для истории; действующее решение ниже.

Ревизия 2026-09-05: DNS через резолвер точки перенесен из 1.1 в 1.0. Причина - не гипотеза, а сравнение с тем, что есть: у всех сегодняшних пользователей DNS уже идет через туннель (IKEv2-сервер пушит DNS, WireGuard-конфиг бота содержит адрес dnsmasq на tunnel-стороне). Клиент со split routing без этого регрессировал бы ровно на подменяемых провайдером доменах, показывая «Подключено» при неработающем сервисе.

Выбран самый простой путь, повторяющий серверную схему (`FR-167`, `FR-167a`, OQ-8): точка отдает адрес своего резолвера (`dnsResolver` в `GET /client/v1/endpoint`), клиент добавляет его в `AllowedIPs` на WireGuard, на IKEv2 сервер пушит его сам; helper выставляет системный DNS на время подключения и возвращает прежний при отключении и по предохранителю. Резолвер достижим только через туннель и попадает под fail-closed. Доменный список для этого не нужен. Цена - все DNS-запросы уходят через точку, и CDN-сервисы вне whitelist могут отдавать «зарубежные» адреса; поэтому в режиме эксперта есть переключатель «оставить системный DNS».

Локальный DNS-прокси только для защищенных доменов был бы точнее, но требует доменного списка, которого нет. Отложено до появления доменных списков.

## Следствия

- Route engine на клиенте остается простым и полностью тестируемым без сети.
- Fail-closed работает по известному набору адресов и не зависит от DNS.
- Качество продукта в значительной степени определяется качеством курируемого списка. Grey list и проверка «почему X (не) идет через туннель» в режиме эксперта (`FR-168`, `FR-169`) - инструменты, которыми список пополняется.

## Альтернативы

- Резолв доменов на backend по опубликованным диапазонам провайдеров: полезно, но это новая функция, а не перенос существующей; клиент к ней готов без изменений. Отложено.
- Резолв на клиенте: разная картина у разных пользователей, сложный fail-closed, DNS-логика на трех платформах. Отклонено.
- Маршрутизация по SNI или по ответам DNS в реальном времени: требует перехвата трафика, противоречит запрету на анализ содержимого из ТЗ 3.2. Отклонено.
