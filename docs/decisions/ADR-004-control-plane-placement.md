# ADR-004: Control plane клиента живет на зарубежном VPN-сервере

Статус: принято
Дата: 2026-09-03
Связано: ТЗ разделы 1.5, 8.1, 15, 15.5, 15.6, 17.2; API_SPEC разделы 1.1 и 11; ADR-001

## Контекст

Владелец подтвердил: зарубежный VPN-сервер его собственный, и он будет использоваться и для авторизации клиента, и для доступа к запрещенным ресурсам. Это закрывает предположение D4 и вопрос OQ-9.

Предыдущая редакция документов размещала control plane (`/client/v1/*`) в `tunnel-dashboard-backend` на RU-сервере, а для регистрации peer на зарубежной точке вводила агент провизионинга. Такая схема означала, что клиент ходит на два хоста, RU и зарубежный, и что доступность авторизации зависит от RU-сервера.

Что есть в RU-контуре и должно остаться нетронутым: дашборд (FastAPI, Postgres) со списком маршрутов в `groups`/`ips` и пользователями в `tunnel_users`, Telegram-бот, strongSwan и `wg0` для приватных пользователей, демон `tunnel_manager`. Бот и дашборд ставят IKEv2-учетки и WireGuard-peer локальными командами на RU-хосте, поэтому переносить их за рубеж нельзя без агента в обратную сторону.

## Решение

На зарубежном сервере работают два компонента:

1. **`wg0`** - WireGuard-интерфейс, к которому подключаются устройства пользователей; `AllowedIPs` на клиенте = whitelist.
2. **`client-api`** - отдельный сервис control plane: `POST /client/v1/auth/*`, `GET /client/v1/profile`, `routes`, `endpoint`, `POST /client/v1/error-reports` и остальное из API_SPEC. Стек тот же, что у дашборда (FastAPI, Postgres), БД своя: устройства, коды активации, публичные ключи, адреса в туннеле, копия статусов подписок.

Клиентское приложение общается только с этим сервером: HTTPS для control plane, WireGuard для трафика. RU-сервер клиенту не виден.

Авторизация человека - только через существующий Telegram-бот: приложение получает код связки у `client-api`, бот подтверждает его по deep link `/start link_<код>` или выдает код для ручного ввода. `client-api` не имеет собственной регистрации и паролей, а бот не хранит коды и не дублирует логику: он вызывает admin API (ТЗ 5.0, API_SPEC 2 и 11).

Peer регистрируются локально: `client-api` и `wg0` на одном хосте, логика `bot/wireguard.py` переносится как есть. Агент провизионинга не нужен.

RU-контур остается источником правды для списка и подписок и интегрируется с `client-api` в обе стороны (ТЗ 15.6):

- `client-api` забирает список у дашборда `GET /api/routes` тем же способом, что `tunnel_manager`, и статусы пользователей `GET /api/tunnel/users` под сервисным токеном; работает на копиях, если RU недоступен;
- бот и админка вызывают admin API `client-api`: выдать код активации, пушнуть статус подписки, посмотреть устройства, отозвать устройство;
- ошибки клиентов `client-api` пересылает в существующий `POST /api/notify`, который уже доставляет сообщения в админ-чаты.

## Следствия

- Один хост для клиента. Если зарубежный сервер заблокирован, не работают ни авторизация, ни туннель; но при заблокированном туннеле авторизация и не нужна. Клиент работает на кеше при недоступности backend (ТЗ 11.5). Вторая точка и `priority` в API - после 1.0 (риск R18).
- Устойчивость к недоступности RU: клиенты продолжают подключаться и получать список из копии; отзыв, сделанный во время недоступности, доезжает при следующей сверке (`API-111`).
- В `tunnel-dashboard-backend` меняется минимум: сервисные токены со scope для endpoints пользователей (`API-122`); фронтенд не меняется, представления клиентского контура живут в боте и админ-панели приложения (ТЗ 15.4). Схема БД дашборда не меняется: устройства и коды живут в БД `client-api`, код которого - отдельный репозиторий `tunnel-client-api`.
- Безопасность зарубежного хоста становится критичной: там и туннель, и БД устройств. `client-api` работает не от root, в БД только публичные ключи и хеши, токен к дашборду с минимальными правами (TH-11, `API-095`, `API-114`).
- Тестовое окружение (`NFR-047`) - тестовый экземпляр `wg0` плюс `client-api` с отдельными ключами и БД.

## Альтернативы

- Control plane в дашборде на RU, агент на зарубежной точке: клиент зависит от двух хостов, авторизация ломается при недоступности RU, лишний компонент. Отклонено.
- Перенести дашборд, БД и бота за рубеж целиком: ломает локальное управление IKEv2 и `wg0` приватного контура, противоречит требованию не трогать его. Отклонено.
- Один общий Postgres, в который пишут оба сервера: межсерверная зависимость на уровне БД, сложнее ограничить права. Отклонено в пользу API с копиями.
