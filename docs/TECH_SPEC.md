# Tunnel Manager Client: техническое задание

## 1. Краткое описание

Tunnel Manager Client - desktop/mobile-приложение, которое устанавливается на устройство пользователя и локально управляет защищенной split-routing логикой. Backend остается ответственным за пользователей, подписки, списки маршрутов, metadata tunnel-точек и аналитику. Клиент отвечает за подключение устройства, синхронизацию whitelist, применение локальных маршрутов и защиту от утечки защищенного трафика через обычную сеть при недоступности tunnel.

Первый релиз делаем под macOS на Apple Silicon. Поддержку Windows и Android нужно заложить в архитектуру сразу, но не выпускать в первом MVP.

## 2. Разделение контуров

Существующий серверный Tunnel Manager остается в эксплуатации и не должен удаляться, отключаться или мигрировать в рамках разработки клиентского приложения. Он нужен для приватного использования владельцем и доверенными пользователями.

Новый Tunnel Manager Client - отдельный коммерческий продукт для продажи подписок. Он должен использовать общий backend/control plane там, где это удобно, но не должен требовать демонтажа текущей серверной схемы.

Разработка клиента не должна ломать:

- существующие серверные подключения;
- текущую админку;
- Telegram-бота;
- backend API, который уже используется серверным контуром;
- текущие правила whitelist для приватного контура.

## 3. Цели

- Убрать необходимость в региональном relay/gateway-сервере.
- Оставить только зарубежные tunnel-точки и легкий backend/control plane.
- Перенести синхронизацию и применение маршрутов на устройство каждого пользователя.
- Оставить большую часть кода приложения на TypeScript.
- По возможности переиспользовать поведение текущего Tunnel Manager.
- Сделать продукт простым для пользователя: установить, войти, подключиться и забыть.

## 4. Что не входит в MVP

- Демонтаж или отключение существующего серверного Tunnel Manager.
- Перевод приватных пользователей на новое клиентское приложение.
- Обязательная миграция текущей серверной инфраструктуры.
- Прямое подключение клиента к базе данных.
- Анализ содержимого трафика.
- Enterprise MDM-деплой в первом релизе.
- Linux-клиент в первом релизе.
- Полноценный Android-релиз до отдельного technical spike.
- Публикация инфраструктурных секретов, адресов серверов, private keys, tokens или admin-only endpoints.

## 5. Продуктовые требования

### 5.1 Пользовательский сценарий

1. Пользователь устанавливает Tunnel Manager Client.
2. Пользователь входит в аккаунт или активирует устройство через выданный account/token.
3. Клиент получает из backend API данные подписки и tunnel-точки.
4. Пользователь нажимает "Подключить".
5. Клиент запускает системное tunnel-подключение.
6. Клиент скачивает и применяет актуальный whitelist.
7. Клиент синхронизирует маршруты в фоне.
8. Пользователь может вручную отключиться.
9. Если доступ истек, клиент отключается и удаляет защищенные маршруты.

### 5.2 Главный экран

Главный экран должен показывать:

- состояние подключения;
- состояние аккаунта/подписки;
- оставшееся время доступа;
- текущую версию приложения;
- короткую понятную ошибку, если подключение не удалось;
- кнопку отправки ошибки админам, если ошибка не была отправлена автоматически.

Главный экран не должен показывать обычному пользователю технические детали, которые не помогают принять решение. Время последней синхронизации, количество маршрутов, текущий tunnel-интерфейс, route drift, hash whitelist и похожая диагностика должны быть доступны только в "Режиме эксперта".

### 5.3 Ошибки и уведомления админам

Ошибки подключения должны быть сделаны лучше, чем обычный сценарий "напишите в поддержку с номером ошибки". Приложение должно само помогать админам увидеть проблему.

Клиент должен автоматически отправлять админам важные ошибки, если они мешают пользователю подключиться или пользоваться tunnel. Уведомления должны уходить через backend API, а backend уже отправляет сообщение администраторам в Telegram.

Автоматически отправлять нужно только actionable ошибки, например:

- не удалось создать или запустить tunnel-профиль;
- не удалось применить маршруты;
- не удалось включить fail-closed;
- tunnel endpoint недоступен при попытке подключения;
- access token отозван или подписка истекла;
- privileged helper не установлен, поврежден или не отвечает;
- ОС вернула ошибку прав/политик, из-за которой подключение невозможно.

Не нужно автоматически отправлять шумные события:

- пользователь сам нажал "Отключить";
- пользователь отменил системный prompt;
- временный сбой сети, который восстановился retry-механизмом;
- успешная синхронизация;
- обычные информационные события;
- повтор той же ошибки чаще заданного rate limit.

Каждая отправляемая ошибка должна иметь:

- error category;
- stable fingerprint для дедупликации;
- severity;
- platform/OS version;
- app version;
- stage, на котором произошел сбой;
- redacted diagnostics;
- user/device id в виде внутреннего id или hash;
- timestamp.

В error report нельзя включать:

- private keys;
- passwords;
- access/refresh tokens;
- полные tunnel credentials;
- содержимое трафика;
- browsing history;
- произвольные пользовательские файлы;
- raw config без redaction.

Если ошибка не ушла автоматически или пользователь хочет отправить ее вручную, на экране ошибки должна быть кнопка "Отправить ошибку". Одно нажатие отправляет тот же redacted error report админам в Telegram через backend API.

Backend должен дедуплицировать и rate-limit уведомления, чтобы админский Telegram не засыпало одинаковыми сообщениями. В Telegram должно приходить короткое сообщение: пользователь/device, платформа, версия приложения, категория ошибки, stage, fingerprint и краткая подсказка, где смотреть детали.

### 5.4 Режим эксперта

"Режим эксперта" выключен по умолчанию и включается пользователем в настройках. Все, что не нужно обычному клиенту для повседневного использования, должно быть спрятано туда.

В режиме эксперта можно показывать:

- время последней успешной синхронизации whitelist;
- количество активных защищенных маршрутов;
- текущий tunnel-интерфейс;
- версию/hash whitelist;
- статус backend и tunnel endpoint;
- последние redacted ошибки;
- экспорт диагностического bundle;
- ручную пересинхронизацию;
- ручной reconnect;
- локальные пользовательские правила whitelist.

Пользовательские правила whitelist в режиме эксперта:

- добавляются только локально на устройстве пользователя;
- не отправляются в серверную БД;
- не влияют на других пользователей;
- переживают перезапуск приложения;
- могут быть включены/выключены или удалены пользователем;
- проходят валидацию перед применением.

На первом этапе локальные правила whitelist должны поддерживать минимум IPv4 CIDR и одиночные IPv4. Поддержку доменов и IPv6 нужно проектировать отдельно, потому что домены требуют DNS-resolution и регулярного обновления IP.

### 5.5 Фоновая работа

Приложение должно:

- синхронизировать whitelist каждые 5-10 минут;
- хранить локальный кеш последнего валидного whitelist;
- запускать watchdog для проверки drift маршрутов;
- автоматически восстанавливать отсутствующие маршруты;
- удалять устаревшие маршруты после обновления списка;
- переживать sleep/wake, смену сети и reconnect tunnel-точки;
- запускаться после перезагрузки ОС, если пользователь включил autostart.

### 5.6 Fail-Closed поведение

Если tunnel недоступен, защищенные направления не должны уходить через обычную сеть. Реализация зависит от платформы:

- macOS: route/firewall rules через privileged helper или system network extension.
- Windows: route table плюс Windows filtering/firewall rules, если одних маршрутов недостаточно.
- Android: правила внутри системного Android tunnel service.

Fail-closed должен настраиваться политикой, но по умолчанию быть включенным.

### 5.7 Локальный кеш

Клиент хранит:

- последний валидный whitelist;
- версию/hash whitelist;
- timestamp последней синхронизации;
- локальные пользовательские правила whitelist из режима эксперта;
- user/session metadata;
- несекретные настройки приложения.

Секреты нужно хранить в защищенном хранилище ОС:

- macOS Keychain;
- Windows Credential Manager или DPAPI;
- Android Keystore.

### 5.8 Диагностика

Клиент должен показывать обычному пользователю только понятный итог: подключено, подключается, не подключено, ошибка подключения. Подробная диагностика должна быть доступна в режиме эксперта.

В режиме эксперта клиент должен показывать:

- статус подключения;
- текущий tunnel-интерфейс;
- количество маршрутов;
- последнюю ошибку синхронизации;
- доступность backend;
- доступность tunnel endpoint;
- экспортируемый diagnostic bundle с логами и redacted config.

Экспорт диагностики должен скрывать секреты.

## 6. Требования к Backend API

Клиент работает только через backend API, не через базу данных.

Backend API должен поддерживать новый клиентский контур отдельно от приватного серверного контура. Изменения для клиентского приложения должны быть обратно совместимы с уже работающей админкой, Telegram-ботом и серверным Tunnel Manager.

Нужные endpoints:

- `POST /client/v1/auth/activate`
- `POST /client/v1/auth/refresh`
- `GET /client/v1/profile`
- `GET /client/v1/routes`
- `GET /client/v1/endpoint`
- `POST /client/v1/events`
- `POST /client/v1/diagnostics`
- `POST /client/v1/error-reports`

### 6.1 Ответ со списком маршрутов

Route list должен включать:

- версию списка;
- content hash;
- время генерации;
- TTL;
- группировку по сервисам;
- IPv4 CIDR;
- IPv6 CIDR, когда платформа поддерживается;
- опциональный emergency blocklist;
- минимальную поддерживаемую версию приложения.

Клиент должен игнорировать невалидные CIDR и отправлять validation errors в диагностику.

### 6.2 Events

Клиент должен отправлять легкие события:

- приложение запущено;
- подключение начато/остановлено;
- синхронизация маршрутов успешна/ошибка;
- fail-closed активирован/деактивирован;
- подписка истекла;
- версия приложения.

Events не должны содержать посещенные URL, payload, историю браузинга или содержимое трафика.

### 6.3 Error Reports

`POST /client/v1/error-reports` принимает redacted error report от клиента. Backend должен:

- проверить user/device access;
- сохранить отчет;
- дедуплицировать повторяющиеся ошибки по fingerprint;
- применить rate limit;
- отправить важные новые ошибки администраторам в Telegram;
- не отправлять в Telegram шумные события и повторы.

Ответ API должен сообщать клиенту, был ли отчет принят и был ли он отправлен администраторам. Пользователю можно показать простой статус: "Ошибка отправлена" или "Не удалось отправить, попробуйте позже".

## 7. Архитектура

Рекомендуемая структура monorepo:

```text
apps/
  desktop/
    src/
    src-tauri/
packages/
  core/
  api-client/
  route-engine/
  local-store/
  shared-types/
native/
  macos-helper/
  windows-helper/
  android/
docs/
```

### 7.1 TypeScript Core

TypeScript core отвечает за:

- API client;
- валидацию route list;
- route diffing;
- state machine приложения;
- retry/backoff policies;
- формат локального кеша;
- diagnostic model;
- status model для UI.

### 7.2 Native Layer

Native layer отвечает за:

- запуск/остановку системного tunnel profile;
- чтение активных сетевых интерфейсов;
- применение/удаление маршрутов;
- применение fail-closed правил;
- защищенное хранение секретов;
- OS-specific autostart integration.

Native layer должен отдавать в TypeScript-приложение небольшой command API.

### 7.3 Предлагаемый Command API

```ts
type TunnelStatus = {
  state: "disconnected" | "connecting" | "connected" | "degraded" | "error";
  interfaceName?: string;
  endpointReachable: boolean;
  activeRouteCount: number;
  lastError?: string;
};

type NativeAdapter = {
  getStatus(): Promise<TunnelStatus>;
  connect(): Promise<void>;
  disconnect(): Promise<void>;
  applyRoutes(routes: string[]): Promise<void>;
  removeRoutes(routes: string[]): Promise<void>;
  applyLocalUserRoutes(routes: string[]): Promise<void>;
  removeLocalUserRoutes(routes: string[]): Promise<void>;
  enableFailClosed(routes: string[]): Promise<void>;
  disableFailClosed(): Promise<void>;
};
```

## 8. Платформенные заметки

### 8.1 macOS Apple Silicon

macOS MVP стоит начинать с наименее рискованной реализации:

- Tauri desktop app;
- helper process для privileged route operations;
- управление OS tunnel profile;
- Keychain для секретов;
- LaunchAgent/LaunchDaemon для фоновой работы, если понадобится.

Открытый вопрос реализации:

- сначала использовать существующий OS tunnel profile flow;
- или перейти на NetworkExtension, если управление профилем окажется слишком ограниченным.

### 8.2 Windows

Windows support должен использовать:

- native desktop app build через Tauri;
- PowerShell/VPN client APIs для настройки профиля и маршрутов, где это надежно;
- Windows Filtering Platform или firewall rules для fail-closed, если маршрутов недостаточно;
- Credential Manager/DPAPI для секретов;
- scheduled task или service для фоновой работы.

### 8.3 Android

Android требует отдельного technical spike. Скорее всего, нужно использовать системную модель Android tunnel service; относиться к Android как к desktop route management нельзя.

Ключевые вопросы:

- реализовывать ли tunnel полностью внутри приложения;
- встраивать ли существующую tunnel-библиотеку;
- как сохранить единый UX с desktop;
- как поддержать always-on behavior.

## 9. Требования безопасности

- Клиенты не подключаются к базе данных напрямую.
- Production secrets не хардкодятся.
- API access tokens должны быть отзывными.
- Route lists должны быть подписаны или hash-validated.
- Backend должен проверять subscription/access state.
- Клиент должен учитывать minimum API compatibility.
- Логи должны скрывать secrets и endpoint credentials.
- Public repository не должен содержать production infrastructure details.
- Новый клиентский контур не должен давать публичным пользователям доступ к приватному серверному контуру.

## 11. Открытые вопросы

- Точная модель активации пользователя: email link, device code, Telegram approval или admin-issued invite.
- Конкретный tunnel transport для первого релиза.
- Может ли один пользователь активировать несколько устройств.
- Отличаются ли route lists по тарифу/user/group.
- Нужен ли traffic accounting на стороне клиента.
- Модель распространения: direct DMG download, signed/notarized app или store distribution.
