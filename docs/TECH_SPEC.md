Требования пронумерованы стабильными идентификаторами и не должны менять номер после утверждения:

- `FR-*` - функциональные требования;
- `NFR-*` - нефункциональные требования;
- `SEC-*` - требования безопасности;
- `UX-*` - требования к интерфейсу;
- `T-*` - требования к тестированию.

Уровни обязательности:

- **MUST** - обязательно для MVP, без этого релиз не принимается;
- **SHOULD** - желательно в MVP, допускается перенос с записанным обоснованием;
- **MAY** - опционально, реализуется по остаточному принципу.

Каждое требование должно быть трассируемо: требование -> issue -> тест. Требование без теста считается нереализованным.

## 1. Назначение и контекст

### 1.1. Что это за продукт

Tunnel Manager Client - кроссплатформенное клиентское приложение, которое устанавливается на устройство пользователя и локально управляет защищенной split-routing логикой. Приложение подключает устройство к зарубежной tunnel-точке, получает из центрального backend API whitelist маршрутов, применяет его к системной таблице маршрутизации и гарантирует, что защищенные направления не уходят в обычную сеть при недоступности tunnel.

Backend остается ответственным за пользователей, подписки, списки маршрутов, metadata tunnel-точек, аналитику и уведомления администраторам. Клиент отвечает за подключение устройства, синхронизацию, применение маршрутов и fail-closed.

### 1.2. Проблема, которую решаем

Текущая серверная схема требует регионального relay/gateway-сервера, через который проходит трафик всех пользователей. Это дает:

- единую точку отказа и единую точку блокировки;
- расходы на региональный сервер и его пропускную способность;
- рост задержки из-за лишнего сетевого плеча;
- сложность масштабирования при росте числа подписчиков.

Целевая схема: устройство пользователя подключается напрямую к зарубежной tunnel-точке, а региональный gateway убирается из data plane. В инфраструктуре остаются только tunnel-точки и легкий backend/control plane, который не передает пользовательский трафик.

### 1.3. Разделение контуров

Существующий серверный Tunnel Manager остается в эксплуатации. Он не удаляется, не отключается и не мигрирует в рамках этого проекта. Он нужен для приватного использования владельцем и доверенными пользователями.

Новый Tunnel Manager Client - отдельный коммерческий продукт для продажи подписок. Он использует общий backend/control plane там, где это удобно, но не требует демонтажа текущей серверной схемы.

Разработка клиента **MUST NOT** ломать:

- существующие серверные подключения;
- текущую админку;
- Telegram-бота;
- backend API, который уже используется серверным контуром;
- текущие правила whitelist приватного контура.

Технические следствия разделения:

| Аспект | Приватный серверный контур | Коммерческий клиентский контур |
| --- | --- | --- |
| Namespace API | текущие пути без изменений | только `/client/v1/*` |
| Аутентификация | как сейчас | отдельные device-токены |
| Whitelist | текущие правила | отдельные списки/группы маршрутов |
| Выкатка | не затрагивается | независимый релизный цикл |
| Аварийное отключение | недоступно из клиентского контура | kill-switch только для клиентского контура |

`SEC-001` (MUST). Клиентский контур **MUST NOT** давать доступ к admin-only endpoints, приватным whitelist-правилам и данным серверного контура. Разграничение проверяется отдельными тестами авторизации.

### 1.4. Глоссарий

| Термин | Значение |
| --- | --- |
| Tunnel-точка (endpoint) | зарубежный сервер, к которому подключается устройство пользователя |
| Control plane / backend | HTTP API, который выдает конфигурацию, проверяет доступ и принимает события |
| Data plane | собственно tunnel-соединение устройства с endpoint; backend в нем не участвует |
| Whitelist / route list | список сетевых префиксов, которые должны идти через tunnel |
| Protected destination | адрес, попадающий в whitelist |
| Split routing | режим, при котором через tunnel идет только whitelist, остальное - напрямую |
| Fail-closed | режим, при котором защищенные направления блокируются, если tunnel недоступен |
| Route drift | расхождение между желаемым набором маршрутов и фактическим состоянием ОС |
| Privileged helper | системный компонент с повышенными правами, выполняющий сетевые операции |
| Native adapter | тонкий platform-специфичный слой между TypeScript-ядром и ОС |
| Режим эксперта | отключаемый по умолчанию раздел UI с технической диагностикой |
| Device | конкретная установка приложения, зарегистрированная в backend |
| Fingerprint | стабильный хеш ошибки для дедупликации отчетов |

## 2. Цели, метрики и критерии успеха

### 2.1. Продуктовые цели

1. Пользователь ставит приложение, входит, нажимает одну кнопку и дальше не думает о технике.
2. Защищенные направления работают стабильно и не утекают мимо tunnel.
3. Проблемы подключения видны администраторам без обращения пользователя в поддержку.
4. Продукт готов к продаже подписок: доступ ограничен, подписка проверяется, отзыв устройства работает.

### 2.2. Технические цели

1. Убрать региональный relay/gateway из data plane.
2. Оставить в инфраструктуре только tunnel-точки и легкий control plane.
3. Перенести синхронизацию и применение маршрутов на устройство пользователя.
4. Держать основную продуктовую логику на TypeScript, а native-код ограничить узкими адаптерами.
5. Переиспользовать поведение текущего Tunnel Manager там, где оно уже проверено.

### 2.3. Метрики MVP

| Метрика | Цель MVP |
| --- | --- |
| Доля успешных подключений | >= 97% попыток |
| Время от нажатия "Подключить" до `connected` | p50 <= 3 c, p95 <= 8 c |
| Задержка доставки изменения whitelist до устройства | p95 <= 10 минут |
| Доля устройств с актуальным whitelist (возраст < 2 x TTL) | >= 98% активных |
| Автоматическое восстановление route drift | >= 99% случаев без участия пользователя |
| Утечки защищенных направлений при недоступном tunnel | 0 в leak-тестах |
| Шум в админском Telegram | <= 20 уникальных сообщений в сутки на 100 активных устройств |

### 2.4. Definition of Done для MVP (macOS)

MVP считается готовым, когда одновременно выполнено:

- все требования уровня MUST разделов 6, 14 и 17 реализованы и покрыты тестами;
- ручная матрица тестов раздела 21 пройдена на чистой машине Apple Silicon;
- leak-тест fail-closed пройден во всех сценариях раздела 14.7;
- удаление приложения не оставляет маршрутов, helper и сломанной сети;
- backend отдает `/client/v1/*` и присылает администраторам только actionable ошибки;
- собран подписанный и нотаризованный DMG, установленный тестером с нуля.

## 3. Границы MVP

### 3.1. Входит в MVP

- macOS на Apple Silicon: полный пользовательский путь от установки до удаления.
- Активация устройства, проверка подписки, отзыв доступа.
- Синхронизация whitelist, локальный кеш, применение и снятие маршрутов.
- Watchdog маршрутов и автоматический ремонт drift.
- Fail-closed, включенный по умолчанию.
- Режим эксперта с диагностикой и локальными правилами.
- Автоматические и ручные отчеты об ошибках администраторам.
- Архитектурные точки расширения под Windows и Android (без релиза).

### 3.2. Не входит в MVP

- Демонтаж или отключение существующего серверного Tunnel Manager.
- Перевод приватных пользователей на новое клиентское приложение.
- Обязательная миграция текущей серверной инфраструктуры.
- Прямое подключение клиента к базе данных.
- Анализ содержимого трафика.
- Enterprise MDM-деплой.
- Linux-клиент.
- Полноценный Android-релиз до отдельного technical spike.
- Публикация инфраструктурных секретов, адресов серверов, private keys, tokens и admin-only endpoints.
- Биллинг и прием платежей внутри приложения: подписка выдается вне клиента.
- Мультиаккаунт и переключение профилей внутри одной установки.

### 3.3. Ограничения совместимости

`FR-001` (MUST). Клиент **MUST** работать только через backend API и **MUST NOT** обращаться к базе данных напрямую ни в каком режиме, включая режим эксперта и диагностику.

`FR-002` (MUST). Изменения backend для клиентского контура **MUST** быть обратно совместимы с работающей админкой, Telegram-ботом и серверным Tunnel Manager.

`FR-003` (MUST). Приложение **MUST** оставаться работоспособным офлайн на последнем валидном кеше whitelist в пределах политики TTL/grace (раздел 11.5).

## 5. Пользовательские сценарии

### 5.1. Основной сценарий

| Шаг | Действие | Состояние клиента | Что происходит внутри |
| --- | --- | --- | --- |
| 1 | Пользователь устанавливает приложение | - | helper еще не установлен |
| 2 | Первый запуск | `unactivated` | показывается экран активации |
| 3 | Пользователь активирует устройство | `activating` | `POST /client/v1/auth/activate`, регистрация устройства |
| 4 | Клиент получает профиль и endpoint | `disconnected` | `GET /client/v1/profile`, `GET /client/v1/endpoint`, секреты в OS keystore |
| 5 | Нажатие "Подключить" | `connecting` | установка helper при первом подключении, запрос прав ОС |
| 6 | Поднимается системное tunnel-подключение | `connecting` | native adapter создает и запускает tunnel profile |
| 7 | Клиент загружает и применяет whitelist | `connecting` | `GET /client/v1/routes`, валидация, diff, применение маршрутов |
| 8 | Включается fail-closed | `connected` | правила блокировки защищенных направлений мимо tunnel |
| 9 | Фоновая работа | `connected` | sync каждые 5-10 минут, watchdog каждые 15-30 секунд |
| 10 | Нажатие "Отключить" | `disconnecting` -> `disconnected` | снятие маршрутов и fail-closed, остановка tunnel |
| 11 | Доступ истек | `access_expired` | отключение, удаление защищенных маршрутов, понятное сообщение |

### 5.2. Альтернативные и аварийные сценарии

| # | Сценарий | Ожидаемое поведение |
| --- | --- | --- |
| A1 | Нет сети при запуске | старт из кеша, состояние `disconnected`, повтор с backoff, без отчета админам |
| A2 | Backend недоступен, tunnel работает | остаемся `connected`, whitelist из кеша, обычный UI не меняется, в режиме эксперта - "синхронизация недоступна" |
| A3 | Backend недоступен дольше grace | переход в `degraded`, предупреждение пользователю, политика stale-кеша (раздел 11.5) |
| A4 | Tunnel endpoint недоступен | `error`, fail-closed активен, автоматический отчет админам, retry с backoff |
| A5 | Tunnel упал во время работы | `reconnecting`, защищенные направления заблокированы, автоматический reconnect |
| A6 | Пользователь отменил системный prompt | возврат в `disconnected`, понятное объяснение, отчет админам не отправляется |
| A7 | Helper не установлен, поврежден или не отвечает | `error` с предложением переустановить helper, автоматический отчет админам |
| A8 | Сон и пробуждение устройства | проверка и восстановление tunnel и маршрутов не позже 10 секунд после wake |
| A9 | Смена сети (Wi-Fi -> LTE, смена SSID) | пересоздание маршрутов на новом интерфейсе, fail-closed не снимается на время переключения |
| A10 | Подписка истекла во время работы | отключение, снятие маршрутов и fail-closed, экран "доступ истек" |
| A11 | Токен устройства отозван | немедленное отключение, очистка секретов, возврат на экран активации |
| A12 | Версия приложения ниже минимальной | блокировка подключения, экран "обновите приложение" со ссылкой |
| A13 | Whitelist содержит невалидные записи | невалидные игнорируются, остальные применяются, validation errors уходят в диагностику |
| A14 | Whitelist не прошел проверку подписи или хеша | список отклоняется целиком, работаем на предыдущем кеше, автоматический отчет админам |
| A15 | Route drift | watchdog восстанавливает маршруты, событие в диагностику, отчет админам только при повторных неудачах ремонта |
| A16 | Аварийное завершение приложения | fail-closed остается активным до явного снятия helper (раздел 14.6) |
| A17 | Удаление приложения | uninstall снимает маршруты, fail-closed, helper и autostart, сеть остается рабочей |

### 5.3. Жизненный цикл устройства

```text
unregistered -> activated -> active (подписка валидна)
                               |-> suspended (подписка истекла, устройство сохранено)
                               |-> revoked   (админ отозвал доступ, нужна повторная активация)
                               |-> removed   (приложение удалено или устройство отвязано)
```

`FR-004` (MUST). Переход в `suspended` или `revoked` **MUST** приводить к снятию защищенных маршрутов и fail-closed не позднее 60 секунд после того, как клиент узнал о смене состояния.

## 6. Функциональные требования

### 6.1. Активация и аутентификация

`FR-010` (MUST). Приложение **MUST** поддерживать активацию устройства через выданный account/token или вход в аккаунт. Конкретная модель активации фиксируется в разделе 24 (открытый вопрос OQ-1); архитектура **MUST** позволять сменить модель без переписывания клиента.

`FR-011` (MUST). При активации клиент **MUST** зарегистрировать устройство и получить пару токенов: короткоживущий access token и долгоживущий refresh token.

`FR-012` (MUST). Access token **MUST** храниться только в памяти процесса и не записываться на диск. Refresh token **MUST** храниться в защищенном хранилище ОС (раздел 12.4).

`FR-013` (MUST). Клиент **MUST** обновлять access token заранее - не позже чем за 20% времени жизни до истечения, и **MUST** уметь обновить его по ответу `401`.

`FR-014` (MUST). При ответе backend о том, что устройство отозвано, клиент **MUST**: отключиться, снять маршруты и fail-closed, удалить refresh token и локальный кеш маршрутов, вернуться на экран активации.

`FR-015` (MUST). Клиент **MUST** генерировать стабильный `deviceId` при первой активации и переиспользовать его при перезапусках. `deviceId` **MUST NOT** содержать серийный номер устройства, MAC-адрес или другие аппаратные идентификаторы в открытом виде.

`FR-016` (SHOULD). При переустановке приложения на том же устройстве клиент **SHOULD** предлагать повторную активацию, а backend **SHOULD** уметь заменить старую регистрацию, чтобы не расходовать лимит устройств.

### 6.2. Подключение и отключение

`FR-020` (MUST). Главное действие приложения - одна кнопка, которая переключает состояние между "Подключить" и "Отключить".

`FR-021` (MUST). Перед подключением клиент **MUST** проверить: наличие валидных токенов, состояние подписки, минимальную поддерживаемую версию приложения, доступность и работоспособность helper.

`FR-022` (MUST). Подключение **MUST** быть атомарным с точки зрения пользователя: если любой обязательный шаг (tunnel, маршруты, fail-closed) не выполнен, клиент **MUST** откатить частично применённые изменения и перейти в `error`, а не остаться в полуприменённом состоянии.

`FR-023` (MUST). Отключение по кнопке **MUST** снимать защищенные маршруты, снимать fail-closed и останавливать tunnel в этом порядке, чтобы не оставить заблокированных направлений без tunnel.

`FR-024` (MUST). Клиент **MUST** поддерживать автоматический reconnect при падении tunnel: до 5 попыток с backoff, затем переход в `error` с отчетом администраторам.

`FR-025` (SHOULD). Клиент **SHOULD** поддерживать опцию "подключаться автоматически при запуске", выключенную по умолчанию.

### 6.3. Синхронизация whitelist

`FR-030` (MUST). Клиент **MUST** синхронизировать whitelist с backend с интервалом 5-10 минут (раздел 11.1).

`FR-031` (MUST). Клиент **MUST** сохранять последнюю валидную версию whitelist локально и использовать ее при старте до первой успешной синхронизации.

`FR-032` (MUST). Клиент **MUST** проверять целостность полученного списка: content hash и, если backend отдает подпись, криптографическую подпись (раздел 11.3).

`FR-033` (MUST). Клиент **MUST** игнорировать невалидные записи списка и отправлять validation errors в диагностику, не отбрасывая при этом валидную часть списка.

`FR-034` (MUST). Клиент **MUST** отклонять список целиком, если не сошелся hash или подпись, и продолжать работу на предыдущем валидном кеше.

`FR-035` (MUST). Клиент **MUST** отклонять список с версией ниже уже применённой (anti-rollback), если backend явно не прислал флаг сброса версии.

`FR-036` (MUST). Синхронизация **MUST** использовать условные запросы (`ETag`/`If-None-Match`), чтобы не скачивать неизменившийся список.

`FR-037` (SHOULD). Синхронизация **SHOULD** выполняться и в состоянии `disconnected`, чтобы кеш был свежим к моменту подключения.

### 6.4. Применение маршрутов

`FR-040` (MUST). Через tunnel **MUST** идти только направления из whitelist и локальных пользовательских правил. Весь остальной трафик идет напрямую.

`FR-041` (MUST). Клиент **MUST** вычислять diff между желаемым и применённым набором маршрутов и применять только разницу.

`FR-042` (MUST). При обновлении списка новые маршруты **MUST** добавляться до удаления устаревших, чтобы не возникало окна утечки.

`FR-043` (MUST). Клиент **MUST** удалять устаревшие маршруты после обновления списка.

`FR-044` (MUST). Клиент **MUST** исключать из tunnel-маршрутов адрес самой tunnel-точки, чтобы не создать маршрутную петлю.

`FR-045` (MUST). Клиент **MUST** отклонять маршруты, которые нарушают guardrails раздела 10.2 (слишком широкие префиксы, loopback, link-local, multicast и т. п.).

`FR-046` (SHOULD). Клиент **SHOULD** агрегировать соседние и вложенные префиксы, чтобы уменьшить размер таблицы маршрутов.

### 6.5. Watchdog и самовосстановление

`FR-050` (MUST). Клиент **MUST** запускать watchdog, который сравнивает желаемое состояние маршрутов с фактическим состоянием ОС с интервалом 15-30 секунд.

`FR-051` (MUST). При обнаружении drift клиент **MUST** автоматически восстанавливать отсутствующие маршруты и удалять лишние защищенные маршруты, созданные приложением.

`FR-052` (MUST). Watchdog **MUST NOT** трогать маршруты, которые приложение не создавало.

`FR-053` (MUST). Клиент **MUST** корректно переживать sleep/wake, смену сети и reconnect tunnel-точки: после каждого такого события выполняется полная сверка состояния.

`FR-054` (MUST). Если ремонт drift не удался 3 раза подряд, клиент **MUST** перейти в `degraded` и отправить отчет администраторам.

`FR-055` (SHOULD). Клиент **SHOULD** запускаться после перезагрузки ОС, если пользователь включил autostart.

### 6.6. Fail-closed

`FR-060` (MUST). Если tunnel недоступен, защищенные направления **MUST NOT** уходить через обычную сеть.

`FR-061` (MUST). Fail-closed **MUST** быть включен по умолчанию и настраиваться политикой.

`FR-062` (MUST). Fail-closed **MUST** активироваться до того, как маршруты будут сняты при падении tunnel, и деактивироваться только после явного отключения пользователем или после отзыва доступа.

`FR-063` (MUST). Выключение fail-closed пользователем **MUST** требовать явного подтверждения с объяснением последствий.

Детали реализации - раздел 14.

### 6.7. Подписка и доступ

`FR-070` (MUST). Клиент **MUST** получать из backend состояние подписки и оставшееся время доступа.

`FR-071` (MUST). При истечении доступа клиент **MUST** отключиться и удалить защищенные маршруты.

`FR-072` (MUST). Клиент **MUST NOT** принимать решение о доступе самостоятельно на основании локального времени: авторитет - только backend. Локальный таймер используется только для отображения оставшегося времени.

`FR-073` (SHOULD). Клиент **SHOULD** предупреждать пользователя об истечении подписки заранее: за 3 дня и за 1 день.

### 6.8. Версионирование и обновления

`FR-080` (MUST). Клиент **MUST** передавать свою версию в каждый запрос к backend и **MUST** учитывать `minSupportedVersion` из ответа.

`FR-081` (MUST). Если версия ниже минимальной, клиент **MUST** блокировать подключение и показывать экран обновления.

`FR-082` (SHOULD). Клиент **SHOULD** поддерживать проверку и установку обновлений; конкретный механизм фиксируется решением по OQ-6.

### 6.9. Фоновая работа

`FR-090` (MUST). Приложение **MUST** продолжать синхронизацию и watchdog при закрытом окне, пока процесс жив.

`FR-091` (MUST). Приложение **MUST** иметь индикатор состояния в меню-баре/трее с быстрым доступом к подключению и отключению.

`FR-092` (SHOULD). Приложение **SHOULD** уметь стартовать при входе пользователя в систему, если autostart включен.

### 6.10. Локальные правила пользователя

`FR-100` (MUST). В режиме эксперта пользователь **MUST** иметь возможность добавлять локальные правила whitelist.

`FR-101` (MUST). Локальные правила **MUST**:

- добавляться только локально на устройстве пользователя;
- не отправляться в серверную БД;
- не влиять на других пользователей;
- переживать перезапуск приложения;
- включаться, выключаться и удаляться пользователем;
- проходить валидацию перед применением.

`FR-102` (MUST). На первом этапе локальные правила **MUST** поддерживать минимум IPv4 CIDR и одиночные IPv4-адреса. Поддержка доменов и IPv6 проектируется отдельно, потому что домены требуют DNS-resolution и регулярного обновления IP.

`FR-103` (MUST). Локальные правила **MUST** проходить те же guardrails, что и серверный список (раздел 10.2), и **MUST** быть визуально отличимы в диагностике от серверных маршрутов.

`FR-104` (MUST). Локальные правила **MUST** сниматься при отключении и при удалении приложения так же, как серверные.

`FR-105` (MAY). Клиент **MAY** позволять экспорт и импорт локальных правил файлом для переноса между устройствами пользователя.

### 6.11. Ошибки и уведомления администраторам

Ошибки подключения должны быть сделаны лучше, чем сценарий "напишите в поддержку с номером ошибки". Приложение само помогает администраторам увидеть проблему.

`FR-110` (MUST). Клиент **MUST** автоматически отправлять администраторам важные ошибки, которые мешают подключиться или пользоваться tunnel. Отправка идет через backend API, а backend уже отправляет сообщение администраторам в Telegram.

`FR-111` (MUST). Автоматически отправляются только actionable ошибки, например:

- не удалось создать или запустить tunnel-профиль;
- не удалось применить маршруты;
- не удалось включить fail-closed;
- tunnel endpoint недоступен при попытке подключения;
- access token отозван или подписка истекла;
- privileged helper не установлен, поврежден или не отвечает;
- ОС вернула ошибку прав или политик, из-за которой подключение невозможно.

`FR-112` (MUST). Не отправляются автоматически шумные события:

- пользователь сам нажал "Отключить";
- пользователь отменил системный prompt;
- временный сбой сети, восстановленный retry-механизмом;
- успешная синхронизация;
- обычные информационные события;
- повтор той же ошибки чаще заданного rate limit.

`FR-113` (MUST). Каждый отправляемый отчет **MUST** содержать: error category, стабильный fingerprint для дедупликации, severity, платформу и версию ОС, версию приложения, stage сбоя, redacted diagnostics, внутренний id или hash пользователя/устройства, timestamp.

`FR-114` (MUST). В error report **MUST NOT** попадать: private keys, пароли, access/refresh tokens, полные tunnel credentials, содержимое трафика, история браузинга, произвольные пользовательские файлы, raw config без redaction.

`FR-115` (MUST). Если ошибка не ушла автоматически или пользователь хочет отправить ее вручную, на экране ошибки **MUST** быть кнопка "Отправить ошибку", отправляющая тот же redacted отчет одним нажатием.

`FR-116` (MUST). Backend **MUST** дедуплицировать и rate-limit уведомления, чтобы админский Telegram не засыпало одинаковыми сообщениями.

`FR-117` (MUST). В Telegram приходит короткое сообщение: пользователь/устройство, платформа, версия приложения, категория ошибки, stage, fingerprint и подсказка, где смотреть детали.

Полные правила - [ERROR_CATALOG.md](ERROR_CATALOG.md).

### 6.12. Диагностика

`FR-120` (MUST). Обычному пользователю показывается только понятный итог: подключено, подключается, не подключено, ошибка подключения.

`FR-121` (MUST). Подробная диагностика доступна только в режиме эксперта: статус подключения, текущий tunnel-интерфейс, количество маршрутов, последняя ошибка синхронизации, доступность backend, доступность tunnel endpoint.

`FR-122` (MUST). Клиент **MUST** уметь экспортировать diagnostic bundle с логами и redacted config. Экспорт **MUST** скрывать секреты.

`FR-123` (MUST). Перед сохранением bundle пользователю **MUST** показываться, что именно попадет в файл.

## 7. Пользовательский интерфейс

### 7.1. Принципы

`UX-001` (MUST). Главный экран показывает только то, что помогает пользователю принять решение. Время последней синхронизации, количество маршрутов, tunnel-интерфейс, route drift, hash whitelist и похожая диагностика **MUST** быть доступны только в режиме эксперта.

`UX-002` (MUST). Любое состояние ошибки **MUST** содержать: что случилось человеческим языком, что делать пользователю, и кнопку действия (повторить / отправить ошибку / обновить приложение).

`UX-003` (MUST). Приложение **MUST NOT** показывать пользователю технические коды как основной текст ошибки. Код и fingerprint показываются мелким шрифтом как вспомогательная информация.

### 7.2. Информационная архитектура

```text
Активация
  └─ Главный экран
       ├─ Экран ошибки (модально или врезкой)
       ├─ Настройки
       │    ├─ Общие (автозапуск, автоподключение, язык)
       │    ├─ Безопасность (fail-closed)
       │    ├─ Аккаунт (подписка, устройство, выход)
       │    └─ Режим эксперта (переключатель)
       └─ Режим эксперта (появляется только если включен)
            ├─ Диагностика
            ├─ Локальные правила whitelist
            └─ Экспорт диагностики
```

### 7.3. Экран активации

Содержит: краткое объяснение, поле ввода кода или кнопку входа, кнопку "Активировать", ссылку на помощь, версию приложения.

Состояния: пустое, ввод, проверка, ошибка активации (неверный код, код использован, лимит устройств, нет сети).

### 7.4. Главный экран

Показывает:

- состояние подключения;
- состояние аккаунта и подписки;
- оставшееся время доступа;
- текущую версию приложения;
- короткую понятную ошибку, если подключение не удалось;
- кнопку отправки ошибки администраторам, если ошибка не была отправлена автоматически.

Визуальные состояния:

| Состояние | Заголовок | Подпись | Кнопка |
| --- | --- | --- | --- |
| `disconnected` | Не подключено | Защищенные сервисы идут напрямую | Подключить |
| `connecting` | Подключение... | Настраиваем защищенное соединение | Отменить |
| `connected` | Подключено | Защищенные сервисы идут через tunnel | Отключить |
| `degraded` | Подключено с ограничениями | Не удается обновить список маршрутов | Отключить |
| `reconnecting` | Восстанавливаем соединение | Защищенные сервисы временно недоступны | Отключить |
| `error` | Не удалось подключиться | текст из каталога ошибок | Повторить / Отправить ошибку |
| `access_expired` | Доступ истек | Продлите подписку, чтобы подключаться | Обновить статус |
| `update_required` | Нужно обновление | Эта версия больше не поддерживается | Обновить приложение |

### 7.5. Меню-бар / трей

`UX-010` (MUST). Иконка **MUST** отражать состояние: подключено, подключается, отключено, ошибка.

`UX-011` (MUST). Меню содержит: текущее состояние, подключить/отключить, открыть окно, выход.

`UX-012` (SHOULD). Выход из приложения при активном подключении **SHOULD** спрашивать подтверждение и объяснять, что произойдет с fail-closed (раздел 14.6).

### 7.6. Настройки

| Раздел | Пункты |
| --- | --- |
| Общие | автозапуск при входе, автоподключение при старте, язык |
| Безопасность | fail-closed (по умолчанию включен, выключение с подтверждением) |
| Аккаунт | план, статус подписки, дата окончания, id устройства, выход и отвязка устройства |
| Дополнительно | переключатель "Режим эксперта" с пояснением, что он для продвинутых пользователей |

### 7.7. Режим эксперта

`UX-020` (MUST). Режим эксперта выключен по умолчанию и включается пользователем в настройках.

`UX-021` (MUST). В режиме эксперта показываются:

- время последней успешной синхронизации whitelist;
- количество активных защищенных маршрутов;
- текущий tunnel-интерфейс;
- версия и hash whitelist;
- статус backend и tunnel endpoint;
- последние redacted ошибки;
- экспорт диагностического bundle;
- ручная пересинхронизация;
- ручной reconnect;
- локальные пользовательские правила whitelist.

`UX-022` (MUST). Раздел локальных правил содержит: список правил с переключателями, добавление правила с валидацией на лету, удаление, отметку "локальное правило, действует только на этом устройстве".

`UX-023` (MUST). Выключение режима эксперта **MUST NOT** удалять локальные правила: они остаются активными, но скрыты из UI. Об этом пользователю **MUST** сообщаться при выключении.

### 7.8. Тексты состояний и ошибок

`UX-030` (MUST). Все пользовательские тексты ошибок **MUST** храниться централизованно и мапиться из категорий каталога ошибок, а не собираться в местах возникновения ошибок.

`UX-031` (MUST). Текст **MUST** быть без внутренней терминологии: вместо "route apply failed via helper IPC" - "не удалось настроить маршруты на этом устройстве".

### 7.9. Локализация и доступность

`NFR-001` (MUST). Интерфейс **MUST** быть готов к локализации: никаких строк, зашитых в компоненты.

`NFR-002` (MUST). MVP поставляется с русской локалью; английская локаль - `SHOULD`.

`NFR-003` (SHOULD). Интерфейс **SHOULD** поддерживать навигацию с клавиатуры, читаемые контрасты и системную темную тему.

## 8. Архитектура

### 8.1. Обзор

```text
┌──────────────────────────────────────────────┐
│ Tunnel Manager Client (устройство)           │
│                                              │
│  ┌────────────────────────────────────────┐  │
│  │ UI: React + TypeScript                 │  │
│  │  обычный режим / режим эксперта        │  │
│  └───────────────┬────────────────────────┘  │
│                  │ status model / commands    │
│  ┌───────────────▼────────────────────────┐  │
│  │ Core (TypeScript)                      │  │
│  │  state machine, sync, route engine,    │  │
│  │  cache, retry, diagnostics, errors     │  │
│  └───────┬───────────────────────┬────────┘  │
│          │ NativeAdapter API      │ HTTPS     │
│  ┌───────▼────────┐               │           │
│  │ Native adapter │               │           │
│  │ (Rust/Tauri)   │               │           │
│  └───────┬────────┘               │           │
│          │ IPC (авторизованный)   │           │
│  ┌───────▼──────────────┐         │           │
│  │ Privileged helper    │         │           │
│  │ routes / firewall /  │         │           │
│  │ tunnel profile       │         │           │
│  └───────┬──────────────┘         │           │
└──────────┼────────────────────────┼───────────┘
           │ tunnel (data plane)     │ control plane
           ▼                         ▼
    ┌─────────────┐          ┌──────────────────┐
    │ Tunnel      │          │ Backend API      │
    │ endpoint    │          │ /client/v1/*     │
    └─────────────┘          └────────┬─────────┘
                                      │
                             ┌────────▼─────────┐
                             │ Telegram админам │
                             └──────────────────┘
```

Ключевое свойство: backend не участвует в передаче пользовательского трафика. Если backend недоступен, tunnel продолжает работать на кешированной конфигурации.

### 8.2. Структура репозитория

```text
apps/
  desktop/
    src/                 # React UI
    src-tauri/           # Tauri shell, Rust-команды, native adapter
packages/
  core/                  # state machine, оркестрация, политики
  api-client/            # HTTP-клиент, схемы, retry, auth
  route-engine/          # нормализация, валидация, агрегация, diff
  local-store/           # кеш, настройки, локальные правила, миграции
  diagnostics/           # логгер, redaction, error reports, bundle
  shared-types/          # общие типы и zod-схемы
  mock-backend/          # локальный mock control plane для разработки
native/
  macos-helper/          # privileged helper для macOS
  windows-helper/        # privileged helper/сервис для Windows
  android/               # Android tunnel service (после spike)
docs/
```

`NFR-010` (MUST). Пакеты `core`, `route-engine`, `local-store`, `api-client` **MUST** быть платформонезависимыми и тестируемыми в Node без ОС-специфичных вызовов.

`NFR-011` (MUST). Зависимости направлены только вниз: `UI -> core -> (api-client | route-engine | local-store | diagnostics) -> shared-types`. Обратные зависимости запрещены и проверяются линтером.

### 8.3. Процессная модель

| Процесс | Права | Ответственность |
| --- | --- | --- |
| UI process | пользовательские | отрисовка, ввод, чтение status model |
| Core (в процессе приложения) | пользовательские | вся логика, сеть, кеш, планировщики |
| Native adapter (Rust в Tauri) | пользовательские | вызов helper, чтение состояния сети |
| Privileged helper | повышенные | маршруты, firewall, tunnel profile |

`SEC-002` (MUST). Helper **MUST** выполнять только фиксированный набор команд с типизированными аргументами. Приём произвольных команд, shell-строк и путей запрещен.

### 8.4. Ключевые потоки

Подключение:

```text
UI: connect
core: проверка токена, подписки, версии, helper
core -> native: connect()
native -> helper: startTunnel(profileRef)
helper: поднимает tunnel, возвращает interfaceName
core: GET /client/v1/routes (или кеш)
route-engine: validate -> normalize -> aggregate -> diff
core -> native: applyRoutes(add)
core -> native: enableFailClosed(protectedSet)
core -> native: removeRoutes(stale)
core: state = connected, POST /client/v1/events
```

Периодическая синхронизация:

```text
scheduler tick (5-10 мин ± jitter)
api-client: GET /client/v1/routes с If-None-Match
  304 -> обновить timestamp, выход
  200 -> проверить hash/подпись/версию -> сохранить кеш
route-engine: diff(applied, desired)
native: applyRoutes(add) -> updateFailClosed -> removeRoutes(remove)
```

Ремонт drift:

```text
watchdog tick (15-30 c)
native: getAppliedRoutes()
route-engine: diff(desired, actual)
если diff не пуст -> repair -> событие в диагностику
3 неудачи подряд -> degraded + error report
```

## 9. Модель состояний

### 9.1. Состояния

| Состояние | Значение |
| --- | --- |
| `unactivated` | устройство не активировано |
| `activating` | идет активация |
| `disconnected` | активировано, tunnel выключен |
| `connecting` | идет подключение и первичное применение конфигурации |
| `connected` | tunnel поднят, маршруты применены, fail-closed активен |
| `degraded` | tunnel работает, но конфигурация устарела или drift не чинится |
| `reconnecting` | tunnel упал, идет автоматическое восстановление |
| `disconnecting` | идет снятие конфигурации и остановка tunnel |
| `error` | подключение невозможно, нужна реакция |
| `access_expired` | подписка истекла или устройство отозвано |
| `update_required` | версия ниже минимальной |

### 9.2. Таблица переходов

| Из | Событие | В | Побочные действия |
| --- | --- | --- | --- |
| `unactivated` | активация успешна | `disconnected` | сохранить токены, загрузить профиль |
| `disconnected` | пользователь нажал "Подключить" | `connecting` | предполетные проверки |
| `connecting` | tunnel поднят и маршруты применены | `connected` | событие `connect_ok` |
| `connecting` | ошибка любого обязательного шага | `error` | откат, error report |
| `connecting` | пользователь отменил | `disconnecting` | откат без error report |
| `connected` | tunnel упал | `reconnecting` | fail-closed остается включенным |
| `connected` | sync не удается дольше grace | `degraded` | предупреждение в UI |
| `connected` | подписка истекла | `access_expired` | снять маршруты и fail-closed |
| `connected` | пользователь нажал "Отключить" | `disconnecting` | снять конфигурацию |
| `degraded` | успешная синхронизация | `connected` | снять предупреждение |
| `reconnecting` | tunnel восстановлен | `connected` | сверка маршрутов |
| `reconnecting` | исчерпан лимит попыток | `error` | error report |
| `error` | пользователь нажал "Повторить" | `connecting` | сброс backoff |
| `access_expired` | подписка продлена | `disconnected` | обновить профиль |
| любое | токен отозван | `unactivated` | полная очистка секретов и кеша маршрутов |
| любое | версия ниже минимальной | `update_required` | блокировать подключение |

### 9.3. Инварианты

`FR-130` (MUST). В состояниях `connected`, `degraded` и `reconnecting` fail-closed **MUST** быть активен, если политика fail-closed включена.

`FR-131` (MUST). В состояниях `disconnected`, `unactivated`, `access_expired` и `update_required` защищенных маршрутов приложения в системе **MUST NOT** оставаться.

`FR-132` (MUST). Переходы **MUST** быть сериализованы: одновременно выполняется не более одной операции изменения сетевого состояния. Конкурентные запросы ставятся в очередь.

## 10. Route Engine

### 10.1. Нормализация

`FR-140` (MUST). Входная запись маршрута нормализуется по правилам:

1. обрезка пробелов, приведение к нижнему регистру;
2. одиночный IPv4 превращается в `/32`, одиночный IPv6 - в `/128`;
3. проверка синтаксиса адреса и длины префикса;
4. обнуление host-битов: `10.1.2.3/24` -> `10.1.2.0/24`;
5. дедупликация после нормализации.

### 10.2. Валидация и guardrails

`FR-141` (MUST). Запись отклоняется, если она:

- синтаксически невалидна;
- имеет длину префикса вне допустимого диапазона (IPv4: 8-32, IPv6: 32-128 по умолчанию);
- равна `0.0.0.0/0` или `::/0` (полный перехват трафика не поддерживается в split-режиме);
- попадает в loopback (`127.0.0.0/8`, `::1/128`);
- попадает в link-local (`169.254.0.0/16`, `fe80::/10`);
- попадает в multicast (`224.0.0.0/4`, `ff00::/8`);
- совпадает с адресом tunnel endpoint или содержит его;
- пересекается с адресом активного шлюза по умолчанию.

`FR-142` (MUST). Приватные диапазоны (`10/8`, `172.16/12`, `192.168/16`) по умолчанию отклоняются, чтобы не ломать локальную сеть пользователя. Исключение допускается только явным флагом в серверном списке.

`FR-143` (MUST). Общее число применяемых маршрутов ограничено (по умолчанию 10 000). При превышении применяется усечённый список, а факт превышения уходит в диагностику и отчет админам.

`FR-144` (MUST). Результат валидации **MUST** содержать список отклоненных записей с причиной; этот список попадает в диагностику и в `POST /client/v1/diagnostics`.

### 10.3. Агрегация

`FR-145` (SHOULD). Перед применением набор префиксов агрегируется: вложенные префиксы поглощаются родительскими, соседние объединяются в один при совпадении границ. Агрегация **MUST NOT** расширять покрытие за пределы исходного набора.

### 10.4. Diff и порядок применения

```ts
type RouteDiff = {
  toAdd: string[];
  toRemove: string[];
  unchanged: string[];
};
```

`FR-146` (MUST). Порядок применения при обновлении: `applyRoutes(toAdd)` -> `updateFailClosed(desiredSet)` -> `removeRoutes(toRemove)`.

`FR-147` (MUST). Применение **MUST** быть идемпотентным: повторный вызов с тем же набором не меняет систему и не считается ошибкой.

`FR-148` (MUST). Маршруты применяются пачками (по умолчанию 256 записей на вызов), чтобы не блокировать helper надолго и давать прогресс в UI.

`FR-149` (MUST). Частичная неудача **MUST** возвращать в core список неудавшихся записей, а не общий флаг ошибки.

### 10.5. Псевдокод цикла применения

```text
desired = aggregate(validate(normalize(serverRoutes ∪ enabledLocalRules)))
desired = desired \ excluded(endpointIp, defaultGateway, guardrails)
diff    = diff(applied, desired)
if diff пуст: выход
apply(diff.toAdd) в пачках
updateFailClosed(desired)
remove(diff.toRemove) в пачках
applied = actualRoutesFromOs()
if applied != desired: пометить drift и запланировать ремонт
```

## 11. Синхронизация и кеш

### 11.1. Расписание

`FR-150` (MUST). Базовый интервал синхронизации - 5-10 минут. Конкретное значение приходит из backend (`syncIntervalSec`), по умолчанию 420 секунд.

`FR-151` (MUST). К интервалу применяется случайный jitter ±20%, чтобы устройства не били в backend одновременно.

`FR-152` (MUST). Внеочередная синхронизация запускается при: подключении, пробуждении из сна, смене сети, ручной кнопке в режиме эксперта, возврате приложения из фона.

### 11.2. Условные запросы

`FR-153` (MUST). Клиент хранит `ETag` последнего успешного ответа и присылает `If-None-Match`. Ответ `304` обновляет только timestamp последней синхронизации.

### 11.3. Проверка целостности

`FR-154` (MUST). Клиент **MUST** проверять `contentHash` полученного списка: канонизировать записи (сортировка, нормализация), посчитать SHA-256 и сравнить.

`FR-155` (SHOULD). Backend **SHOULD** подписывать route list detached-подписью Ed25519, клиент **SHOULD** проверять подпись по публичному ключу, вшитому в сборку, с поддержкой `keyId` для ротации ключей. Реализация подписи обязательна к моменту публичной продажи подписок.

### 11.4. Anti-rollback

`FR-156` (MUST). Клиент хранит максимальную применённую `version` и отклоняет ответы с меньшей версией, кроме случая, когда backend прислал `resetVersion: true` вместе с валидной подписью.

### 11.5. TTL, grace и деградация

| Возраст кеша | Поведение |
| --- | --- |
| < TTL | нормальная работа |
| TTL .. TTL + grace (по умолчанию grace = 3 x TTL) | продолжаем работать на кеше, в режиме эксперта показывается предупреждение |
| > TTL + grace | состояние `degraded`, предупреждение обычному пользователю |
| > hardExpiry (по умолчанию 7 суток) | защищенные маршруты снимаются, fail-closed сохраняется до отключения, подключение требует успешной синхронизации |

`FR-157` (MUST). Политика stale-кеша **MUST** быть настраиваемой из backend в пределах разумных границ и иметь безопасные значения по умолчанию.

### 11.6. Retry и backoff

`FR-158` (MUST). Ошибки сети и `5xx` ретраятся с экспоненциальным backoff: 5 c, 10 c, 30 c, 60 c, 300 c (потолок), с jitter ±20%. Успех сбрасывает счетчик.

`FR-159` (MUST). Ошибки `4xx`, кроме `401` и `429`, не ретраятся автоматически: они означают проблему конфигурации или доступа.

`FR-160` (MUST). Ответ `429` **MUST** уважать заголовок `Retry-After`.

### 11.7. Старт офлайн

`FR-161` (MUST). При старте без сети клиент читает кеш, показывает состояние `disconnected` и позволяет подключиться, если кеш свежее `hardExpiry`.

`FR-174` (MUST). Удаление приложения удаляет все перечисленное выше, helper, autostart-записи, tunnel-профиль, маршруты и правила fail-closed.

## 13. Native Adapter и privileged helper

### 13.1. Контракт

Native layer отвечает за:

- запуск и остановку системного tunnel profile;
- чтение активных сетевых интерфейсов;
- применение и удаление маршрутов;
- применение правил fail-closed;
- защищенное хранение секретов;
- OS-specific autostart integration.

Native layer отдает в TypeScript-приложение небольшой command API.

### 13.2. Расширенный Command API

```ts
type TunnelState =
  | "disconnected"
  | "connecting"
  | "connected"
  | "degraded"
  | "error";

type TunnelStatus = {
  state: TunnelState;
  interfaceName?: string;
  endpointReachable: boolean;
  activeRouteCount: number;
  failClosedActive: boolean;
  helperVersion?: string;
  lastError?: NativeError;
};

type NativeError = {
  code: string;          // стабильный код, см. ERROR_CATALOG.md
  osCode?: number;       // код ОС, если есть
  stage: string;         // где произошло
  message: string;       // уже redacted
};

type RouteApplyResult = {
  applied: string[];
  failed: Array<{ route: string; code: string }>;
};

type NativeAdapter = {
  // статус и окружение
  getStatus(): Promise<TunnelStatus>;
  getActiveRoutes(): Promise<string[]>;
  getNetworkSnapshot(): Promise<{
    defaultGateway?: string;
    primaryInterface?: string;
    interfaces: Array<{ name: string; up: boolean }>;
  }>;

  // tunnel
  connect(): Promise<void>;
  disconnect(): Promise<void>;

  // маршруты
  applyRoutes(routes: string[]): Promise<RouteApplyResult>;
  removeRoutes(routes: string[]): Promise<RouteApplyResult>;
  applyLocalUserRoutes(routes: string[]): Promise<RouteApplyResult>;
  removeLocalUserRoutes(routes: string[]): Promise<RouteApplyResult>;

  // fail-closed
  enableFailClosed(routes: string[]): Promise<void>;
  updateFailClosed(routes: string[]): Promise<void>;
  disableFailClosed(): Promise<void>;

  // helper
  ensureHelperInstalled(): Promise<{ installed: boolean; version: string }>;
  repairHelper(): Promise<void>;
  uninstallHelper(): Promise<void>;

  // секреты и автозапуск
  secretsSet(key: string, value: string): Promise<void>;
  secretsGet(key: string): Promise<string | undefined>;
  secretsDelete(key: string): Promise<void>;
  setAutostart(enabled: boolean): Promise<void>;
};
```

`FR-180` (MUST). Все методы адаптера **MUST** быть идемпотентными и **MUST** возвращать типизированные ошибки из каталога, а не свободный текст.

`FR-181` (MUST). Все методы **MUST** иметь таймаут (по умолчанию 15 секунд, для установки helper - 90 секунд). Истечение таймаута - отдельный код ошибки.

`FR-182` (MUST). Адаптер **MUST** возвращать сообщения уже в redacted виде: адреса endpoint заменяются на стабильный хеш.

### 13.3. IPC и аутентификация вызывающего

`SEC-020` (MUST). Канал между приложением и helper **MUST** быть локальным и недоступным другим пользователям системы.

`SEC-021` (MUST). Helper **MUST** проверять подлинность вызывающего процесса средствами платформы (на macOS - проверка code signing requirement вызывающего; на Windows - проверка SID и подписи).

`SEC-022` (MUST). Helper **MUST** валидировать все аргументы: маршруты как строгие CIDR, имена интерфейсов по allowlist-шаблону, размер батча по лимиту.

`SEC-023` (MUST). Helper **MUST NOT** выполнять команды shell, собранные из входных данных, и **MUST NOT** принимать пути к файлам от вызывающего.

### 13.4. Версионирование протокола

`FR-183` (MUST). Протокол helper имеет числовую версию. При несовпадении с ожидаемой приложение предлагает переустановить helper и не выполняет операции по несовместимому протоколу.

`FR-184` (MUST). Обновление приложения **MUST** уметь обновить helper без ручных действий пользователя, кроме одного системного запроса прав.

### 13.5. Жизненный цикл helper

| Операция | Когда | Поведение |
| --- | --- | --- |
| install | первое подключение | один системный запрос прав, объяснение зачем |
| verify | каждый старт приложения | проверка наличия, версии и отклика |
| repair | verify не прошел | предложение переустановить, кнопка в UI |
| upgrade | обновление приложения | автоматически при первом запуске новой версии |
| uninstall | удаление приложения / кнопка в настройках | снятие всех правил и удаление компонента |

## 14. Fail-Closed

### 14.1. Что защищаем

Утечкой считается ситуация, когда пакет к protected destination уходит через физический интерфейс, а не через tunnel. Основные окна утечки:

1. tunnel упал, а маршруты еще указывают на старый интерфейс;
2. интерфейс tunnel исчез, ОС вернула маршруты на шлюз по умолчанию;
3. смена сети: старые маршруты сняты, новые еще не применены;
4. запуск приложения до поднятия tunnel при включенном автоподключении;
5. аварийное завершение приложения при активном подключении.

### 14.2. Требования

`FR-190` (MUST). Fail-closed **MUST** блокировать трафик к protected destinations на всех интерфейсах, кроме tunnel-интерфейса.

`FR-191` (MUST). Правила fail-closed **MUST** переживать исчезновение tunnel-интерфейса: блокировка не должна зависеть от существования интерфейса.

`FR-192` (MUST). Трафик к tunnel endpoint **MUST** оставаться разрешенным, иначе reconnect невозможен.

`FR-193` (MUST). DNS-запросы к системным резолверам **MUST NOT** блокироваться целиком; блокируются только protected destinations.

`FR-194` (MUST). Локальная сеть пользователя (шлюз, принтеры, NAS) **MUST** оставаться доступной, если явно не включено обратное.

### 14.3. macOS

- Правила применяются privileged helper через packet filter и таблицу маршрутов.
- Набор protected destinations выносится в отдельную именованную таблицу/якорь, чтобы не конфликтовать с чужими правилами.
- При выключении приложение удаляет только свой якорь.
- Альтернатива при ограничениях платформы - system network extension; решение фиксируется в OQ-2.

### 14.4. Windows

- Маршруты в таблице маршрутизации плюс правила Windows Filtering Platform или firewall, если одних маршрутов недостаточно.
- Правила помечаются собственным именем группы для безопасного удаления.

### 14.5. Android

- Реализация внутри системного Android tunnel service.
- Эквивалент fail-closed достигается настройками самого сервиса, отдельная таблица маршрутов недоступна.

### 14.6. Поведение при завершении приложения

`FR-195` (MUST). При штатном выходе приложение снимает fail-closed и маршруты.

`FR-196` (MUST). При аварийном завершении fail-closed **MUST** оставаться активным (это безопасное состояние). При следующем старте приложение обнаруживает "осиротевшие" правила и предлагает подключиться заново или снять защиту.

`FR-197` (MUST). Helper **MUST** иметь механизм автоматического снятия правил, если приложение не выходило на связь дольше заданного времени (по умолчанию 24 часа), чтобы пользователь не остался с непонятной блокировкой навсегда.

### 14.7. Проверка (leak test)

Обязательные проверки перед релизом:

| # | Проверка | Ожидание |
| --- | --- | --- |
| L1 | Подключено, запрос к protected IP | идет через tunnel-интерфейс |
| L2 | Принудительно останавливаем tunnel | запрос к protected IP не проходит вообще |
| L3 | Отключаем Wi-Fi и включаем снова | утечек нет ни в один момент переключения |
| L4 | Sleep/wake | после пробуждения либо tunnel восстановлен, либо доступ заблокирован |
| L5 | Убиваем процесс приложения | protected IP остается заблокирован |
| L6 | Смена сети Wi-Fi -> Ethernet | утечек нет |
| L7 | Запрос к non-protected IP во всех состояниях | всегда проходит напрямую |
| L8 | Доступ к локальной сети | сохраняется |

`T-001` (MUST). Leak-тесты **MUST** выполняться с фиксацией сетевого трафика на физическом интерфейсе, а не только по факту доступности сервиса.

## 15. Backend API

Клиент работает только через backend API. Backend поддерживает клиентский контур отдельно от приватного серверного контура; изменения обратно совместимы с админкой, Telegram-ботом и серверным Tunnel Manager.

Endpoints:

| Метод и путь | Назначение |
| --- | --- |
| `POST /client/v1/auth/activate` | активация устройства и выдача токенов |
| `POST /client/v1/auth/refresh` | обновление access token |
| `GET /client/v1/profile` | пользователь, подписка, политики, версия |
| `GET /client/v1/routes` | route list с версией, хешем, TTL |
| `GET /client/v1/endpoint` | metadata tunnel-точки |
| `POST /client/v1/events` | легкие события |
| `POST /client/v1/diagnostics` | диагностика и validation errors |
| `POST /client/v1/error-reports` | redacted отчеты об ошибках |

Общие правила:

`API-001` (MUST). Все ответы содержат `serverTime` для коррекции расхождения часов и `minSupportedVersion`.

`API-002` (MUST). Все ошибки возвращаются в едином формате с машинным `code` и человеческим `message`.

`API-003` (MUST). Все мутирующие запросы поддерживают `Idempotency-Key`.

`API-004` (MUST). Backend применяет rate limit per device и возвращает `Retry-After`.

Полная спецификация с телами запросов и ответов - [API_SPEC.md](API_SPEC.md).

### 15.1. Ответ со списком маршрутов

Route list включает:

- версию списка;
- content hash;
- время генерации;
- TTL;
- группировку по сервисам;
- IPv4 CIDR;
- IPv6 CIDR, когда платформа поддерживается;
- опциональный emergency blocklist;
- минимальную поддерживаемую версию приложения.

Клиент игнорирует невалидные CIDR и отправляет validation errors в диагностику.

### 15.2. События

Клиент отправляет легкие события:

- приложение запущено;
- подключение начато или остановлено;
- синхронизация маршрутов успешна или неуспешна;
- fail-closed активирован или деактивирован;
- подписка истекла;
- версия приложения.

`SEC-030` (MUST). События **MUST NOT** содержать посещенные URL, payload, историю браузинга или содержимое трафика.

### 15.3. Error reports

`POST /client/v1/error-reports` принимает redacted отчет. Backend:

- проверяет доступ пользователя и устройства;
- сохраняет отчет;
- дедуплицирует повторы по fingerprint;
- применяет rate limit;
- отправляет важные новые ошибки администраторам в Telegram;
- не отправляет в Telegram шумные события и повторы.

Ответ сообщает клиенту, был ли отчет принят и был ли он отправлен администраторам. Пользователю показывается простой статус: "Ошибка отправлена" или "Не удалось отправить, попробуйте позже".

## 17. Безопасность

### 17.1. Базовые требования

- Клиенты не подключаются к базе данных напрямую.
- Production secrets не хардкодятся.
- API access tokens отзывные.
- Route lists подписаны или hash-validated.
- Backend проверяет subscription/access state.
- Клиент учитывает minimum API compatibility.
- Логи скрывают secrets и endpoint credentials.
- Public repository не содержит production infrastructure details.
- Новый клиентский контур не дает публичным пользователям доступ к приватному серверному контуру.

### 17.2. Модель угроз

| # | Угроза | Митигация |
| --- | --- | --- |
| TH-1 | Утечка защищенного трафика мимо tunnel | fail-closed, watchdog, leak-тесты (разделы 6.5, 14) |
| TH-2 | Кража refresh token с устройства | хранение в OS keystore, ротация при refresh, отзыв на backend |
| TH-3 | Подмена route list посредником | TLS, content hash, подпись Ed25519, anti-rollback |
| TH-4 | Откат на старый список маршрутов | монотонная версия, отклонение старых версий |
| TH-5 | Локальная эскалация через helper | ограниченный набор команд, проверка вызывающего, валидация аргументов |
| TH-6 | Утечка PII в отчетах и логах | allowlist-сериализация, redaction-фильтры, запрет свободного текста |
| TH-7 | Доступ клиентского контура к приватному | раздельный namespace, отдельные токены, тесты авторизации |
| TH-8 | Раскрытие инфраструктуры через публичный репозиторий | запрет реальных адресов и ключей, проверка в CI |
| TH-9 | DoS на backend от массы клиентов | jitter, backoff, условные запросы, rate limit на стороне backend |
| TH-10 | Использование отозванного устройства | короткий TTL access token, проверка отзыва при каждом refresh |

### 17.3. Токены

| Параметр | Значение по умолчанию |
| --- | --- |
| TTL access token | 15 минут |
| TTL refresh token | 30 суток, продлевается при использовании |
| Ротация refresh | при каждом использовании, старый инвалидируется |
| Обнаружение переиспользования | использование инвалидированного refresh отзывает устройство |
| Хранение access | только память процесса |
| Хранение refresh | OS keystore |

### 17.4. Канал

`SEC-040` (MUST). Все обращения к backend только по HTTPS с проверкой сертификата.

`SEC-041` (SHOULD). Клиент **SHOULD** использовать pinning публичного ключа backend с запасным ключом и процедурой ротации. Pinning без запасного ключа запрещен.

### 17.5. Публичный репозиторий

`SEC-042` (MUST). В репозитории **MUST NOT** быть: реальных адресов tunnel-точек и backend, private keys, tokens, admin-only endpoints, дампов конфигурации. Для примеров используются заглушки.

`SEC-043` (MUST). CI **MUST** содержать шаг проверки на секреты и на IP/hostname-паттерны в коммитах.

## 19. Платформенные требования

### 19.1. macOS Apple Silicon (MVP)

Реализация начинается с наименее рискованного варианта:

- Tauri desktop app;
- helper process для privileged route operations;
- управление OS tunnel profile;
- Keychain для секретов;
- LaunchAgent/LaunchDaemon для фоновой работы, если понадобится.

Дополнительно:

`FR-210` (MUST). Приложение **MUST** подписываться и нотаризоваться, иначе Gatekeeper не даст установить его пользователю.

`FR-211` (MUST). Установка helper **MUST** идти через штатный системный механизм установки привилегированных сервисов, один запрос прав, с понятным объяснением до появления системного диалога.

Открытый вопрос: начинать с существующего OS tunnel profile flow или сразу переходить на NetworkExtension, если управление профилем окажется слишком ограниченным (OQ-2).

### 19.2. Windows

- Native desktop build через Tauri.
- PowerShell/VPN client APIs для настройки профиля и маршрутов там, где это надежно.
- Windows Filtering Platform или firewall rules для fail-closed, если маршрутов недостаточно.
- Credential Manager/DPAPI для секретов.
- Scheduled task или служба для фоновой работы.
- Установщик MSI/NSIS с корректным uninstall cleanup.

### 19.3. Android

Android требует отдельного technical spike. Скорее всего нужно использовать системную модель Android tunnel service; относиться к Android как к desktop route management нельзя.

Ключевые вопросы spike:

- реализовывать ли tunnel полностью внутри приложения;
- встраивать ли существующую tunnel-библиотеку;
- как сохранить единый UX с desktop;
- как поддержать always-on behavior;
- какие требования Google Play применимы к категории приложения.
