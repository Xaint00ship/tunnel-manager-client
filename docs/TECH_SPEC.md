## 0. Как читать документ

Требования пронумерованы стабильными идентификаторами и не должны менять номер после утверждения:

- `FR-*` - функциональные требования;
- `NFR-*` - нефункциональные требования;
- `SEC-*` - требования безопасности;
- `UX-*` - требования к интерфейсу;
- `T-*` - требования к тестированию.

Уровни обязательности:

- **MUST** - обязательно для MVP, без этого релиз не принимается;
- **SHOULD** - желательно в MVP, допускается перенос с записанным обоснованием;
- **MAY** - опционально, реализуется по остаточному принципу.

Каждое требование должно быть трассируемо: требование -> issue -> тест. Требование без теста считается нереализованным.

## 1. Назначение и контекст

### 1.1. Что это за продукт

Tunnel Manager Client - кроссплатформенное клиентское приложение, которое устанавливается на устройство пользователя и локально управляет защищенной split-routing логикой. Приложение подключает устройство к зарубежной tunnel-точке, получает из центрального backend API whitelist маршрутов, применяет его к системной таблице маршрутизации и гарантирует, что защищенные направления не уходят в обычную сеть при недоступности tunnel.

Backend остается ответственным за пользователей, подписки, списки маршрутов, metadata tunnel-точек, аналитику и уведомления администраторам. Клиент отвечает за подключение устройства, синхронизацию, применение маршрутов и fail-closed.

### 1.2. Проблема, которую решаем

Текущая серверная схема требует регионального relay/gateway-сервера, через который проходит трафик всех пользователей. Это дает:

- единую точку отказа и единую точку блокировки;
- расходы на региональный сервер и его пропускную способность;
- рост задержки из-за лишнего сетевого плеча;
- сложность масштабирования при росте числа подписчиков.

Целевая схема: устройство пользователя подключается напрямую к зарубежной tunnel-точке, а региональный gateway убирается из data plane. В инфраструктуре остаются только tunnel-точки и легкий backend/control plane, который не передает пользовательский трафик.

### 1.3. Разделение контуров

Существующий серверный Tunnel Manager остается в эксплуатации. Он не удаляется, не отключается и не мигрирует в рамках этого проекта. Он нужен для приватного использования владельцем и доверенными пользователями.

Новый Tunnel Manager Client - отдельный коммерческий продукт для продажи подписок. Он использует общий backend/control plane там, где это удобно, но не требует демонтажа текущей серверной схемы.

Разработка клиента **MUST NOT** ломать:

- существующие серверные подключения;
- текущую админку;
- Telegram-бота;
- backend API, который уже используется серверным контуром;
- текущие правила whitelist приватного контура.

Технические следствия разделения:

| Аспект | Приватный серверный контур | Коммерческий клиентский контур |
| --- | --- | --- |
| Namespace API | текущие пути без изменений | только `/client/v1/*` |
| Аутентификация | как сейчас | отдельные device-токены |
| Whitelist | общий список дашборда | тот же список в JSON-проекции; правка из приложения меняет его для обоих контуров |
| Выкатка | не затрагивается | независимый релизный цикл |
| Аварийное отключение | недоступно из клиентского контура | kill-switch только для клиентского контура |

Что у контуров общее, а что раздельное, и кто это меняет:

| Данные | Источник правды | Кто меняет | Затрагивает приватный контур |
| --- | --- | --- | --- |
| Список маршрутов (`groups`, `ips`) | дашборд на RU | админка дашборда, бот `/addip`, админ-панель приложения (1.1) с теми же guardrails | да: менеджер на RU подхватит при следующем refresh или по «применить сейчас» |
| Пользователи и подписки (`tunnel_users`) | дашборд на RU | админка, бот, админ-панель приложения через admin API `client-api` | да: это одни и те же пользователи |
| Устройства, коды активации, ключи WireGuard и EAP-учетки клиентского контура | `client-api` за рубежом | только `client-api` | нет |
| IKEv2-учетки и peer приватного контура на RU | RU-сервер | бот и админка, как сегодня | клиентский контур их не видит |

`SEC-001` (MUST). Клиентский контур **MUST NOT** обращаться к admin-only endpoints дашборда напрямую: все, что приложение может изменить, идет через admin API `client-api` под ролью `admin`, с аудитом и теми же guardrails, что у бота. Из приложения приватный контур затрагивают две операции: правка общего списка маршрутов (1.1) и управление общими пользователями и подписками - продление, отключение, включение действуют на те же аккаунты, что ходят по IKEv2 на RU-сервер. Интерфейс **MUST** говорить об этом явно в обоих разделах. Разграничение проверяется отдельными тестами авторизации.

### 1.4. Глоссарий

| Термин | Значение |
| --- | --- |
| Tunnel-точка (endpoint) | зарубежный сервер, к которому подключается устройство пользователя |
| Control plane / backend | HTTP API, который выдает конфигурацию, проверяет доступ и принимает события |
| Data plane | собственно tunnel-соединение устройства с endpoint; backend в нем не участвует |
| Whitelist / route list | список сетевых префиксов, которые должны идти через tunnel |
| Protected destination | адрес, попадающий в whitelist |
| Split routing | режим, при котором через tunnel идет только whitelist, остальное - напрямую |
| Fail-closed | режим, при котором защищенные направления блокируются, если tunnel недоступен |
| Route drift | расхождение между желаемым набором маршрутов и фактическим состоянием ОС |
| Privileged helper | системный компонент с повышенными правами, выполняющий сетевые операции |
| Native adapter | тонкий platform-специфичный слой между TypeScript-ядром и ОС |
| Режим эксперта | отключаемый по умолчанию раздел UI с технической диагностикой |
| Device | конкретная установка приложения, зарегистрированная в backend |
| Fingerprint | стабильный хеш ошибки для дедупликации отчетов |

### 1.5. Что существует сегодня

Изучено по коду репозиториев `tunnel_manager` и `tunnel-dashboard-backend` (2026-09-03).

```text
устройство ──IKEv2 (strongSwan, EAP) или WireGuard (wg0)──► RU-сервер ──IPsec «import VPN»──► зарубежная точка
                                                             │
                                                             └─ tunnel_manager (демон): listed → import VPN, остальное → RU egress
```

- Один Linux-сервер: strongSwan (IKEv2 EAP), WireGuard (`wg0`), dnsmasq на tunnel-адресах, per-user rate limit, `tunnel_manager` как split-демон, FastAPI-дашборд с Postgres, Telegram-бот.
- Пользователь получает доступ через бота: заявка, одобрение админом, пробная подписка на 7 дней, конфиг под ОС: mobileconfig для iOS и macOS, `.sswan` для Android, ручная настройка IKEv2 для Windows; с 2026-08-30 - WireGuard `.conf` из карточки пользователя.
- WireGuard-клиенты получают `AllowedIPs = 0.0.0.0/0`: весь трафик идет на RU-сервер, и уже он делит его по списку.
- Список маршрутов - таблицы `groups` и `ips` дашборда: вручную курируемые IP и CIDR по сервисам. Менеджеру отдается текстом через `GET /api/routes` с `X-Api-Key`. Grey list помогает находить новые адреса из логов. Резолва доменов нет.
- `tunnel_manager` умеет работать и на desktop (macOS, Windows, Linux): пользователь вручную подключает системный VPN-профиль, демон находит интерфейс, снимает catch-all default и ставит маршруты по списку. Fail-closed через blackhole реализован только на Linux.

Новый клиент заменяет связку «системный VPN-профиль + tunnel-manager демон + RU-сервер как gateway» одним приложением, которое подключается напрямую к зарубежной точке и делит трафик на устройстве. Проверенное поведение демона переносится в клиент, см. приложение B.

Целевая схема:

```text
устройство ──WireGuard или IKEv2 + HTTPS──► зарубежный сервер владельца: wg0, strongSwan + client-api (/client/v1/*)
     │                                        ▲ pull списка (/api/routes) и статусов подписок
     └─ всё вне списка напрямую               │ push отчетов об ошибках (/api/notify)
                                     RU-сервер: дашборд, Postgres, бот, приватный контур (не меняется)
```

Клиент общается только с зарубежным сервером: там и авторизация, и туннель. RU-сервер остается источником правды для списка и подписок, но клиент к нему не ходит; зарубежный backend забирает данные сам и работает на копии, если RU недоступен ([ADR-004](decisions/ADR-004-control-plane-placement.md)).

## 2. Цели, метрики и критерии успеха

### 2.1. Продуктовые цели

1. Пользователь ставит приложение, входит, нажимает одну кнопку и дальше не думает о технике.
2. Защищенные направления работают стабильно и не утекают мимо tunnel.
3. Проблемы подключения видны администраторам без обращения пользователя в поддержку.
4. Продукт готов к продаже подписок: доступ ограничен, подписка проверяется, отзыв устройства работает.

### 2.2. Технические цели

1. Убрать региональный relay/gateway из data plane.
2. Оставить в инфраструктуре только tunnel-точки и легкий control plane.
3. Перенести синхронизацию и применение маршрутов на устройство пользователя.
4. Держать продуктовую логику на TypeScript, а native-код ограничить адаптерами и privileged helper.
5. Переиспользовать поведение текущего Tunnel Manager там, где оно уже проверено.

Где на самом деле риск и трудозатраты. TypeScript-ядро (state machine, diff, синхронизация, кеш) - понятная и дешевая часть. Основной объем работы и почти весь риск лежат в native-части: туннель, маршруты, fail-closed, helper с IPC, подпись сборок, uninstall, и все это на двух ОС. Формулировка "TypeScript основной, native маленький" описывает архитектуру, а не распределение усилий. Проекту нужен человек, способный на системное программирование на macOS и Windows, и дорожная карта построена так, чтобы это выяснилось в первые недели (фаза 1, walking skeleton), а не на фазе упаковки.

### 2.3. Метрики MVP

| Метрика | Цель MVP |
| --- | --- |
| Доля успешных подключений | >= 97% попыток |
| Время от нажатия "Подключить" до `connected` | p50 <= 3 c, p95 <= 8 c |
| Задержка доставки изменения whitelist до устройства | p95 <= 15 минут от изменения в дашборде: бюджет RU -> `client-api` до 5 минут (`API-110`), `client-api` -> клиент до 10 минут (`syncIntervalSec` 420 с плюс jitter 20%) |
| Доля устройств с актуальным whitelist (возраст < 2 x TTL) | >= 98% активных |
| Автоматическое восстановление route drift | >= 99% случаев без участия пользователя |
| Утечки защищенных направлений при недоступном tunnel | 0 в leak-тестах |
| Шум в админском Telegram | <= 20 уникальных сообщений в сутки на 100 активных устройств |

### 2.4. Definition of Done для MVP (macOS и Windows)

MVP выходит сразу на двух desktop-платформах. Платформы равноправны: релиз не принимается, если приемка провалена хотя бы на одной из них.

Общая часть, обязательная для обеих платформ:

- все требования уровня MUST разделов 6, 14 и 17 реализованы и покрыты тестами;
- ручная матрица тестов раздела 21 пройдена на чистой машине каждой платформы;
- leak-тест fail-closed пройден во всех сценариях раздела 14.7 на каждой платформе;
- удаление приложения не оставляет маршрутов, helper и сломанной сети;
- backend отдает `/client/v1/*` и присылает администраторам только actionable ошибки;
- обе сборки выходят из одного CI по одному тегу и имеют одинаковую версию.

Платформенная часть:

| Платформа | Дополнительное условие приемки |
| --- | --- |
| macOS | собран подписанный и нотаризованный DMG, установленный тестером с нуля |
| Windows | собран подписанный установщик, проходящий SmartScreen, установленный тестером с нуля |

`FR-005` (MUST). Функциональность обеих платформ **MUST** быть одинаковой с точки зрения пользователя. Расхождения допускаются только там, где их диктует ОС, и **MUST** быть перечислены в разделе 19.4.

## 3. Границы MVP

### 3.1. Входит в MVP

- macOS на Apple Silicon: полный пользовательский путь от установки до удаления.
- Windows 10 21H2+ и Windows 11 на x64: полный пользовательский путь от установки до удаления.
- Активация устройства, проверка подписки, отзыв доступа.
- Синхронизация whitelist, локальный кеш, применение и снятие маршрутов.
- Watchdog маршрутов и автоматический ремонт drift.
- Fail-closed, включенный по умолчанию.
- Режим эксперта с диагностикой, выбором транспорта и режима DNS; локальные правила - 1.1.
- Автоматические и ручные отчеты об ошибках администраторам.
- Архитектурные точки расширения под Android (без релиза).

### 3.2. Не входит в MVP

- Демонтаж или отключение существующего серверного Tunnel Manager.
- Перевод приватных пользователей на новое клиентское приложение.
- Обязательная миграция текущей серверной инфраструктуры.
- Прямое подключение клиента к базе данных.
- Анализ содержимого трафика.
- Enterprise MDM-деплой.
- Linux-клиент.
- Windows on ARM и Intel-маки: сборки закладываются в CI, но в приемку MVP не входят.
- Полноценный Android-релиз до отдельного technical spike.
- Публикация инфраструктурных секретов, адресов серверов, private keys, tokens и admin-only endpoints.
- Биллинг и прием платежей внутри приложения: подписка выдается вне клиента.
- Мультиаккаунт и переключение профилей внутри одной установки.

### 3.3. Ограничения совместимости

`FR-001` (MUST). Клиент **MUST** работать только через backend API и **MUST NOT** обращаться к базе данных напрямую ни в каком режиме, включая режим эксперта и диагностику.

`FR-002` (MUST). Изменения backend для клиентского контура **MUST** быть обратно совместимы с работающей админкой, Telegram-ботом и серверным Tunnel Manager.

`FR-003` (MUST). Приложение **MUST** оставаться работоспособным офлайн на последнем валидном кеше whitelist в пределах политики TTL/grace (раздел 11.5).

Чтобы 1.0 вышел, объем сужен. Требования с пометкой "(MUST, 1.1)" обязательны для продукта, но не блокируют первый релиз.

## 4. Акторы и роли

| Актор | Описание | Что делает |
| --- | --- | --- |
| Обычный пользователь | владелец подписки | ставит приложение, активирует, подключается, отключается |
| Продвинутый пользователь | тот же пользователь с включенным режимом эксперта | смотрит диагностику, выбирает транспорт и режим DNS, шлет ошибку вручную; локальные правила с 1.1 |
| Администратор | владелец продукта | получает уведомления в Telegram, выдает и отзывает доступ, правит whitelist |
| Backend / control plane | сервис | проверяет доступ, отдает конфигурацию, дедуплицирует ошибки, шлет уведомления |
| Tunnel endpoint | зарубежная точка | принимает tunnel-соединение устройства |
| ОС устройства | macOS / Windows / Android | дает tunnel API, таблицу маршрутов, firewall и защищенное хранилище |
| Privileged helper | системный компонент | выполняет привилегированные сетевые операции по ограниченному протоколу |

## 5. Пользовательские сценарии

### 5.0. Как пользователь получает доступ

Авторизация - только через существующий Telegram-бот. У приложения нет своих логинов, паролей и регистрации: онбординг с одобрением заявки админом, пробная подписка, продление и отключение остаются в боте как есть. Технически подтверждение проходит через `client-api` (раздел 15.6), но для пользователя единственное место, где он «входит», - бот. Приложение ни в каком виде не участвует в оплате.

Основной сценарий, deep link:

```text
1. приложение: «Войти через Telegram» -> client-api выдает код связки
2. приложение открывает t.me/<бот>?start=link_<код>; на десктопе рядом QR для телефона
3. бот: /start link_<код> -> находит пользователя по Telegram ID, проверяет подписку,
   при необходимости запускает обычный онбординг -> подтверждает код в client-api
4. приложение опрашивает client-api -> получает токены -> устройство зарегистрировано
```

Запасной сценарий, код вручную: кнопка «Активировать приложение» в меню бота выдает одноразовый код, пользователь вводит его в приложении. Нужен, когда Telegram стоит не на том устройстве, где ставится клиент. Тот же код администратор может выдать из карточки пользователя.

Пробный период запускается из приложения: кнопка «Начать пробный период» на экране активации ведет в тот же deep link с пометкой `intent=trial`. Бот создает пробную подписку по существующей логике онбординга, включая одобрение админом, если оно включено, срок берет из настроек `client-api` (`trialDays`, раздел 6.14) и подтверждает код связки. Пользователь видит в приложении дату окончания пробного периода.

`FR-008` (MUST). Оба сценария обслуживает `client-api`; бот - единственный интерфейс авторизации для человека. Коды из бота и из админки имеют один формат и срок жизни, клиент источник не различает.

`FR-009` (MUST). Приложение **MUST NOT** регистрировать новых пользователей само и **MUST NOT** иметь форму логина и пароля. Пользователь без подписки получает из бота обычный онбординг, а приложение показывает «дождитесь подтверждения в Telegram».

### 5.1. Основной сценарий

| Шаг | Действие | Состояние клиента | Что происходит внутри |
| --- | --- | --- | --- |
| 1 | Пользователь устанавливает приложение | - | helper еще не установлен |
| 2 | Первый запуск | `unactivated` | показывается экран активации |
| 3 | Пользователь входит через бота | `activating` | `device-code` -> подтверждение в боте -> `device-token`, либо `activate` кодом; на сервере регистрируются устройство, peer и EAP-учетка |
| 4 | Клиент получает профиль и endpoint | `disconnected` | `GET /client/v1/profile`, `GET /client/v1/endpoint`, секреты в OS keystore |

| 7 | Клиент загружает whitelist и применяет конфигурацию | `connecting` | `GET /client/v1/routes` или кеш, валидация, одна операция `applyConfiguration`: блокировка, маршруты, DNS (13.6) |

### 5.2. Альтернативные и аварийные сценарии

| # | Сценарий | Ожидаемое поведение |
| --- | --- | --- |

| A1a | Backend недоступен, endpoint достижим, приложение стартует | подключение по офлайн-профилю (`FR-161a`), в режиме эксперта видно, что профиль из кеша |
| A2 | Backend недоступен, tunnel работает | остаемся `connected`, whitelist из кеша, обычный UI не меняется, в режиме эксперта - "синхронизация недоступна" |
| A3 | Backend недоступен дольше grace | переход в `degraded`, предупреждение пользователю, политика stale-кеша (раздел 11.5) |

| A8 | Сон и пробуждение устройства | проверка и восстановление tunnel и маршрутов не позже 10 секунд после wake |
| A9 | Смена сети (Wi-Fi -> LTE, смена SSID) | пересоздание маршрутов на новом интерфейсе, fail-closed не снимается на время переключения |

| A11 | Токен устройства отозван | немедленное отключение, очистка секретов, возврат на экран активации |
| A12 | Версия приложения ниже минимальной | блокировка подключения, экран "обновите приложение" со ссылкой |
| A13 | Whitelist содержит невалидные записи | невалидные игнорируются, остальные применяются, validation errors уходят в диагностику |
| A14 | Whitelist не прошел проверку подписи или хеша | список отклоняется целиком, работаем на предыдущем кеше, автоматический отчет админам |
| A15 | Route drift | watchdog восстанавливает маршруты, событие в диагностику, отчет админам только при повторных неудачах ремонта |

| A17 | Удаление приложения | uninstall снимает маршруты, fail-closed, helper и autostart, сеть остается рабочей |
| A18 | Туннель упал при DNS через точку | системный DNS возвращен за 5 секунд после обнаружения потери (`FR-187`), интернет вне списка работает, защищенные адреса заблокированы (`FR-167b`) |
| A19 | Старт приложения, а helper еще держит правила после аварии | `error` с текстом «Защита активна, соединение не восстановлено», кнопки «Подключить» и «Снять защиту»; при автоподключении - сразу `reconnecting` (`FR-196`) |

### 5.3. Жизненный цикл устройства

```text
unregistered -> activated -> active (подписка валидна)
                               |-> suspended (подписка истекла, устройство сохранено)
                               |-> revoked   (админ отозвал доступ, нужна повторная активация)
                               |-> removed   (приложение удалено или устройство отвязано)
```

`FR-004` (MUST). Переход в `suspended` или `revoked` **MUST** приводить к снятию защищенных маршрутов и fail-closed не позднее 60 секунд после того, как клиент узнал о смене состояния. Клиент узнает о ней при refresh (не реже 15 минут) или при `profile`; на сервере peer и EAP-учетка снимаются не позже 60 секунд после того, как событие дошло до `client-api` (`API-097`, `API-120a`), так что отозванное устройство теряет туннель раньше, чем клиент это отобразит.

## 6. Функциональные требования

### 6.1. Активация и аутентификация

`FR-010` (MUST). Приложение **MUST** поддерживать два способа активации через бота: deep link с опросом статуса подтверждения и ручной ввод кода (раздел 5.0). Других способов входа нет. Архитектура **MUST** позволять добавить способ без переписывания клиента.

`FR-011` (MUST). При активации клиент **MUST** зарегистрировать устройство и получить пару токенов: короткоживущий access token и долгоживущий refresh token.

`FR-012` (MUST). Access token **MUST** храниться только в памяти процесса и не записываться на диск. Refresh token **MUST** храниться в защищенном хранилище ОС (раздел 12.4).

`FR-013` (MUST). Клиент **MUST** обновлять access token заранее - не позже чем за 20% времени жизни до истечения, и **MUST** уметь обновить его по ответу `401`. Для refresh действующий access token не нужен (`API-023`): после перезапуска и после истечения access token клиент восстанавливает сессию одним refresh token.

`FR-013a` (MUST). Refresh **MUST** быть сериализован и восстанавливаем: одновременно в полете не больше одного запроса, конкурентные `401` ждут его результата и повторяют свой запрос один раз; до отправки клиент пишет в keystore запись `pendingRefresh` с `Idempotency-Key` и старым токеном, после сохранения нового refresh token удаляет ее; при старте с непустой записью он повторяет тот же запрос с тем же ключом (`API-024`-`API-026`). То же правило для получения токенов при активации: `device-token` повторяет сохраненный ответ до истечения кода (`API-019`), `activate` идемпотентен по ключу, записанному до отправки (`API-014a`). Штатное восстановление после потери ответа или падения **MUST NOT** приводить к отзыву устройства.

`FR-014` (MUST). При ответе backend о том, что устройство отозвано, клиент **MUST**: отключиться, снять маршруты и fail-closed, удалить refresh token и локальный кеш маршрутов, вернуться на экран активации.

`FR-015` (MUST). Клиент **MUST** генерировать стабильный `deviceId` при первой активации и переиспользовать его при перезапусках. `deviceId` **MUST NOT** содержать серийный номер устройства, MAC-адрес или другие аппаратные идентификаторы в открытом виде.

`FR-016` (SHOULD). При переустановке приложения на том же устройстве клиент **SHOULD** предлагать повторную активацию, а backend **SHOULD** уметь заменить старую регистрацию, чтобы не расходовать лимит устройств.

### 6.2. Подключение и отключение

`FR-020` (MUST). Главное действие приложения - одна кнопка, которая переключает состояние между "Подключить" и "Отключить".

`FR-021` (MUST). Перед подключением клиент **MUST** проверить: наличие refresh token в keystore (access token не обязателен, он получается refresh-ем по `FR-013a`), состояние подписки, минимальную поддерживаемую версию приложения, доступность и работоспособность helper, наличие профиля подключения. Клиент пытается обновить профиль и endpoint у backend; если control plane недоступен, проверки выполняются по офлайн-профилю (раздел 11.7), и подключение разрешается, пока он действителен. Отсутствие сети вообще подключение не блокирует: попытка уходит в helper и завершается `transport_unreachable` с удержанной защитой, как любое недостижимое подключение.

`FR-022` (MUST). Подключение **MUST** быть атомарным с точки зрения пользователя: если любой обязательный шаг (tunnel, маршруты, fail-closed) не выполнен, клиент **MUST** откатить частично применённые изменения и перейти в `error`, а не остаться в полуприменённом состоянии.

`FR-023` (MUST). Отключение по кнопке **MUST** снимать защищенные маршруты, снимать fail-closed и останавливать tunnel в этом порядке, чтобы не оставить заблокированных направлений без tunnel.

`FR-024` (MUST). Клиент **MUST** поддерживать автоматический reconnect при падении tunnel: каждая попытка - `applyConfiguration` с `rebuild: true` (13.6, шаг 4), попытки идут с backoff и чередуют транспорты по политике `FR-260`; после 5 неудачных циклов - переход в `error` с отчетом администраторам. Защита остается активной все это время.

`FR-025` (SHOULD). Клиент **SHOULD** поддерживать опцию "подключаться автоматически при запуске", выключенную по умолчанию.

`FR-026` (MUST). Клиент **MUST** поддерживать два транспорта, WireGuard и IKEv2, за одним контрактом helper: маршруты, fail-closed, watchdog и диагностика от транспорта не зависят (раздел 6.13).

### 6.3. Синхронизация whitelist

`FR-030` (MUST). Клиент **MUST** синхронизировать whitelist с backend с интервалом 5-10 минут (раздел 11.1).

`FR-031` (MUST). Клиент **MUST** сохранять последнюю валидную версию whitelist локально и использовать ее при старте до первой успешной синхронизации.

`FR-032` (MUST). Клиент **MUST** проверять целостность полученного списка: content hash всегда, криптографическую подпись - с 1.1 (`FR-155`, раздел 11.3).

`FR-033` (MUST). Клиент **MUST** игнорировать невалидные записи списка и отправлять validation errors в диагностику, не отбрасывая при этом валидную часть списка.

`FR-034` (MUST). Клиент **MUST** отклонять список целиком, если не сошелся hash или подпись, и продолжать работу на предыдущем валидном кеше.

`FR-035` (MUST). Клиент **MUST** отклонять список с версией ниже уже применённой (anti-rollback), если backend явно не прислал флаг сброса версии.

`FR-036` (MUST). Синхронизация **MUST** использовать условные запросы (`ETag`/`If-None-Match`), чтобы не скачивать неизменившийся список.

`FR-037` (SHOULD). Синхронизация **SHOULD** выполняться и в состоянии `disconnected`, чтобы кеш был свежим к моменту подключения.

`FR-038` (MUST). Список, который распарсился в ноль записей, **MUST** отклоняться целиком, как и невалидный: пустой ответ, HTML-страница ошибки или `[]` не должны превращать все маршруты в устаревшие. Перенесено из `tunnel_manager`.

### 6.4. Применение маршрутов

`FR-040` (MUST). Через tunnel **MUST** идти только направления из whitelist и локальных пользовательских правил. Весь остальной трафик идет напрямую.

`FR-041` (MUST). Core передает helper полное желаемое состояние; helper **MUST** применять только разницу между зафиксированным и желаемым набором (diff внутри `applyConfiguration`, раздел 13.6). Route engine считает diff только для диагностики и тестов.

`FR-042` (MUST). При обновлении списка новые маршруты **MUST** добавляться до удаления устаревших, чтобы не возникало окна утечки.

`FR-043` (MUST). Клиент **MUST** удалять устаревшие маршруты после обновления списка.

`FR-044` (MUST). Helper **MUST** держать host-маршрут к адресу tunnel-точки через физический шлюз, чтобы не создать маршрутную петлю, даже если точка попадает в широкий префикс whitelist. Префикс из-за этого не отклоняется: более специфичный host-маршрут выигрывает.

`FR-045` (MUST). Клиент **MUST** отклонять маршруты, которые нарушают guardrails раздела 10.2 (слишком широкие префиксы, loopback, link-local, multicast и т. п.).

`FR-046` (SHOULD). Клиент **SHOULD** агрегировать соседние и вложенные префиксы, чтобы уменьшить размер таблицы маршрутов.

### 6.5. Watchdog и самовосстановление

`FR-050` (MUST). За drift следит helper, а не приложение: подписка на изменения таблицы маршрутов и интерфейсов средствами ОС плюс контрольная сверка по таймеру не реже раза в 60 секунд, сравнение с зафиксированным поколением конфигурации и повторное применение того же поколения. Приложение получает события (`HelperEvent`, раздел 13.2) и ведет только политику. Чистый опрос каждые 15-30 секунд без подписки на события недопустим из-за батареи (`NFR-027`). Helper продолжает следить, даже когда приложение закрыто.

`FR-051` (MUST). При обнаружении drift клиент **MUST** автоматически восстанавливать отсутствующие маршруты и удалять лишние защищенные маршруты, созданные приложением.

`FR-052` (MUST). Watchdog **MUST NOT** трогать маршруты, которые приложение не создавало.

`FR-053` (MUST). Клиент **MUST** корректно переживать sleep/wake, смену сети и reconnect tunnel-точки: после каждого такого события выполняется полная сверка состояния.

`FR-054` (MUST). Если ремонт drift не удался 3 раза подряд, клиент **MUST** перейти в `degraded` и отправить отчет администраторам.

`FR-055` (SHOULD). Клиент **SHOULD** запускаться после перезагрузки ОС, если пользователь включил autostart.

`FR-056` (MUST). Клиент **MUST** периодически проверять, что трафик к защищенным направлениям реально проходит через туннель, а не только что маршрут есть в таблице: раз в 15 минут выбираются до трех адресов из whitelist, к каждому делается TCP-проба через туннель. Ответ или RST считаются живым путем, только тишина - мертвым. Два подряд цикла без единого живого ответа **MUST** приводить к одному пересозданию туннеля (`applyConfiguration` с `rebuild: true`) с cooldown в 1 час, а не к циклу пересозданий. Это единственная защита от «тихой черной дыры», когда таблица маршрутов в порядке, а пакеты умирают. Если пересборка на том же транспорте не помогла, следующий шаг - переключение транспорта по политике `FR-260`, и только затем `health_rebuild_failed`. Перенесено из `tunnel_manager` (health probes).

`FR-057` (MUST). Пробы **MUST NOT** отправлять ничего, кроме TCP SYN на порт 443, и **MUST NOT** логировать адреса проб иначе как через `<ip>`.

### 6.6. Fail-closed

`FR-060` (MUST). Если tunnel недоступен, защищенные направления **MUST NOT** уходить через обычную сеть.

`FR-061` (MUST). Fail-closed **MUST** быть включен по умолчанию и настраиваться политикой.

`FR-062` (MUST). Fail-closed **MUST** активироваться до того, как маршруты будут сняты при падении tunnel, и деактивироваться только в трех случаях: явное отключение пользователем, отзыв доступа или истечение подписки, полученные от backend, и предохранитель helper по `FR-197`. Других путей снятия защиты нет: обновление списка, его отклонение, недоступность backend, истечение hardExpiry, смена транспорта и падение приложения защиту не снимают.

`FR-063` (MUST). Выключение fail-closed пользователем **MUST** требовать явного подтверждения с объяснением последствий.

Детали реализации - раздел 14.

### 6.7. Подписка и доступ

`FR-070` (MUST). Клиент **MUST** получать из backend состояние подписки и оставшееся время доступа.

`FR-071` (MUST). При истечении доступа клиент **MUST** отключиться и удалить защищенные маршруты.

`FR-072` (MUST). Клиент **MUST NOT** предоставлять доступ на основании локального времени: авторитет - только backend. Локальное время (с поправкой `serverTime`) может только запретить новое подключение офлайн, когда последний известный `expiresAt` уже прошел (раздел 11.7), но не продлить доступ и не разорвать работающее подключение. Локальный таймер используется для отображения оставшегося времени.

`FR-073` (MUST). Клиент **MUST** предупреждать пользователя об истечении подписки заранее: за 3 дня и за 1 день, с кнопкой «Продлить в боте» (deep link).

### 6.8. Версионирование и обновления

`FR-080` (MUST). Клиент **MUST** передавать свою версию в каждый запрос к backend и **MUST** учитывать `minSupportedVersion` из ответа.

`FR-081` (MUST). Если версия ниже минимальной, клиент **MUST** блокировать подключение и показывать экран обновления.

`FR-082` (MUST). Клиент **MUST** проверять наличие обновлений при старте и не реже раза в сутки и **MUST** уметь установить обновление с подтверждением пользователя. Это сетевой клиент с привилегированным компонентом: исправления безопасности должны доезжать без ручного скачивания. Механизм зафиксирован в OQ-6.

`FR-083` (MUST). Если версия ниже `minSupportedVersion`, экран обновления **MUST** предлагать установку через встроенный updater, а не только ссылку на скачивание.

`FR-084` (MUST). Модель обновлений - штатный updater Tauri v2, и она описывается точно, потому что подпись там относится к артефактам, а не к манифесту:

- артефакты обновления: macOS - `TunnelManagerClient.app.tar.gz` плюс отсоединенная подпись `.sig`; Windows - тот же подписанный установщик MSI или NSIS плюс `.sig`. DMG нужен только для первой установки на macOS, updater его не использует; релиз, у которого нет `app.tar.gz` с подписью, для macOS не обновляем (`NFR-041`);
- подпись артефактов - ключ updater (minisign-совместимый), отдельный от Apple Developer ID и Windows code signing; приватный ключ живет только в CI как секрет, публичный вшит в сборку. Артефакт с неверной подписью не устанавливается;
- манифест `latest.json` (`version`, `pub_date`, `notes`, `platforms.{macos-aarch64,windows-x86_64}.{url,signature}`) лежит на VPN-хосте по пути `https://<VPN_SERVER_HOST>/client/updates/latest.json` вместе с артефактами: приложение по-прежнему общается только с одним хостом (API_SPEC 1.1). Манифест сам не подписан и защищен только TLS; целостность обеспечивает подпись артефакта, а подмена манифеста может максимум предложить другой подписанный нами артефакт. Если потребуется подписывать и манифест, это отдельный механизм поверх штатного, сейчас не требуется;
- порядок обновления app и helper: новая версия приложения несет helper в своем bundle; при первом старте она сверяет версию протокола helper (`FR-183`) и при несовпадении обновляет helper с одним системным запросом прав (`FR-184`). Приложение версии N обязано работать с helper протокола N-1 в пределах одного минорного релиза, чтобы отказ обновления helper не оставил пользователя без подключения: в этом случае приложение работает на старом helper и показывает «обновите системный компонент». Обновление helper не снимает удержанную защиту: новый helper читает тот же журнал (13.6);
- прерванная установка: обновление ставится во временный путь и подменяет приложение атомарно; старая версия остается запускаемой до успешного первого старта новой. Проверяется в матрице `M15` и в Phase 5 (ROADMAP).

### 6.9. Фоновая работа

`FR-090` (MUST). Приложение **MUST** продолжать синхронизацию при закрытом окне, пока процесс жив; watchdog живет в helper и от окна и процесса приложения не зависит.

`FR-091` (MUST). Приложение **MUST** иметь индикатор состояния в меню-баре/трее с быстрым доступом к подключению и отключению.

`FR-092` (SHOULD). Приложение **SHOULD** уметь стартовать при входе пользователя в систему, если autostart включен.

### 6.10. Локальные правила пользователя (релиз 1.1)

Весь раздел относится к релизу 1.1 (см. 3.4). В 1.0 режим эксперта содержит только диагностику. Требования зафиксированы сейчас, чтобы хранилище и адаптер были спроектированы с учетом локальных правил.

`FR-100` (MUST, 1.1). В режиме эксперта пользователь **MUST** иметь возможность добавлять локальные правила whitelist.

`FR-101` (MUST). Локальные правила **MUST**:

- добавляться только локально на устройстве пользователя;
- не отправляться в серверную БД;
- не влиять на других пользователей;
- переживать перезапуск приложения;
- включаться, выключаться и удаляться пользователем;
- проходить валидацию перед применением.

`FR-102` (MUST). На первом этапе локальные правила **MUST** поддерживать минимум IPv4 CIDR и одиночные IPv4-адреса. Поддержка доменов и IPv6 проектируется отдельно, потому что домены требуют DNS-resolution и регулярного обновления IP.

`FR-103` (MUST). Локальные правила **MUST** проходить те же guardrails, что и серверный список (раздел 10.2), и **MUST** быть визуально отличимы в диагностике от серверных маршрутов.

`FR-104` (MUST). Локальные правила **MUST** сниматься при отключении и при удалении приложения так же, как серверные.

`FR-105` (MAY). Клиент **MAY** позволять экспорт и импорт локальных правил файлом для переноса между устройствами пользователя.

### 6.11. Ошибки и уведомления администраторам

Ошибки подключения должны быть сделаны лучше, чем сценарий "напишите в поддержку с номером ошибки". Приложение само помогает администраторам увидеть проблему.

`FR-110` (MUST). Клиент **MUST** автоматически отправлять администраторам важные ошибки, которые мешают подключиться или пользоваться tunnel. Отправка идет через backend API, а backend уже отправляет сообщение администраторам в Telegram.

`FR-111` (MUST). Автоматически отправляются только actionable ошибки, например:

- не удалось создать или запустить tunnel-интерфейс;
- не удалось применить маршруты;
- не удалось включить fail-closed;
- tunnel endpoint недоступен при попытке подключения;
- обнаружено переиспользование refresh token, то есть возможная компрометация устройства;
- privileged helper не установлен, поврежден или не отвечает;
- ОС вернула ошибку прав или политик, из-за которой подключение невозможно.

`FR-112` (MUST). Не отправляются автоматически шумные события:

- пользователь сам нажал "Отключить";
- пользователь отменил системный prompt;
- временный сбой сети, восстановленный retry-механизмом;
- успешная синхронизация;
- обычные информационные события;
- истечение подписки и отзыв устройства администратором: это штатные события, они и так видны в боте;
- повтор той же ошибки чаще заданного rate limit.

`FR-113` (MUST). Каждый отправляемый отчет **MUST** содержать: error category, стабильный fingerprint для дедупликации, severity, платформу и версию ОС, версию приложения, stage сбоя, redacted diagnostics, внутренний id или hash пользователя/устройства, timestamp.

`FR-114` (MUST). В error report **MUST NOT** попадать: private keys, пароли, access/refresh tokens, полные tunnel credentials, содержимое трафика, история браузинга, произвольные пользовательские файлы, raw config без redaction.

`FR-115` (MUST). Если ошибка не ушла автоматически или пользователь хочет отправить ее вручную, на экране ошибки **MUST** быть кнопка "Отправить ошибку", отправляющая тот же redacted отчет одним нажатием.

`FR-116` (MUST). Backend **MUST** дедуплицировать и rate-limit уведомления, чтобы админский Telegram не засыпало одинаковыми сообщениями.

`FR-117` (MUST). В Telegram приходит короткое сообщение: пользователь/устройство, платформа, версия приложения, категория ошибки, stage, fingerprint и подсказка, где смотреть детали.

Полные правила - [ERROR_CATALOG.md](ERROR_CATALOG.md).

### 6.12. Диагностика

`FR-120` (MUST). Обычному пользователю показывается только понятный итог: подключено, подключается, не подключено, ошибка подключения.

`FR-121` (MUST). Подробная диагностика доступна только в режиме эксперта: статус подключения, текущий tunnel-интерфейс, количество маршрутов, последняя ошибка синхронизации, доступность backend, доступность tunnel endpoint.

`FR-122` (MUST, 1.1). Клиент **MUST** уметь экспортировать diagnostic bundle с логами и redacted config. Экспорт **MUST** скрывать секреты.

`FR-123` (MUST, 1.1). Перед сохранением bundle пользователю **MUST** показываться, что именно попадет в файл.

В 1.0 вместо экспорта bundle достаточно кнопки "Отправить ошибку" (`FR-115`) и локальных redacted логов, которые пользователь может найти по подсказке в режиме эксперта.

### 6.13. Транспорты: WireGuard и IKEv2

Сервер терминирует оба транспорта, и клиент **MUST** уметь оба ([ADR-005](decisions/ADR-005-dual-transport.md)). WireGuard основной; IKEv2 нужен там, где UDP WireGuard не проходит, и как путь, которым сегодняшние пользователи уже ходят.

`FR-260` (MUST). Порядок транспортов приходит из backend в `policy.transports`, по умолчанию `["wireguard", "ikev2"]`. Клиент пробует первый; если туннель не поднялся за `transportTimeoutSec` (по умолчанию 15 секунд), переходит к следующему. Fail-closed активен на протяжении всего переключения.

`FR-261` (MUST). Клиент **MUST** запоминать последний успешный транспорт для текущей сети (по хешу шлюза по умолчанию, не по SSID) и начинать с него при следующем подключении в этой сети.

`FR-262` (MUST). В режиме эксперта - переключатель «Авто / Только WireGuard / Только IKEv2» и индикация текущего транспорта. Обычный пользователь транспорт не видит.

`FR-263` (MUST). Учетные данные IKEv2, EAP-идентификатор и пароль, выдаются per device при активации, приходят в `GET /client/v1/endpoint` до подтверждения сохранения `ikev2-ack` и ротируются по `rotate-ikev2` (`API-058`, `API-058a`), хранятся только в OS keystore и отзываются вместе с устройством. Отправленный ответ backend подтверждением сохранения не считается: потеря ответа и ошибка keystore лечатся повторным запросом endpoint. Сервер применяет их той же логикой, что сегодня бот: запись в `ipsec.secrets`, `ipsec rereadsecrets`, `ipsec down` при отзыве.

`FR-264` (MUST). Оба транспорта получают один и тот же набор маршрутов и одни и те же правила fail-closed. Смена транспорта - один `applyConfiguration` с новым `transport`: helper расширяет блокировку, поднимает B, переносит маршруты, снимает A, сужает блокировку (раздел 13.6).

`FR-265` (MUST). На IKEv2 ОС ставит маршрут по умолчанию в туннель; helper **MUST** снимать catch-all и удерживать его снятым, как `tunnel_manager` (приложение B), а watchdog **MUST** считать вернувшийся catch-all drift.

`FR-266` (SHOULD). Сертификат IKEv2-сервера **SHOULD** быть публично доверенным, чтобы клиент не устанавливал CA в системное хранилище. Если CA собственный, установку делает helper с явным согласием пользователя. Решение - OQ-10.

`FR-267` (MUST). Переход на другой транспорт - событие `transport_fallback` в диагностике. Если IKEv2 сработал там, где WireGuard не смог, это не ошибка и админам не отправляется, но копится в счетчиках `POST /client/v1/diagnostics`, чтобы админ видел сети, где WireGuard блокируют.

### 6.14. Пробный период

`FR-270` (MUST). На экране активации есть кнопка «Начать пробный период». Она запускает сценарий deep link с `intent=trial`; пробную подписку создает бот по своей существующей логике онбординга, включая одобрение админом, если оно включено.

`FR-271` (MUST). Продолжительность пробного периода `trialDays` хранится в настройках `client-api` и меняется из админ-панели (6.15). Бот читает ее через admin API и использует для всех пробных подписок; при недоступности `client-api` берет значение из своего `.env`.

`FR-272` (MUST). Один Telegram-аккаунт - один пробный период; повторную попытку бот отклоняет по существующей проверке, приложение показывает «пробный период уже использован, продлите доступ в боте».

`FR-273` (MUST). На главном экране в пробном периоде показывается «Пробный период до <дата>», предупреждения по `FR-073`, после истечения - `access_expired` с подсказкой продлить в боте.

### 6.15. Админ-панель в приложении

Администратор входит в приложение так же, как все, через бота. Если его Telegram-аккаунт есть в списке администраторов бота (`telegram_bot_admins`), бот при подтверждении входа передает роль `admin`, и приложение показывает раздел «Администрирование».

Состав по релизам: в 1.0 разделы «Настройки» и «Пользователи» (`FR-281`, `FR-282`); «Список маршрутов», «Отчеты об ошибках» и «Состояние» - в 1.1 (`FR-283`, `FR-284`). Так первый релиз не растет за счет того, что уже есть в веб-админке и боте.

`FR-280` (MUST). Роль приходит в токенах и в `GET /client/v1/profile`; раздел и все admin-вызовы недоступны без роли. Роль проверяется на сервере при каждом запросе, а не только на клиенте. Источник роли - список администраторов бота; бот пушит ее в запись пользователя `client-api` при подтверждении входа и при каждом изменении списка, и снятие доезжает до всех устройств пользователя не позже 15 минут (`API-138`). Приложение под ролью `admin` не может менять роль: набор методов приложения и сервисного токена задан матрицей `API-137`, актор аудита берется из токена, а не из тела запроса.

`FR-281` (MUST). Раздел «Настройки»: все поля `policy` (интервалы, fail-closed по умолчанию и право пользователя его выключать, лимит устройств, grace и hardExpiry, maxRoutes, лимиты отчетов), `trialDays`, `minSupportedVersion`, порядок транспортов. Изменение сохраняется через `PUT /admin/v1/settings` и действует у клиентов при следующем `profile`, не позже часа; панель это показывает.

`FR-282` (MUST). Раздел «Пользователи»: список с поиском, статус подписки, устройства; действия: продлить (+7, +30, бессрочно), включить, отключить, отозвать устройство, выдать код активации. Это те же операции, что в карточке пользователя бота, через тот же admin API.

`FR-283` (MUST, 1.1). Раздел «Список маршрутов»: группы и записи, добавление и удаление IP или CIDR с теми же guardrails, что `/addip` бота, кнопка «применить сейчас». Запись идет в таблицы дашборда через `client-api` с отдельным токеном на запись (`API-114`). Панель **MUST** показывать, что список общий и правка действует на всех пользователей, включая приватный контур (раздел 1.3).

`FR-284` (MUST, 1.1). Раздел «Отчеты об ошибках»: список с фильтром по категории, устройству и fingerprint, отметка «решено». Раздел «Состояние»: peer онлайн по транспортам, возраст копий списка и статусов, распределение версий приложения. До 1.1 то же доступно через команды бота `/report` и `/clientstatus` (`API-005`).

`FR-285` (MUST). Каждое действие в админ-панели пишется в аудит `client-api` с Telegram ID администратора, действием и целью, как `AUDIT`-строки бота. Разрушительные действия (отзыв, отключение, изменение `minSupportedVersion`, удаление записи списка) требуют подтверждения в приложении.

`FR-286` (SHOULD). Для `minSupportedVersion` и массовых операций **SHOULD** требоваться второе подтверждение в боте: `client-api` шлет администратору сообщение с кнопкой, действие применяется после нажатия. Защита от админского ноутбука в чужих руках.

`FR-287` (MUST). Админ-панель - тот же UI на TypeScript, без отдельной сборки; в обычной и экспертной части приложения она не появляется ни одним элементом.

## 7. Пользовательский интерфейс

### 7.1. Принципы

`UX-001` (MUST). Главный экран показывает только то, что помогает пользователю принять решение. Время последней синхронизации, количество маршрутов, tunnel-интерфейс, route drift, hash whitelist и похожая диагностика **MUST** быть доступны только в режиме эксперта.

`UX-002` (MUST). Любое состояние ошибки **MUST** содержать: что случилось человеческим языком, что делать пользователю, и кнопку действия (повторить / отправить ошибку / обновить приложение).

`UX-003` (MUST). Приложение **MUST NOT** показывать пользователю технические коды как основной текст ошибки. Код и fingerprint показываются мелким шрифтом как вспомогательная информация.

### 7.2. Информационная архитектура

```text
Активация
  └─ Главный экран
       ├─ Экран ошибки (модально или врезкой)
       ├─ Настройки
       │    ├─ Общие (автозапуск, автоподключение, язык)
       │    ├─ Безопасность (fail-closed)
       │    ├─ Аккаунт (подписка, устройство, выход)
       │    └─ Режим эксперта (переключатель)
       ├─ Режим эксперта (появляется только если включен)
       │    ├─ Диагностика и выбор транспорта
       │    ├─ Локальные правила whitelist (1.1)
       │    └─ Экспорт диагностики (1.1)
       └─ Администрирование (только роль admin)
            ├─ Настройки
            ├─ Пользователи
            ├─ Список маршрутов
```

Ключевое свойство: backend не участвует в передаче пользовательского трафика. Если backend недоступен, tunnel продолжает работать на кешированной конфигурации.

Если на macOS придется перейти на NetworkExtension, появится Swift-компонент, и это изменит схему; поэтому решение принимается по итогам walking skeleton в фазе 1.

`client-api` живет в отдельном репозитории `tunnel-client-api` (FastAPI, Postgres, тот же стек, что дашборд): он деплоится на другой хост и по другому циклу. Контракт между репозиториями - API_SPEC; JSON-схемы и фикстуры (`API-092`) публикуются из него и используются mock-backend клиента.

### 8.3. Процессная модель

| Процесс | Права | Ответственность |
| --- | --- | --- |
| UI process | пользовательские | отрисовка, ввод, чтение status model |
| Core (в процессе приложения) | пользовательские | вся логика, сеть, кеш, планировщики |
| Native adapter (Rust в Tauri) | пользовательские | вызов helper, чтение состояния сети |
| Privileged helper | повышенные | драйверы WireGuard и IKEv2, маршруты, firewall, DNS, журнал применения, watchdog drift, предохранитель |

`SEC-002` (MUST). Helper **MUST** выполнять только фиксированный набор команд с типизированными аргументами. Приём произвольных команд, shell-строк и путей запрещен.

### 8.4. Ключевые потоки

Подключение:

```text
UI: connect
core: проверка токена, подписки, версии, helper; GET /client/v1/routes (или кеш)
route-engine: validate -> normalize -> aggregate -> desired
core: транспорт = запомненный для этой сети, иначе первый из policy.transports
core -> helper: applyConfiguration({generation, transport, routes, failClosed: true, dnsResolver})
helper: расширить блокировку -> журнал begin -> поднять транспорт, ждать handshake до transportTimeoutSec
        -> AllowedIPs или снятие catch-all -> добавить маршруты -> снять лишние -> DNS
        -> журнал commit -> сузить блокировку                                (раздел 13.6)
  rolled_back с кодом transport_unreachable -> защита удержана, core берет следующий транспорт, событие transport_fallback
  транспорты кончились -> state = error (защита активна), all_transports_failed
core: state = connected; дальше helper сам следит за drift и шлет события
```

Периодическая синхронизация:

```text
scheduler tick (5-10 мин ± jitter)
api-client: GET /client/v1/routes с If-None-Match
  304 -> обновить timestamp, выход
  200 -> проверить hash/подпись/версию -> сохранить кеш
route-engine: desired отличается от applied?
native: applyConfiguration(desired) - diff и порядок считает helper (раздел 13.6)
```

Ремонт drift:

```text
helper: событие ОС об изменении маршрутов/интерфейсов или контрольный tick (60 c)
helper: сравнить таблицу ОС и правила с зафиксированным поколением
drift -> повторно применить то же поколение -> событие driftRepaired в приложение
ремонт не удался -> событие driftRepairFailed; core после 3 подряд -> degraded + error report
приложение закрыто -> helper делает то же самое, события копятся до следующего старта
```

## 9. Модель состояний

### 9.1. Состояния

| Состояние | Значение |
| --- | --- |
| `unactivated` | устройство не активировано |
| `activating` | идет активация |
| `disconnected` | активировано, tunnel выключен |
| `connecting` | идет подключение: перебор транспортов по политике, затем применение конфигурации |
| `connected` | tunnel поднят, маршруты применены, fail-closed активен |
| `degraded` | tunnel работает, но конфигурация устарела или drift не чинится |
| `reconnecting` | tunnel упал, идет автоматическое восстановление |
| `disconnecting` | идет снятие конфигурации и остановка tunnel |
| `error` | подключение невозможно, нужна реакция |
| `access_expired` | подписка истекла или устройство отозвано |
| `update_required` | версия ниже минимальной |

### 9.2. Таблица переходов

| Из | Событие | В | Побочные действия |
| --- | --- | --- | --- |
| `unactivated` | пользователь начал вход | `activating` | код связки, ожидание подтверждения в боте |
| `activating` | бот подтвердил, токены получены | `disconnected` | сохранить токены, загрузить профиль |
| `activating` | подтверждение не пришло за 10 минут или бот отказал | `unactivated` | понятное сообщение, новый код по кнопке |
| старт приложения | helper держит поколение с fail-closed без туннеля | `error`, при автоподключении `reconnecting` | `FR-196` |
| старт приложения | `committed` жив и совпадает с желаемой конфигурацией | `connected` после сверки | `FR-133`, офлайн-профиль 11.7 |
| старт приложения | `committed` - `disabled` или отсутствует | `disconnected` | - |
| `disconnected` | пользователь нажал "Подключить" | `connecting` | предполетные проверки |
| `connecting` | `applyConfiguration` вернул `applied` для полной желаемой конфигурации | `connected` | событие `connect_ok`; вход в `connected` только после подтвержденной полной конфигурации |
| `connecting` | транспорт не поднялся за `transportTimeoutSec` | `connecting` | следующий транспорт по политике, событие `transport_fallback`; транспорты кончились - `error` |
| `connecting` | ошибка любого обязательного шага | `error` | откат, error report |
| `connecting` | пользователь отменил | `disconnecting` | откат без error report |
| `connected` | tunnel упал | `reconnecting` | fail-closed остается включенным, системный DNS возвращен (`FR-167b`) |
| `degraded` | tunnel упал | `reconnecting` | как из `connected` |
| `connected` | sync не удается дольше grace | `degraded` | причина `sync_stale`, предупреждение в UI |
| `connected` | ремонт drift не удался 3 раза (`FR-054`) | `degraded` | причина `drift_unrepaired`, error report |
| `connected` | пересборка по health probes не помогла (`FR-056`) | `degraded` | причина `health_failed`, error report |
| `connected`, `degraded` | пользователь нажал "Отключить" | `disconnecting` | снять конфигурацию, `reason: "user"` |
| `degraded` | причина снята: успешный sync снимает `sync_stale`, успешная сверка `driftRepaired` - `drift_unrepaired`, живая проба - `health_failed` | `connected`, если причин не осталось | причины хранятся множеством; успешный sync при неустраненном drift оставляет `degraded` |
| `reconnecting` | `applyConfiguration` с `rebuild: true` вернул `applied` | `connected` | вход только после полной конфигурации; `applied` с неудавшимися маршрутами - `degraded` с `drift_unrepaired` |
| `reconnecting` | исчерпан лимит попыток | `error` | error report |
| `error` | пользователь нажал "Повторить" | `connecting` | сброс backoff |
| `access_expired` | подписка продлена | `disconnected` | обновить профиль |
| `disconnecting` | конфигурация снята | `disconnected` | - |
| `update_required` | обновление установлено | `disconnected` | перезапуск приложения |
| `connecting`, `connected`, `degraded`, `reconnecting` | подписка истекла или устройство приостановлено (от backend) | `disconnecting` -> `access_expired` | `applyConfiguration` с `transport: null, failClosed: false, reason: "subscription_expired"`; сообщение после снятия |
| `disconnected`, `error` | подписка истекла (от backend) | `access_expired` | если helper держит защиту (`FR-196`) - сначала снять ее тем же путем |
| `connecting`, `connected`, `degraded`, `reconnecting` | токен или устройство отозваны | `disconnecting` -> `unactivated` | `reason: "access_revoked"`, затем полная очистка секретов и кеша маршрутов |
| остальные | токен или устройство отозваны | `unactivated` | снять удержанную защиту, если есть; полная очистка секретов и кеша |
| `connecting`, `connected`, `degraded`, `reconnecting` | версия ниже минимальной | `disconnecting` -> `update_required` | `reason: "update_required"`: работающее соединение завершается, потому что `FR-131` запрещает маршруты в `update_required`; пользователь видит объяснение |
| остальные | версия ниже минимальной | `update_required` | блокировать подключение; удержанную защиту снять тем же путем |

### 9.3. Инварианты

`FR-130` (MUST). В состояниях `connected`, `degraded` и `reconnecting` fail-closed **MUST** быть активен, если политика fail-closed включена.

`FR-131` (MUST). В состояниях `disconnected`, `unactivated`, `access_expired` и `update_required` защищенных маршрутов приложения в системе **MUST NOT** оставаться.

`FR-132` (MUST). Переходы **MUST** быть сериализованы: одновременно выполняется не более одной операции изменения сетевого состояния. Конкурентные запросы ставятся в очередь. Потеря доступа (`access_expired`, отзыв) и `update_required` - общие переходы из всех сетевых состояний через `disconnecting`, а не только из `connected`.

`FR-134` (MUST). Причины `degraded` (`sync_stale`, `drift_unrepaired`, `health_failed`) хранятся раздельно; каждая снимается только своим восстановлением, и `connected` наступает, когда множество причин пусто. Вход в `connected` из любого состояния разрешен только после `applied` от helper для полной желаемой конфигурации.

`FR-133` (MUST). При старте приложение **MUST** сверить свое состояние с `getAppliedConfiguration()` helper: источник правды о примененной конфигурации - helper и его журнал, а не `state.json` приложения.

## 10. Route Engine

### 10.1. Нормализация

`FR-140` (MUST). Входная запись маршрута нормализуется по правилам:

1. обрезка пробелов, приведение к нижнему регистру;
2. одиночный IPv4 превращается в `/32`, одиночный IPv6 - в `/128`;
3. проверка синтаксиса адреса и длины префикса;
4. обнуление host-битов: `10.1.2.3/24` -> `10.1.2.0/24`;
5. дедупликация после нормализации.

### 10.2. Валидация и guardrails

`FR-141` (MUST). Запись отклоняется, если она:

- синтаксически невалидна;
- имеет длину префикса вне допустимого диапазона: минимум из `policy.minPrefixLength`, по умолчанию `/8` для IPv4 и `/16` для IPv6, те же границы, что у `validate_routable_cidr` бота и `API-133`, чтобы клиент никогда не отклонял запись, которую список может содержать; максимум `/32` и `/128`;
- равна `0.0.0.0/0` или `::/0` (полный перехват трафика не поддерживается в split-режиме);
- попадает в loopback (`127.0.0.0/8`, `::1/128`);
- попадает в link-local (`169.254.0.0/16`, `fe80::/10`);
- попадает в multicast (`224.0.0.0/4`, `ff00::/8`);
- равна `/32` адреса tunnel-точки или резолвера точки (широкий префикс, который их содержит, допустим: `FR-044`);
- пересекается с адресом активного шлюза по умолчанию.

`FR-142` (MUST). Приватные диапазоны (`10/8`, `172.16/12`, `192.168/16`, `fc00::/7`) отклоняются всегда, чтобы не ломать локальную сеть пользователя; исключений в 1.0 нет, флаг разрешения в API отсутствует и появится только вместе с решением в decision record. Адреса самого туннеля (`assignedAddresses`, `dnsResolver`) под это правило не попадают: это не маршруты whitelist, а on-link адреса tunnel-интерфейса.

`FR-143` (MUST). Общее число применяемых маршрутов ограничено (по умолчанию 10 000). Список, превышающий лимит после всех преобразований конвейера 10.7 (вычитание blocklist, исключения, агрегация), **MUST** отклоняться целиком, как невалидный (`FR-034`): клиент остается на предыдущей валидной конфигурации, факт превышения уходит в диагностику и отчет админам (`route_limit_exceeded`). Усечение недопустимо: отброшенные адреса ушли бы напрямую без защиты, а fail-closed о них не знал бы.

`FR-144` (MUST). Результат валидации **MUST** содержать список отклоненных записей с причиной; этот список попадает в диагностику и в `POST /client/v1/diagnostics`.

### 10.3. Агрегация

`FR-145` (SHOULD). Перед применением набор префиксов агрегируется: вложенные префиксы поглощаются родительскими, соседние объединяются в один при совпадении границ. Агрегация **MUST NOT** расширять покрытие за пределы исходного набора.

### 10.4. Diff и порядок применения

```ts
type RouteDiff = {
  toAdd: string[];
  toRemove: string[];
  unchanged: string[];
};
```

`FR-146` (MUST). Применение выполняется одной операцией helper `applyConfiguration(desired)` с порядком шагов, откатом и восстановлением по разделу 13.6. Core не вызывает шаги по отдельности и не знает, в каком порядке helper их выполняет.

`FR-147` (MUST). Применение **MUST** быть идемпотентным: повторный вызов с тем же набором не меняет систему и не считается ошибкой.

`FR-148` (MUST). Маршруты применяются пачками (по умолчанию 256 записей на вызов), чтобы не блокировать helper надолго и давать прогресс в UI.

`FR-149` (MUST). Частичная неудача **MUST** возвращать в core список неудавшихся записей, а не общий флаг ошибки.

### 10.5. Псевдокод цикла применения

```text
routes = pipeline(routesResponse, enabledLocalRules, endpoint, networkSnapshot)   // 10.7
if routes == rejected: остаться на предыдущем списке, error report (FR-143, FR-034)
state = helper.getAppliedConfiguration()
desired = {transport, routes, failClosed, dnsResolver, policy, rebuild}
if state.committed != null
   and sameConfig(state.committed, desired)        // транспорт, routes, failClosed, dnsResolver
   and state.tunnelUp and not desired.rebuild:
     helper.applyConfiguration({generation: state.committed.generation, ...desired})  // сверка, не новое поколение
     выход
result = helper.applyConfiguration({generation: state.lastGeneration + 1, ...desired})
  // внутри helper: intent, расширение блокировки, begin, транспорт, diff, пачки, DNS, commit, сужение (13.6)
if result.status == "in_progress": result = poll helper.getApplyStatus(generation)
if result.status != "applied": остаемся на предыдущей конфигурации, решение по коду (13.6), error report
helper сам сверяет committed с таблицей ОС и чинит drift той же операцией (FR-186)
```

Сравнение делается по полной конфигурации и фактическому состоянию, а не по набору маршрутов: смена DNS-режима или транспорта при том же списке - новое поколение, а совпадающая конфигурация при `tunnelUp: false` - пересборка (`FR-024`, R04 проверки документации).

### 10.6. Список маршрутов, домены и DNS

Whitelist - вручную курируемые IP и CIDR по сервисам из дашборда (таблицы `groups` и `ips`). Так это работает сегодня, и клиент этого не меняет ([ADR-003](decisions/ADR-003-domain-resolution.md)): резолва доменов нет ни на сервере, ни на клиенте, доменные списки отложены владельцем (пункт W5 в HANDOFF серверного репозитория).

`FR-165` (MUST). `GET /client/v1/routes` **MUST** отдавать ту же таблицу, что `GET /api/routes` для приватного контура, в JSON-проекции: `services` = группы дашборда. Один источник правды, два представления.

`FR-166` (MUST). Route list **MUST** оставаться в пределах `NFR-025`: агрегация на backend той же логикой `collapse_addresses`, что в `tunnel_manager`; список сверх `maxRoutes` клиент отклоняет целиком по `FR-143`.

Почему DNS входит в 1.0. Если системный резолвер отдает для сервиса адрес вне whitelist, трафик уходит напрямую, сервис не работает при статусе «Подключено», а fail-closed не срабатывает, потому что адрес не защищен. У сегодняшних пользователей этой проблемы нет: IKEv2-сервер пушит DNS, а WireGuard-конфиг бота содержит адрес dnsmasq на tunnel-стороне, так что DNS у них всегда идет через туннель. Клиент со split routing без DNS через туннель был бы регрессом ровно на подменяемых доменах, поэтому это требование 1.0.

`FR-167` (MUST). Клиент **MUST** направлять DNS через резолвер на tunnel-точке на время подключения: адрес приходит в `GET /client/v1/endpoint` (`dnsResolver`); на WireGuard клиент добавляет его в `AllowedIPs`, на IKEv2 сервер пушит его сам. Helper выставляет системный DNS при подключении и восстанавливает прежний при отключении и при падении приложения (тем же предохранителем, что `FR-197`). Доменный список не нужен. В режиме эксперта - переключатель «оставить системный DNS», по умолчанию выключен. Механизм - OQ-8.

`FR-167a` (MUST). Резолвер tunnel-точки **MUST** быть доступен только через туннель, иначе fail-closed на него не распространяется; helper **MUST** блокировать DNS-запросы к нему на физических интерфейсах теми же правилами, что protected destinations.

`FR-167b` (MUST). Подмена системного DNS действует только пока туннель поднят. При потере туннеля helper **MUST** вернуть системный DNS не позже 5 секунд после ее обнаружения по `FR-187` (само обнаружение молчаливой потери занимает до 45 секунд), иначе у пользователя перестанет работать весь интернет, а не только защищенные сервисы; при восстановлении туннеля - снова выставить резолвер точки. Защищенные адреса в это время остаются заблокированы (`FR-190`). Это осознанный компромисс: DNS - не protected destination, обещание fail-closed относится к адресам из списка.

`FR-168` (MUST). Режим эксперта **MUST** отвечать на вопрос «почему X (не) идет через туннель»: пользователь вводит IP или домен, клиент резолвит, делает longest-prefix match по whitelist с указанием сервиса и записи и сверяет с живой таблицей маршрутов. Аналог `tunnel-manager --why`.

`FR-169` (MUST). Режим эксперта **MUST** уметь проверить, куда трафик уходит на самом деле: сравнить выбор маршрута ОС для цели с контрольным незащищенным адресом и сделать живую TCP-пробу. Различает «в списке, но утекает», «маршрут есть, трафик умирает» и «заблокировано fail-closed». Аналог `tunnel-manager --test`.

### 10.7. Конвейер: от ответа API до маршрутов, AllowedIPs и защиты

Единственное нормативное описание того, как из `GET /client/v1/routes` получаются три множества: `routes` (что ставится в таблицу маршрутов), `AllowedIPs` (WireGuard) и `protected(G)` (что блокируется на физических интерфейсах). Core, helper и backend используют одни fixture-векторы (`API-092`): для каждого вектора зафиксированы вход и все три результата.

```text
1. input      = ∪ services[].ipv4 ∪ services[].ipv6 ∪ enabledLocalRules (1.1; в 1.0 пусто)
2. normalized = normalize(input)                                  // FR-140; невалидные -> validation error, FR-033
3. valid      = guardrails(normalized, policy.minPrefixLength)    // FR-141, FR-142
4. minusBlock = subtractCidr(valid, guardrails(normalize(emergencyBlocklist)))   // API-041
5. minusLocal = subtractCidr(minusBlock, {endpointIp/32, endpointIp/128, defaultGateway/32})  // API-051, FR-141
6. routes     = aggregate(minusLocal)                             // FR-145
7. if |routes| > policy.maxRoutes: список отклонен целиком (FR-143), остаемся на предыдущем
```

Дальше для поколения G:

```text
resolverPrefix = dnsResolver ? (isIPv6 ? dnsResolver/128 : dnsResolver/32) : ∅   // только в режиме DNS через туннель
protected(G)   = failClosed ? routes ∪ resolverPrefix : ∅
AllowedIPs(G)  = routes ∪ resolverPrefix ∪ assignedAddresses      // WireGuard; IKEv2 - маршруты на iface(G), FR-265
```

Правила, которые из этого следуют:

- `subtractCidr` - вычитание по CIDR: пересекающийся префикс заменяется набором префиксов той же области без исключенной части; `/32` внутри `/24` дает до 16 префиксов. Исключенная часть уходит напрямую и не защищается; в диагностике она видна как «исключено blocklist» в ответе «почему X не идет через туннель» (`FR-168`);
- `dnsResolver` отсутствует или включен режим «системный DNS» - `resolverPrefix = ∅`, резолвер не маршрутизируется и не блокируется; IPv6-резолвер дает `/128`;
- `assignedAddresses` входят только в `AllowedIPs`, не в `routes` и не в `protected(G)` (`FR-142`);
- host-маршрут к `endpointIp` через физический шлюз ставит helper (`FR-044`), в `routes` его нет;
- обязательные fixture-векторы: IPv6 `/24` (отклоняется по `minPrefixLength`), приватный диапазон, вложенное исключение `/32` в `/24`, `dnsResolver` вне whitelist, IPv6-резолвер, отсутствие `dnsResolver`, список, который превышает `maxRoutes` только после вычитания.

## 11. Синхронизация и кеш

### 11.1. Расписание

`FR-150` (MUST). Базовый интервал синхронизации - 5-10 минут. Конкретное значение приходит из backend (`syncIntervalSec`), по умолчанию 420 секунд.

`FR-151` (MUST). К интервалу применяется случайный jitter ±20%, чтобы устройства не били в backend одновременно.

`FR-152` (MUST). Внеочередная синхронизация запускается при: подключении, пробуждении из сна, смене сети, ручной кнопке в режиме эксперта, возврате приложения из фона.

### 11.2. Условные запросы

`FR-153` (MUST). Клиент хранит `ETag` последнего успешного ответа и присылает `If-None-Match`. Ответ `304` обновляет только `fetchedAt`.

`FR-153a` (MUST). Клиент различает два возраста: `fetchedAt` - последнее успешное общение с `client-api` (`200` или `304`), и `sourceCheckedAt` - когда `client-api` в последний раз успешно сверил свою копию с RU (`API-034`; при `304` берется из заголовка `X-Source-Checked-At`). Политика 11.5 считается по `fetchedAt`: недоступность RU не должна переводить устройства в `degraded`, потому что список у них актуален настолько, насколько он есть у control plane. `sourceCheckedAt` старше 24 часов - предупреждение `upstream_stale` в режиме эксперта и в диагностике, чтобы «устройство актуально» не скрывало давно несвежий источник; администратор видит возраст копий в `/clientstatus`.

`FR-153b` (MUST). Метрика доставки (2.3) измеряется без событий: клиент присылает `X-Route-List-Version` в каждом запросе `routes` и `profile`, `client-api` хранит `updated_at` строки списка из ответа дашборда и момент, когда версия впервые пришла от устройства; p95 считается по устройствам, у которых был хотя бы один запрос за интервал. Отзыв и отключение измеряются от получения события `client-api` (`API-120a`).

### 11.3. Проверка целостности

`FR-154` (MUST). Клиент **MUST** проверять `contentHash` полученного списка по каноническому envelope `API-040`: он покрывает `version`, `groupId`, `generatedAt`, `ttlSec`, `resetVersion`, записи `services` и `emergencyBlocklist`, так что подпись 1.1 удостоверяет и метаданные anti-rollback, а не только набор префиксов.

`FR-155` (MUST, 1.1). Backend **MUST** подписывать route list detached-подписью Ed25519, клиент **MUST** проверять подпись по публичному ключу, вшитому в сборку, с поддержкой `keyId` для ротации ключей. В 1.0 целостность обеспечивают TLS и `contentHash`; поле `signature` в ответе уже есть, клиент 1.0 его игнорирует.

### 11.4. Anti-rollback

`FR-156` (MUST). Клиент хранит максимальную применённую `version` и отклоняет ответы с меньшей версией, кроме случая, когда backend прислал `resetVersion: true`. В 1.0 сброс принимается под защитой TLS и `contentHash`, как и весь список, и пишется в диагностику как `route_version_reset`; с 1.1 - только с валидной подписью envelope (`API-041a`). Replay старого подписанного envelope с `resetVersion: true` отклоняется по `generatedAt`: он не может быть старше `generatedAt` текущего кеша.

### 11.5. TTL, grace и деградация

| Возраст кеша | Поведение |
| --- | --- |
| < TTL | нормальная работа |
| TTL .. TTL + grace (по умолчанию grace = 3 x TTL) | продолжаем работать на кеше, в режиме эксперта показывается предупреждение |
| > TTL + grace | состояние `degraded`, предупреждение обычному пользователю |
| > hardExpiry (по умолчанию 30 суток) | работающее подключение не трогаем: остаемся в `degraded` на кеше; новое подключение блокируется до успешной синхронизации с сообщением `cache_hard_expired` |

`FR-157` (MUST). Политика stale-кеша **MUST** быть настраиваемой из backend в пределах разумных границ и иметь безопасные значения по умолчанию. `hardExpirySec` не может быть меньше 7 суток.

`FR-162` (MUST). Истечение hardExpiry **MUST NOT** снимать маршруты или fail-closed у работающего подключения. Backend не участвует в data plane, и его недоступность не должна ломать туннель, который работает. Единственный способ лишить работающее устройство доступа - явный отзыв или истечение подписки, полученные от backend.

### 11.6. Retry и backoff

`FR-158` (MUST). Ошибки сети и `5xx` ретраятся с экспоненциальным backoff: 5 c, 10 c, 30 c, 60 c, 300 c (потолок), с jitter ±20%. Успех сбрасывает счетчик.

`FR-159` (MUST). Ошибки `4xx`, кроме `401` и `429`, не ретраятся автоматически: они означают проблему конфигурации или доступа.

`FR-160` (MUST). Ответ `429` **MUST** уважать заголовок `Retry-After`.

### 11.7. Старт офлайн и офлайн-профиль подключения

Два разных случая: нет сети вообще, и control plane недоступен, а tunnel endpoint достижим. Первый случай тривиален: подключение невозможно физически. Второй - штатный режим, ради которого backend вынесен из data plane, и для него нужен полный сохраненный профиль, а не один whitelist.

`FR-161` (MUST). Офлайн-профиль подключения - все, что нужно для `applyConfiguration` без backend, и он сохраняется при каждом успешном ответе соответствующего endpoint:

| Данные | Источник | Где хранится | Срок действия офлайн |
| --- | --- | --- | --- |
| whitelist, `version`, `contentHash`, `etag`, `fetchedAt` | `GET /client/v1/routes` | `whitelist.json` | политика 11.5: подключение разрешено до `hardExpiry` |
| статус подписки, `expiresAt`, `role`, `policy`, `minSupportedVersion`, `fetchedAt` | `GET /client/v1/profile` | `profile.json` | `hardExpiry` от `fetchedAt`, но не позже `expiresAt + grace` (см. ниже) |
| `host`, `dnsResolver`, `transports[]` без секретов, `credentialVersion`, `fetchedAt` | `GET /client/v1/endpoint` | `endpoint.json` | вместе с профилем |
| refresh token, приватный ключ WireGuard, пароль IKEv2 | активация, `endpoint` | OS keystore | пока устройство не отозвано |

`FR-161a` (MUST). Проверки `FR-021` по офлайн-профилю: refresh token есть в keystore; последний известный `subscription.status` = `active` и `expiresAt` (по часам с поправкой `serverTime`) еще не наступил либо наступил не раньше, чем `graceUntil`; `profile.fetchedAt` и `whitelist.fetchedAt` моложе `hardExpiry`; версия приложения не ниже последнего известного `minSupportedVersion`; секреты выбранных транспортов есть в keystore. Все условия выполнены - подключение разрешено на офлайн-профиле, в режиме эксперта видно «control plane недоступен, используется профиль от <дата>». Любое не выполнено - подключение блокируется с соответствующим кодом: `cache_hard_expired`, `subscription_expired` (по последнему известному статусу), `client_too_old`, `activation_required` при отсутствии секретов. Профиль, который ни разу не был получен, - это отсутствие профиля: подключение блокируется до первой успешной синхронизации.

`FR-161b` (MUST). Статус подписки, известный только из кеша, - не разрешение, а отсутствие запрета: работающее подключение он не разрывает никогда (`FR-162`), а новое запрещает только в перечисленных случаях. Как только backend снова доступен, свежий профиль заменяет офлайн-профиль целиком, и его результат применяется по обычным правилам разделов 6.7 и 9.2.

`FR-161c` (MUST). При старте без сети клиент читает кеш и профиль, показывает `disconnected` и разрешает нажать «Подключить» по правилам `FR-161a`. Если кеш старше `hardExpiry`, кнопка запускает попытку синхронизации и при неудаче показывает `cache_hard_expired` с подсказкой проверить интернет. Все сценарии холодного старта без backend при доступном endpoint - с кешем разного возраста, с секретами и без них - имеют ровно один ожидаемый исход по таблице `FR-161a`, и он покрыт интеграционным тестом (21.2).

## 13. Native Adapter и privileged helper

### 13.1. Контракт

Native layer отвечает за:

- запуск и остановку WireGuard-туннеля;
- чтение активных сетевых интерфейсов;
- применение и удаление маршрутов;
- применение правил fail-closed;
- защищенное хранение секретов;
- OS-specific autostart integration.

Native layer отдает в TypeScript-приложение небольшой command API.

Транспорты по [ADR-001](decisions/ADR-001-transport.md) и [ADR-005](decisions/ADR-005-dual-transport.md) - WireGuard и IKEv2. Следствия для контракта:

- ключевая пара устройства генерируется на клиенте при активации; приватный ключ хранится в OS keystore и никогда не покидает устройство; backend получает только публичный ключ (API_SPEC, раздел 2);
- helper владеет туннелем целиком: поднимает интерфейс, задает peer с `AllowedIPs`, равным желаемому набору маршрутов, и синхронно с этим применяет системные маршруты и правила fail-closed. `AllowedIPs`, таблица маршрутов и правила блокировки **MUST** меняться одной операцией helper `applyConfiguration` с журналом и откатом (раздел 13.6), иначе возможна рассинхронизация;
- на Windows helper использует kernel-драйвер WireGuard через штатную библиотеку; на macOS - userspace-реализацию на Rust внутри helper через utun ([ADR-002](decisions/ADR-002-macos-tunnel-path.md));
- peer регистрирует `client-api` локально на том же сервере (раздел 15.5); клиент общается с этим сервером по HTTPS для control plane и по WireGuard для трафика, больше ни с кем;
- обфускации поверх WireGuard в текущей реализации нет, это чистый UDP. Транспортный слой helper - набор драйверов за одним интерфейсом: WireGuard, IKEv2, в будущем обфусцированный транспорт; маршруты и fail-closed от драйвера не зависят;
- IKEv2: на Windows helper создает RAS-подключение со split tunneling и ставит маршруты на RAS-интерфейс; на macOS - Personal VPN через NetworkExtension с мостом Swift, helper снимает catch-all и ставит маршруты на `ipsecN` (ADR-005). Учетные данные IKEv2 helper получает из OS keystore через авторизованный IPC, как приватный ключ WireGuard.

### 13.6. Контракт применения конфигурации

Все изменения сети проходят через одну операцию helper `applyConfiguration(desired)`. Core передает желаемое состояние целиком; порядок шагов, диф и восстановление - ответственность helper. Это центральная гарантия архитектуры, и она формулируется как инвариант, а не как последовательность вызовов.

Обозначения. `prev` - последнее зафиксированное поколение, `desired` - применяемое. `protected(G)` определен в 10.7: `G.routes` плюс host-префикс `dnsResolver` (`/32` или `/128`), если он задан, и `∅` при `failClosed = false`; резолвер точки - такой же tunnel-only адрес, как маршруты whitelist, и во всех шагах ниже идет вместе с ними (`FR-167a`). `iface(G)` - интерфейс транспорта поколения.

Защита привязана к намерению, а не к успеху транзакции. Поколение с `failClosed = true` находится в одном из состояний: `prepared` (записан `intent`, блокировка еще не подтверждена), `in-flight` (записан `begin`: блокировка установлена и проверена, применение идет), `committed` (записан `commit`), `held` (записан `rollback` после подтвержденной блокировки: применение не удалось, защита удерживается), `aborted` (записан `abort`: отказ до подтверждения блокировки, защита для N никогда не была установлена; в `INV-1` и в восстановление не входит) или `superseded` (после него зафиксировано более новое поколение). Разница между `held` и `aborted` принципиальна: `held` может быть только у поколения, для которого блокировка была установлена и проверена, иначе журнал обещал бы защиту, которой физически нет. Все состояния персистентны в журнале: удержанная защита никогда не существует только в памяти helper, иначе перезагрузка ее потеряла бы. `prepared` - это сохраненное намерение, источник восстановления после падения, а не гарантия защиты; гарантия начинается с записи `begin`, которая делается только после установки и проверки правил. Отказ применения не снимает защиту: он переводит поколение в `held`, и блокировка держится, пока следующее поколение не будет зафиксировано - удачная попытка на другом транспорте, повтор или явное `failClosed: false` от пользователя. Так выполняется `FR-260`: между попытками подключения защита не исчезает, в том числе при самом первом подключении, когда `prev` пуст.

Обозначение `active` - множество поколений в состояниях `committed`, `in-flight` и `held`; `protected(active)` - объединение их `protected(G)`. Для поколения с `failClosed = false` `protected(G) = ∅`. Инвариант `INV-1`. Блокировка на физических интерфейсах в любой момент покрывает не меньше, чем `protected(active)`. Поколения `prepared` в инвариант не входят: между записью `intent` и записью `begin` защита N еще не обещана, и ничего из N в систему еще не применено. Сужение блокировки происходит только после записи `commit`, и только до `protected(committed)`: запись `commit` одновременно переводит все прежние поколения в `superseded`. Расширение происходит и проверяется до записи `begin`. Граница «политика N вступила в силу» - это запись `commit N`. При такой привязке к журналу убийство helper после любого шага оставляет инвариант верным, а восстановление однозначно: при старте helper сначала восстанавливает блокировку по всем сохраненным намерениям, включая `prepared`, и только потом отвечает приложению.

Порядок внутри helper для поколения N:

1. Записать в журнал `intent N` с полным `desired`; журнал на диске, запись атомарная. N становится `prepared`. Не записалось - применение не начинается, ничего не изменено, `rolled_back` с `journal_write_failed`. Так намерение всегда есть на диске раньше, чем блокировка появляется в системе, и восстановление после падения его найдет.
2. Расширить блокировку до `protected(active) ∪ protected(N)` и проверить по фактическим правилам ОС, что она установлена. `active` включает не только `prev`, но и все удержанные поколения: при последовательности A committed, B held с новыми адресами, C apply - адреса B остаются заблокированы до `commit C`. Расширение безопасно: лишняя блокировка утечкой не является.
3. Записать в журнал `begin N`: это подтверждение, что защита N установлена, N становится `in-flight`. Не записалось - блокировка уже стоит, в памяти N считается `held`, на диске остается `prepared`; при восстановлении это даст то же самое, см. ниже. Откат не нужен, шаги 4-8 не начинались; `rolled_back` с `journal_write_failed`.
4. Если меняется транспорт, либо `iface(prev)` отсутствует или помечен `tunnelUp: false` (после перезагрузки, исчезновения интерфейса, потери по `FR-187`), либо в запросе `rebuild: true` (ручной reconnect, пересборка по health probes `FR-056`): поднять интерфейс заново и дождаться подтверждения (WireGuard: первый handshake; IKEv2: установленная IKE_SA) не дольше `transportTimeoutSec`; старый интерфейс, если он есть, пока не трогать. Не дождались - откат с кодом `transport_unreachable`, и core выбирает следующий транспорт (`FR-260`). Живой интерфейс того же транспорта с той же конфигурацией без `rebuild` переиспользуется.
5. WireGuard: задать `AllowedIPs` равным `AllowedIPs(N)` по 10.7. IKEv2: снять catch-all с `iface(N)` (`FR-265`).
6. Поставить маршруты на `iface(N)`: если интерфейс переиспользован - `protected(N) \ protected(prev)`; если интерфейс поднят заново на шаге 4 - весь `protected(N)`, потому что на новом интерфейсе нет ничего. Пачками по 256, с верификацией по таблице после каждой пачки. Host-маршрут к tunnel-точке через физический шлюз (`FR-044`) ставится здесь же.
7. Снять с `iface(prev)` маршруты `protected(prev) \ protected(N)`; если интерфейс поднят заново - все маршруты `prev` и сам старый интерфейс, если он еще существует.
8. Применить `dnsResolver`: выставить системный DNS или вернуть прежний.
9. Записать `commit N`. С этого момента действует политика N, все прежние поколения - `superseded`.
10. Сузить блокировку до `protected(N)`: после `commit N` `active = {N}`, поэтому сужение до одного поколения и есть сужение до `protected(active)`.

Ошибка на шагах 4-8: helper откатывает физическое состояние к `prev` (маршруты на `iface(prev)`, `AllowedIPs`, DNS; поднятый новый интерфейс опускается), пишет `rollback N`, переводит N в `held` и возвращает `status: "rolled_back"` с кодом шага и списком неудавшихся записей. Блокировка остается `protected(active) ∪ protected(N)` и не сужается. Core остается на `prev` и решает, что дальше: следующий транспорт, повтор с backoff или `error` с активной защитой. Частичного успеха как итога нет: либо поколение N зафиксировано целиком, либо действует N-1 с удержанной защитой N.

`journal_write_failed` на любом шаге core трактует как отказ устройства, а не транспорта: перебор транспортов не имеет смысла, если состояние защиты нельзя сохранить. Переход в `error`, отчет администраторам. Есть ли при этом защита, core берет только из `protectionHeld` в ответе и из `getAppliedConfiguration()`, а не выводит из кода ошибки: при отказе записи `intent` на первом подключении защиты нет, и интерфейс обязан показать «не подключено, защита не активна», а не обещать отсутствующую блокировку. Это правило общее: статус защиты в UI строится по фактическому состоянию helper, а не по тому, что приложение хотело сделать.

Исходы ошибок вне шагов 4-8 и ошибки самого отката:

| Где сбой | Действующее поколение | Защита | Что получает приложение |
| --- | --- | --- | --- |
| Шаг 1, не записался `intent` | `prev` | как была: `protected(prev)`; при первом подключении - никакой | `rolled_back`, `journal_write_failed`, `protectionHeld` по факту; ничего не изменено |

Падение helper или машины. При каждом старте helper делает три вещи в этом порядке, до того как отвечать приложению:

1. По журналу восстанавливает блокировку: `protected(committed) ∪ protected(in-flight) ∪ protected(held) ∪ protected(prepared)`, и проверяет ее по фактическим правилам ОС. Намерения `prepared` включаются нарочно: лишняя блокировка безопасна, а пропущенная - нет. Поколения `aborted` и `superseded` не учитываются. Это выполняется раньше, чем сеть становится доступной приложениям, поэтому fail-closed переживает перезагрузку.
2. Сверяет журнал. `intent N` или `begin N` без завершающей записи: если блокировка по N на шаге 1 установилась и проверена - пишет `rollback N`, N переходит в `held`; если установить не удалось - запись остается как есть до успешного повтора по единому правилу ниже, в `aborted` при восстановлении поколение не переводится никогда. Для `begin` прежнее подтверждение до перезагрузки ничего не доказывает сейчас, поэтому правило одно для обеих записей. `commit N` без сужения - сужает до объединения активных поколений, которое после `commit N` равно `protected(N)`.
3. Сверяет фактическое состояние с `committed`: интерфейсы, маршруты, `AllowedIPs`, DNS. Если `committed` - `disabled`-поколение или незавершенный `intent` с `failClosed: false`, helper доводит отключение до конца и ничего не восстанавливает. Наличие `commit` в журнале ничего не говорит о живом туннеле после перезагрузки. Туннель helper сам не поднимает: секреты живут в keystore приложения и приходят через IPC (`privateKeyRef`, `passwordRef`), и helper держит их только в памяти на время сессии. Если интерфейс `committed` жив и совпадает с журналом, helper его принимает и чинит недостающие маршруты; иначе фиксирует `tunnelUp: false`, возвращает системный DNS (`FR-167b`) и остается в защищенном состоянии без туннеля. Приложению при подписке отдаются `apply_recovered` и `tunnelLost`, и оно поднимает туннель новым `applyConfiguration`.

Единое правило после старта: статус защиты для любого поколения, в любом состоянии, определяется только текущей проверкой правил ОС на шаге 1, а не записями журнала. Если ОС отказала в установке правил хотя бы для части объединения, helper не объявляет защиту: `protectionHeld: false`, `tunnelUp: false`, событие `protectionRestoreFailed` и отчет `fail_closed_restore_failed`. Записи `intent`, `begin`, `held` и `committed` при этом сохраняются как есть, в `aborted` не переводятся: намерение остается для повтора. Helper повторяет восстановление каждые 30 секунд и при каждом `applyConfiguration`; при успехе дописывает завершающие записи по правилам шага 2 и отдает `protectionHeld: true`. Приложение стартует в `error` с честным «защита не активна» и кнопкой «Повторить». `INV-1` в этом окне не выполняется по причине, которую helper устранить не может, и именно поэтому окно видно пользователю и администратору, а не скрыто за статусом «защищено».

Сериализация и таймауты. Helper выполняет не больше одного `applyConfiguration` за раз. Запрос, пришедший во время идущей операции, отвечает `rejected` с кодом `apply_in_progress` и номером идущего поколения; core ждет ее исхода через `getApplyStatus`, а не повторяет запрос. Таймаут IPC на стороне core (`FR-181`) не прерывает операцию: helper всегда доводит ее до одного из терминальных исходов, `applied` или `rolled_back`, и хранит исход последних десяти поколений для `getApplyStatus(generation)`; пока операция идет, `getApplyStatus` и `getAppliedConfiguration().inProgress` отдают `in_progress` с номером шага. Следующий `applyConfiguration` допустим только после терминального исхода. Внутренние операции helper - сверка drift, восстановление при старте, повтор восстановления защиты каждые 30 секунд - стоят в той же очереди: во время применения сверка не запускается, а очередная сверка после применения сравнивает уже с новым `committed`. Отмены операции нет: откат внутри helper и так ограничен `transportTimeoutSec` плюс время маршрутов, а «отмена» с точки зрения пользователя - это следующее поколение с `transport: null`, которое встанет в очередь.

Номера поколений. Источник следующего номера - `AppliedState.lastGeneration`, наибольший номер, встречающийся в журнале в любом состоянии, включая `held`, `aborted` и восстановленные после падения; core берет `lastGeneration + 1` и никогда не ведет свой счетчик. Полная матрица:

| Запрос | Что делает helper |
| --- | --- |
| `generation < lastGeneration`, любое содержимое | `rejected`, `generation_conflict`: устаревший запрос |
| `generation` равен `committed`, то же содержимое | сверка (ниже), новое поколение не создается |
| `generation` равен `committed`, другое содержимое | `rejected`, `generation_conflict` |
| `generation` равен `held` или `prepared` поколению, то же содержимое | повтор той же попытки: журнал `retry N`, шаги 2-10 заново под тем же номером |
| `generation` равен `held` или `prepared`, другое содержимое | `rejected`, `generation_conflict` |
| `generation = lastGeneration + 1`, любое содержимое, включая совпадающее с `committed` | новое применение по шагам 1-10; при совпадающем содержимом и живом интерфейсе шаги 4-8 ничего не меняют, `commit N` переводит прежние в `superseded` |
| `generation > lastGeneration + 1` | `rejected`, `generation_conflict`: пропуск номеров запрещен, чтобы после восстановления core и helper не разошлись |

Повтор запроса и сверка. Повторный `applyConfiguration` с тем же `generation` и тем же содержимым - не «ничего не делать», а «сверить и доложить»: helper сравнивает таблицу маршрутов, `AllowedIPs`, DNS и правила блокировки с зафиксированным поколением; если все на месте, возвращает `applied` без изменений, если нет - восстанавливает недостающее тем же кодом, что шаги 5-8, без записи нового поколения. Блокировку при сверке helper выставляет в `protected(active)`, а не в `protected(committed)`: пока после отката B удерживается защита его адресов, ремонт A не имеет права ее снять. Сужение до одного поколения делает только шаг 10 после новой записи `commit`, которая переводит остальные в `superseded`. Именно эта сверка и есть ремонт drift (`FR-186`): helper делает ее сам по событиям ОС и по таймеру. Запрос с меньшим `generation` отклоняется; с большим и другим содержимым - новое применение по шагам 1-10.

Отключение и снятие защиты. `applyConfiguration` с `failClosed: false` и обязательным `reason` - единственный штатный способ снять блокировку; helper проверяет `reason` против `policy.failClosedUserOverride` (`reason: "user"` при `false` - `rejected`, `policy_violation`). Три формы: полное отключение (`transport: null, failClosed: false`), снятие только защиты при живом туннеле (`transport` задан, `failClosed: false`) и отключение с сохранением защиты (`transport: null, failClosed: true`; это состояние `FR-196`, а не отключение). Поколение с `failClosed: false` имеет `protected = ∅` и после фиксации называется `disabled`; это персистентное терминальное состояние, из которого восстановление при старте ничего не блокирует. Порядок для поколения N c `failClosed: false`:

1. Записать `intent N` с `reason`. Не записалось - ничего не менять, `rolled_back` с `journal_write_failed`; защита остается как была.
2. Снять маршруты `protected(active)` со всех интерфейсов helper.
3. Вернуть системный DNS (`dnsRestored` с `reason: "disconnect"`).
4. Снять блокировку целиком.
5. Если `transport: null` - опустить интерфейс; иначе оставить туннель и `AllowedIPs` равными `routes ∪ assignedAddresses` без резолвера в защите.
6. Записать `commit N`: все прежние поколения - `superseded`, N - `disabled` (или `committed` без защиты при живом туннеле).

Шаги 2-5 выполняются до конца даже при ошибках: намерение снять защиту уже зафиксировано, и половинчатое состояние «блокировка снята, маршруты остались» хуже, чем «все снято, кроме того, что не удалось». Каждая неудача попадает в `failed`; `commit N` пишется в любом случае, ответ - `applied` с кодом `cleanup_incomplete`, если что-то не снялось. Helper повторяет незавершенную очистку при каждой сверке и при старте, core показывает «отключено, часть настроек не удалось убрать» и шлет `route_remove_failed`. Падение после шага 1 и до шага 6: при старте helper находит `intent N` с `failClosed: false` и завершающей записи нет - он **не** восстанавливает блокировку по этому намерению (`protected(N) = ∅`), а доводит отключение до конца по шагам 2-6, потому что намерение снять защиту исходит от разрешенного `FR-062` источника и уже записано; прежние поколения при этом в `INV-1` не участвуют с момента записи `intent N` с `failClosed: false`. Так снятая по разрешенной причине защита не возвращается сама ни после падения helper, ни после перезагрузки, ни от watchdog.

Предохранитель (`FR-197`) идет тем же путем: helper сам записывает `intent` и `commit` поколения `lastGeneration + 1` с `transport: null, failClosed: false, reason: "safety_valve"`, выполняет шаги 2-5 и ставит маркер. С этого момента `committed` - `disabled`-поколение, и ни watchdog, ни восстановление при старте прежние поколения не трогают. Маркер снимается следующим `applyConfiguration` от приложения, после того как оно показало предупреждение и отправило `fail_closed_auto_lifted`.

Старт приложения (`FR-133`, `FR-196`) различает по `AppliedState`: `committed` жив (`tunnelUp: true`, конфигурация совпадает с желаемой) - сверка и `connected`; `committed` с защитой и `tunnelUp: false` - `error`/`reconnecting` по `FR-196`; `committed` - `disabled` или `committed: null` - `disconnected`.

Потеря туннеля без команды приложения: helper оставляет блокировку и маршруты, возвращает системный DNS (`FR-167b`), помечает поколение `tunnelUp: false` и шлет `tunnelLost`. Условия потери - `FR-187`. Поднимать туннель заново решает приложение новым `applyConfiguration` с `rebuild: true` (`FR-024`); если приложения нет, состояние держится до его старта или до предохранителя (`FR-197`).

`FR-187` (MUST). Живость туннеля helper определяет так, и только так:

- интерфейс транспорта исчез или ОС сообщила о его выключении - потеря немедленно;
- IKEv2: IKE_SA разорвана или ОС сообщила о разрыве подключения - потеря немедленно;
- WireGuard: возраст handshake сам по себе потерей не считается. Keepalive не обновляет handshake, а штатный rekey происходит раз в 120 секунд (`REKEY_AFTER_TIME`) и только при отправке данных, поэтому у исправной сессии возраст handshake законно превышает любой кратный keepalive порог. Признак подозрения - счетчик отправленных байт растет, а принятых не меняется 30 секунд, либо handshake старше 180 секунд (`REJECT_AFTER_TIME`) при попытках отправки. По подозрению helper шлет пробы через туннель: три ICMP echo или TCP SYN на порт 53 к `dnsResolver` (при его отсутствии - к адресу сервера в tunnel-подсети, первому адресу `assignedAddresses`-сети) с интервалом 5 секунд. Любой ответ, включая RST, - туннель жив, счетчики сбрасываются; тишина на все три - `tunnelLost` с `reason: "probe_timeout"`.

Гарантия времени: обнаружение молчаливой потери занимает не больше 45 секунд (30 секунд тишины плюс три пробы), обнаружение исчезновения интерфейса и разрыва IKE_SA - немедленно. Пять секунд `FR-167b` отсчитываются от обнаружения, а не от фактической потери: при молчаливой потере пакетов пользователь без DNS может провести до 50 секунд, и это осознанная граница, а не обещание. Ложные срабатывания недопустимы: исправный туннель под нагрузкой и в простое в течение нескольких минут не должен давать ни одного `tunnelLost`, это проверяется отдельным тестом helper (`T-002`). `tunnelRestored` helper шлет только после подтвержденного обмена по тому же правилу проб.

`FR-185` (MUST). Гранулярные операции (`applyRoutes`, `removeRoutes`, `enableFailClosed`, `updateFailClosed`, `disableFailClosed`) существуют только в тестовой сборке helper (`--features test-commands`) и нужны тестам `T-002`; релизная сборка отвечает на них `not_permitted`, и приложение их не вызывает ни в одном режиме, включая режим эксперта. Диагностика режима эксперта (`FR-168`, `FR-169`) использует только читающие методы адаптера и пробы из пользовательского процесса. Так `applyConfiguration` остается единственным путем изменения сети, а `failClosedUserOverride: false` нельзя обойти гранулярной командой. В тестовой сборке любой такой вызов пишется в журнал helper и не меняет состояние поколений: `committed` и `INV-1` он не затрагивает, а расхождение, которое он внес, следующая сверка чинит как drift.

`FR-186` (MUST). Helper чинит drift сверкой фактического состояния ОС с зафиксированным поколением и восстановлением недостающего тем же кодом, что шаги применения, а не точечными правками, чтобы инварианты применения и ремонта были одними. «Ничего не менять» допустимо только после сверки, подтвердившей, что конфигурация действует. Приложению для ремонта быть запущенным не обязательно.

`T-002` (MUST). Тесты helper **MUST** включать: убийство helper после каждого шага 1-10 применения и после каждого шага 1-6 отключения с проверкой `INV-1` захватом трафика и корректного восстановления при старте, включая то, что снятая по `reason` защита после падения не возвращается; предохранитель, затем watchdog-сверка и перезагрузка, с проверкой, что блокировка не вернулась; снятие только защиты при живом туннеле; ошибку удаления правил при отключении с проверкой `cleanup_incomplete` и повторной очистки; поздний `commit` после таймаута IPC с проверкой, что `getApplyStatus` отдает терминальный исход и следующий `apply` не принимается раньше; потерю ответа `commit`; рестарт приложения при `held` с большим номером, чем `committed`, с проверкой, что core берет `lastGeneration + 1`; последовательность A committed, B held с новыми адресами, C apply с проверкой, что адреса B заблокированы до `commit C`; неизменный список и транспорт после перезагрузки, исчезновение интерфейса, ручной reconnect и смену DNS без изменения списка с проверкой, что каждый сценарий доходит до нужных операций helper; исправный туннель под нагрузкой и в простое без ложного `tunnelLost` и обнаружение молчаливой потери не позже 45 секунд (`FR-187`); перезагрузку машины после `commit` с проверкой, что блокировка стоит до появления сети, а туннель поднимается только приложением; отказ ОС при восстановлении правил после перезагрузки с проверкой, что helper отдает `protectionHeld: false`, записи журнала сохранены и повтор восстановления проходит после снятия отказа; отказ ОС на шаге 6 с проверкой отката; две совмещенные последовательности: откат поколения с дополнительными адресами, затем ремонт drift предыдущего поколения, с проверкой, что адреса удержанного поколения остались заблокированы; отказ записи `begin` при уже записанном `intent`, затем перезагрузка, с проверкой, что удержанная защита восстановлена из журнала; первое подключение, где первый транспорт не поднялся, с захватом трафика в паузе перед вторым транспортом; каждый исход из таблицы выше, включая инъекцию отказа записи `begin`, `commit` и самого отката; смену транспорта с неизменным списком с проверкой, что весь список оказался на новом интерфейсе; повтор того же поколения без изменений при целой конфигурации и с восстановлением при искусственно удаленном маршруте; достижимость резолвера точки только через туннель.

## 14. Fail-Closed

### 14.1. Что защищаем

Утечкой считается ситуация, когда пакет к protected destination уходит через физический интерфейс, а не через tunnel. Основные окна утечки:

1. tunnel упал, а маршруты еще указывают на старый интерфейс;
2. интерфейс tunnel исчез, ОС вернула маршруты на шлюз по умолчанию;
3. смена сети: старые маршруты сняты, новые еще не применены;
4. запуск приложения до поднятия tunnel при включенном автоподключении;
5. аварийное завершение приложения при активном подключении.

### 14.2. Требования

`FR-190` (MUST). Fail-closed **MUST** блокировать трафик к protected destinations на всех интерфейсах, кроме tunnel-интерфейса.

`FR-191` (MUST). Правила fail-closed **MUST** переживать исчезновение tunnel-интерфейса: блокировка не должна зависеть от существования интерфейса.

`FR-192` (MUST). Трафик к tunnel endpoint **MUST** оставаться разрешенным, иначе reconnect невозможен.

`FR-193` (MUST). DNS-запросы к системным резолверам **MUST NOT** блокироваться целиком; блокируются только protected destinations. Приложения с собственным DoH или DoT, например браузеры, обходят системный DNS: для них работает только IP-whitelist, и справка об этом говорит.

`FR-194` (MUST). Локальная сеть пользователя (шлюз, принтеры, NAS) **MUST** оставаться доступной, если явно не включено обратное.

Grace-период. `tunnel_manager` ждет 60 секунд до блокировки, потому что blackhole на шлюзе роняет всех клиентов за ним. На устройстве пользователя такой цены нет, и блокировка включается сразу. При этом у WireGuard маршруты продолжают указывать в интерфейс, пока он существует, и пакеты без handshake просто не уходят: окно утечки возникает только при исчезновении интерфейса, его и закрывают правила `FR-191`. На IKEv2 такого свойства нет: при падении туннеля ОС возвращает маршруты на шлюз по умолчанию, и блокировка `FR-190` - единственная защита.

`FR-198` (MUST). Правила fail-closed не привязаны к типу интерфейса: они пропускают protected destinations только через интерфейс активного транспорта (`utun`/`wg` или `ipsec`/RAS) и блокируют на остальных. Смена транспорта - обновление одного правила, а не снятие блокировки.

### 14.3. macOS

- Туннель и правила живут в одном privileged helper: userspace WireGuard через utun плюс packet filter для блокировки (ADR-002).
- Набор protected destinations выносится в отдельную таблицу pf в собственном якоре, чтобы не конфликтовать с чужими правилами.
- Helper проверяет привязку якоря при каждой сверке: система может перезагрузить правила при смене сети, и якорь должен быть восстановлен раньше, чем маршруты.
- При выключении приложение удаляет только свой якорь.
- NetworkExtension остается запасным путем, если userspace-реализация упрется в ограничения системы или потребуется распространение через App Store.

### 14.4. Windows

- Маршруты в таблице маршрутизации плюс правила Windows Filtering Platform или firewall: на Windows одних маршрутов недостаточно, блокирующие правила обязательны (`FR-217`).
- Правила создаются в собственной именованной группе, чтобы удаление не задевало правила сторонних VPN-клиентов и антивирусов.
- Метрики маршрутов задаются явно: без этого система может предпочесть маршрут по умолчанию и увести защищенный трафик мимо tunnel.
- Правила применяются службой helper и переживают исчезновение tunnel-интерфейса и перезапуск пользовательской части приложения.

### 14.5. Android

- Реализация внутри системного Android tunnel service.
- Эквивалент fail-closed достигается настройками самого сервиса, отдельная таблица маршрутов недоступна.

### 14.6. Поведение при завершении приложения

`FR-195` (MUST). При штатном выходе приложение снимает fail-closed и маршруты.

`FR-196` (MUST). При аварийном завершении fail-closed **MUST** оставаться активным (это безопасное состояние). При следующем старте приложение читает `getAppliedConfiguration()`: если helper держит поколение с `failClosed = true` без живого туннеля, приложение стартует в `error` с текстом «Защита активна, соединение не восстановлено» и кнопками «Подключить» и «Снять защиту»; при включенном автоподключении сразу переходит в `reconnecting`. Helper тем временем продолжает следить за drift и держит блокировку.

`FR-197` (MUST). Предохранитель helper. «Приложение на связи» - любой авторизованный IPC-вызов, включая `heartbeat()`, который приложение шлет раз в 5 минут; срок считается от `lastHeartbeatAt` в журнале helper и переживает его перезапуск. Если приложение не выходило на связь дольше `policy.safetyValveHours` (по умолчанию 24 часа), helper **MUST** снять свои правила блокировки, маршруты и подмену DNS через `disabled`-поколение с `reason: "safety_valve"` (13.6), чтобы ни watchdog, ни перезагрузка их не вернули. Это единственное автоматическое исключение из `FR-062`, и оно осознанное: приложение могло быть удалено вручную или сломаться, и пользователь без защиты на этом устройстве лучше, чем пользователь с неработающими сайтами навсегда и без объяснения. Helper **MUST** записать событие в свой журнал и оставить маркер; при следующем старте приложение **MUST** показать пользователю, что защита была снята автоматически, и отправить `fail_closed_auto_lifted` администраторам. Срок настраивается политикой в пределах 6-72 часов, отключить предохранитель нельзя.

### 14.7. Проверка (leak test)

Обязательные проверки перед релизом:

| # | Проверка | Ожидание |
| --- | --- | --- |
| L1 | Подключено, запрос к protected IP | идет через tunnel-интерфейс |
| L2 | Принудительно останавливаем tunnel | запрос к protected IP не проходит вообще |
| L3 | Отключаем Wi-Fi и включаем снова | утечек нет ни в один момент переключения |
| L4 | Sleep/wake | после пробуждения либо tunnel восстановлен, либо доступ заблокирован |
| L5 | Убиваем процесс приложения | protected IP остается заблокирован |
| L6 | Смена сети Wi-Fi -> Ethernet | утечек нет |
| L7 | Запрос к non-protected IP во всех состояниях | всегда проходит напрямую |
| L8 | Доступ к локальной сети | сохраняется |
| L9 | Туннель упал при DNS через точку | системный DNS возвращен не позже 5 с после обнаружения (при молчаливой потере UDP - не позже 50 с от блокировки), сайты вне списка открываются, защищенные заблокированы |
| L11 | Исправный туннель несколько минут под нагрузкой и в простое, затем UDP заблокирован при живом интерфейсе | ни одного ложного `tunnelLost` до блокировки; после блокировки потеря обнаружена не позже 45 с |
| L10 | Резолвер точки мимо туннеля | запрос к адресу резолвера на физическом интерфейсе блокируется |

`T-001` (MUST). Leak-тесты **MUST** выполняться с фиксацией сетевого трафика на физическом интерфейсе, а не только по факту доступности сервиса, и на каждом транспорте отдельно; на IKEv2 дополнительно проверяется, что catch-all не вернулся после reconnect.

## 15. Backend API

Клиент работает только через backend API. Backend поддерживает клиентский контур отдельно от приватного серверного контура; изменения обратно совместимы с админкой, Telegram-ботом и серверным Tunnel Manager.

Control plane клиента - отдельный сервис `client-api` на зарубежном VPN-сервере, рядом с `wg0` ([ADR-004](decisions/ADR-004-control-plane-placement.md)). Стек тот же, что у дашборда (FastAPI, Postgres), но БД своя и живет за рубежом: устройства, коды активации, публичные ключи, копия статусов подписок. Дашборд и бот на RU-сервере остаются источником правды для списка и подписок и интегрируются с `client-api` через admin API (раздел 15.6). Клиент к RU-серверу не обращается.

Endpoints:

| Метод и путь | Назначение |
| --- | --- |
| `POST /client/v1/auth/device-code` | код связки для входа через бота по deep link |
| `POST /client/v1/auth/device-token` | опрос подтверждения и получение токенов |
| `POST /client/v1/auth/activate` | активация кодом, выданным ботом или админкой |
| `POST /client/v1/auth/refresh` | обновление access token, без `Authorization` (`API-023`) |
| `POST /client/v1/endpoint/ikev2-ack` | подтверждение сохранения пароля IKEv2 (`API-058`) |
| `POST /client/v1/endpoint/rotate-ikev2` | ротация учетных данных IKEv2 (`API-058a`) |
| `DELETE /client/v1/device` | отвязка устройства при выходе из аккаунта |
| `GET /client/v1/profile` | пользователь, подписка, политики, версия |
| `GET /client/v1/routes` | route list с версией, хешем, TTL |
| `GET /client/v1/endpoint` | metadata tunnel-точки |
| `POST /client/v1/events` | легкие события |
| `POST /client/v1/diagnostics` | диагностика и validation errors |
| `POST /client/v1/error-reports` | redacted отчеты об ошибках |

Общие правила:

`API-001` (MUST). Все ответы содержат `serverTime` для коррекции расхождения часов и `minSupportedVersion`.

`API-002` (MUST). Все ошибки возвращаются в едином формате с машинным `code` и человеческим `message`.

`API-003` (MUST). Все мутирующие запросы поддерживают `Idempotency-Key`.

`API-004` (MUST). Backend применяет rate limit per device и возвращает `Retry-After`.

Полная спецификация с телами запросов и ответов - [API_SPEC.md](API_SPEC.md).

### 15.1. Ответ со списком маршрутов

Route list включает:

- версию списка;
- content hash;
- время генерации;
- TTL;
- группировку по сервисам;
- IPv4 CIDR;
- IPv6 CIDR, когда платформа поддерживается;
- опциональный emergency blocklist;
- минимальную поддерживаемую версию приложения.

Клиент игнорирует невалидные CIDR и отправляет validation errors в диагностику.

### 15.2. События

Клиент отправляет легкие события:

- приложение запущено;
- подключение начато или остановлено;
- синхронизация маршрутов успешна или неуспешна;
- fail-closed активирован или деактивирован;
- подписка истекла;
- версия приложения.

`SEC-030` (MUST). События **MUST NOT** содержать посещенные URL, payload, историю браузинга или содержимое трафика.

### 15.3. Error reports

`POST /client/v1/error-reports` принимает redacted отчет. Backend:

- проверяет доступ пользователя и устройства;
- сохраняет отчет;
- дедуплицирует повторы по fingerprint;
- применяет rate limit;
- отправляет важные новые ошибки администраторам в Telegram;
- не отправляет в Telegram шумные события и повторы.

Ответ сообщает клиенту, был ли отчет принят и был ли он отправлен администраторам. Пользователю показывается простой статус: "Ошибка отправлена" или "Не удалось отправить, попробуйте позже".

### 15.4. Админка

В 1.0 у клиентского контура нет отдельной веб-админки: чтобы не менять фронтенд дашборда, административные представления живут в двух местах, которые уже есть, - в боте и в админ-панели приложения (6.15). Оба ходят в один admin API `client-api` (API_SPEC, раздел 11).

`API-005` (MUST). Бот получает команды-обертки над admin API по образцу существующих `/users` и `/user <id>`: `/devices <user>` (устройства: платформа, версия, последний sync, возраст whitelist, транспорт), `/report <fingerprint>` (карточка отчета с историей повторов и кнопкой «решено»), `/clientstatus` (peer онлайн, возраст копий списка и статусов, распределение версий).

`API-006` (MUST). Сообщение об ошибке в Telegram заканчивается подсказкой `/report <fingerprint>`, а не ссылкой на веб-страницу.

`API-007` (MUST). Выдача и отзыв кодов активации, отзыв устройства и сброс лимита устройств доступны из карточки пользователя бота и из админ-панели приложения.

`API-008` (MUST). Веб-админка дашборда в 1.0 не меняется (`FR-002`). Ее расширение под клиентский контур - после 1.0, если бота и панели окажется мало.

### 15.5. Провизионинг peer

`client-api` и `wg0` работают на одном хосте, поэтому регистрация peer - локальный вызов, как сегодня у бота: `wg set`, дозапись блока с маркером в wg-quick конфиг, удаление по маркеру. Логика `bot/wireguard.py` серверного репозитория переносится как есть.

`API-009` (MUST). Peer регистрируется в момент активации устройства и снимается при отзыве устройства или истечении подписки. `GET /client/v1/endpoint` отдается только после успешной регистрации peer.

`API-095` (MUST). `client-api` работает от отдельного системного пользователя без capabilities и без прав на `wg0`, `wg-quick` конфиг, `ipsec.secrets` и команды strongSwan. Привилегированные операции выполняет отдельный юнит `client-api-provisioner` от root с фиксированным набором команд через локальный unix-сокет с правами только для пользователя `client-api`: `add_peer(publicKey, addresses)`, `remove_peer(publicKey)`, `set_eap_secret(identity, passwordHash)`, `remove_eap_secret(identity)`, `terminate_ike(identity)`, `list_peers()`. Аргументы типизированы и валидируются провизионером, shell-строки и пути не принимаются, каждая команда идемпотентна и пишется в его журнал. `CAP_NET_ADMIN` для `client-api` не используется: эта capability не ограничивается одним интерфейсом и дала бы процессу с внешним HTTP-интерфейсом власть над всеми интерфейсами, маршрутами и firewall сервера.

`API-095a` (MUST). Активация - распределенная операция между БД, WireGuard и EAP, и она восстанавливаема: запись устройства создается со статусом `provisioning`; затем `add_peer`, затем `set_eap_secret`, затем статус `active`; токены и `endpoint` выдаются только из `active`. Отказ любого шага откатывает уже сделанные (`remove_peer`, `remove_eap_secret`) и возвращает ошибку; перезапуск `client-api` посреди активации оставляет `provisioning`, и сверка `API-096` при следующем проходе доводит такие записи старше 60 секунд до `active` или удаляет их вместе с частично созданными peer и учетками. Код связки при этом остается в ожидании и повторный `approve` идемпотентен.

`API-096` (MUST). Раз в 5 минут `client-api` сверяет peer на интерфейсе и EAP-учетки со своей БД через `list_peers` провизионера: лишние снимает, недостающие для активных устройств ставит, незавершенные активации завершает (`API-095a`). Событие отзыва с повторами (`API-120a`) - основной путь для срока 60 секунд, сверка - страховка от потерянных событий и путь для изменений из веб-админки.

`API-097` (MUST). Отзыв устройства (`FR-014`) **MUST** снимать peer не позже 60 секунд.

`API-098` (MUST). Пул адресов устройств - подсеть `wg0`, первый адрес - сервер. Соответствие устройство -> адрес хранится в БД `client-api`; один адрес двум устройствам не выдается.

Вторая и последующие tunnel-точки - после 1.0. Для них либо на каждой точке свой экземпляр `client-api` с общей БД, либо агент провизионинга; набросок контракта агента - API_SPEC, раздел 11.1, помечен как отложенный.

### 15.6. Интеграция с RU-контуром

Клиент никогда не обращается к RU-серверу. Данные ходят между серверами:

`API-110` (MUST). Список маршрутов `client-api` забирает у дашборда `GET /api/routes` с `X-Api-Key`, тем же путем, что `tunnel_manager`, не реже раза в 5 минут и с `If-None-Match`; парсит тем же парсером, агрегирует и публикует как `GET /client/v1/routes` с версией и хешем. При недоступности дашборда отдается последняя валидная копия, клиенты этого не замечают.

`API-111` (MUST). Пользователи и подписки: источник правды - таблица `tunnel_users` дашборда. `client-api` хранит копию нужных полей: id, enabled, expires_at, лимит устройств. Бот **MUST** пушить изменение статуса в `client-api` при продлении, отключении и включении из своей карточки; изменения из веб-админки дашборда доезжают сверкой, которую `client-api` делает раз в 5 минут вместе со списком. При недоступности RU действует последняя известная копия; отзыв, сделанный во время недоступности, доезжает при сверке.

`API-112` (MUST). Коды активации и подтверждение кодов связки делает `client-api` по запросу бота или админки через admin API с отдельным токеном. Бот сам коды не генерирует и в своей БД не хранит; для человека он единственный интерфейс авторизации (раздел 5.0).

`API-113` (MUST). Отчеты об ошибках `client-api` пересылает в существующий `POST /api/notify` дашборда, который уже доставляет сообщения в админ-чаты; дедупликация и rate limit делаются в `client-api` до пересылки.

`API-114` (MUST). Все межсерверные вызовы - только по HTTPS с токенами из `.env`; токены дашборда и `client-api` разные. `client-api` ходит в дашборд сервисными токенами со scope: `routes:read`, `users:read` и `notify` в 1.0; `users:write` для мутаций пользователей из админ-панели приложения (`API-136`); `routes:write` в 1.1 (`FR-283`). Один токен - один scope. В репозиториях токенов нет.

`API-115` (MUST). IKEv2 на зарубежном сервере обслуживает strongSwan; `client-api` выдает EAP-учетки per device той же логикой, что `bot/tunnel_helpers.py` (`_rewrite_secret_line`, `_reread_secrets`, `_terminate_identity`), и снимает их при отзыве (`FR-263`).

Контракт admin API - API_SPEC, раздел 11.

## 17. Безопасность

### 17.1. Базовые требования

- Клиенты не подключаются к базе данных напрямую.
- Production secrets не хардкодятся.
- API access tokens отзывные.
- Route lists подписаны или hash-validated.
- Backend проверяет subscription/access state.
- Клиент учитывает minimum API compatibility.
- Логи скрывают secrets и endpoint credentials.
- Public repository не содержит production infrastructure details.
- Новый клиентский контур не дает публичным пользователям доступ к приватному серверному контуру.

### 17.2. Модель угроз

| # | Угроза | Митигация |
| --- | --- | --- |
| TH-1 | Утечка защищенного трафика мимо tunnel | fail-closed, watchdog, leak-тесты (разделы 6.5, 14) |
| TH-2 | Кража refresh token с устройства | хранение в OS keystore, ротация при refresh, отзыв на backend |
| TH-3 | Подмена route list посредником | TLS, content hash, подпись Ed25519, anti-rollback |
| TH-4 | Откат на старый список маршрутов | монотонная версия, отклонение старых версий |
| TH-5 | Локальная эскалация через helper | ограниченный набор команд, проверка вызывающего, валидация аргументов |
| TH-6 | Утечка PII в отчетах и логах | allowlist-сериализация, redaction-фильтры, запрет свободного текста |
| TH-7 | Доступ клиентского контура к приватному | раздельный namespace, отдельные токены, тесты авторизации |
| TH-8 | Раскрытие инфраструктуры через публичный репозиторий | запрет реальных адресов и ключей, проверка в CI |
| TH-9 | DoS на backend от массы клиентов | jitter, backoff, условные запросы, rate limit на стороне backend |
| TH-10 | Использование отозванного устройства | короткий TTL access token, проверка отзыва при каждом refresh |
| TH-11 | Компрометация зарубежного сервера, где и туннель, и БД устройств | `client-api` не от root (`API-095`); в БД только публичные ключи и хеши; токен к дашборду с минимальными правами (`API-114`) |
| TH-12 | Недоступность RU-сервера для зарубежного backend | копии списка и статусов (`API-110`, `API-111`): клиенты работают, отзыв доезжает при восстановлении |
| TH-13 | Админский токен на скомпрометированном устройстве | роль проверяется на сервере, TTL 15 минут, аудит, подтверждение разрушительных действий, второе подтверждение в боте (`FR-285`, `FR-286`) |
| TH-14 | Утечка пароля IKEv2 устройства | пароль per device, выдается один раз при активации, отзыв устройства снимает его (`FR-263`, `API-058`) |
| TH-15 | Злоупотребление пробным периодом через много Telegram-аккаунтов | существующий онбординг бота с одобрением админом и анти-флудом; один аккаунт - один пробный период (`FR-272`) |
| TH-16 | Окно после потери туннеля: DNS возвращен на системный, ответы могут быть подменены | защищенные адреса остаются заблокированы (`FR-190`); адрес вне списка уходит напрямую, как в режиме «системный DNS»; режим эксперта показывает причину (`FR-168`) |

### 17.3. Токены

| Параметр | Значение по умолчанию |
| --- | --- |
| TTL access token | 15 минут |
| TTL refresh token | 30 суток, продлевается при использовании |
| Ротация refresh | при каждом использовании, старый инвалидируется |
| Обнаружение переиспользования | использование инвалидированного refresh отзывает устройство |
| Хранение access | только память процесса |
| Хранение refresh | OS keystore |
| Роль в токене | выдается ботом при подтверждении входа, хранится в записи пользователя `client-api` и меняется только push-ем бота (`API-138`); перепроверяется при каждом refresh; снятие роли в боте доезжает не позже 15 минут после получения push-а `client-api`, при недоступном RU действует последняя известная роль |

### 17.4. Канал

`SEC-040` (MUST). Все обращения к backend только по HTTPS с проверкой сертификата.

`SEC-041` (SHOULD). Клиент **SHOULD** использовать pinning публичного ключа backend с запасным ключом и процедурой ротации. Pinning без запасного ключа запрещен.

### 17.5. Публичный репозиторий

`SEC-042` (MUST). В репозитории **MUST NOT** быть: реальных адресов tunnel-точек и backend, private keys, tokens, admin-only endpoints, дампов конфигурации. Для примеров используются заглушки.

`SEC-043` (MUST). CI **MUST** содержать шаг проверки на секреты и на IP/hostname-паттерны в коммитах.

## 19. Платформенные требования

Обе desktop-платформы входят в MVP и разрабатываются параллельно против одного контракта `NativeAdapter` (раздел 13.2). Платформенный код **MUST** жить только за этим контрактом: `core`, `route-engine`, `api-client` и UI не содержат платформенных ветвлений.

### 19.1. macOS Apple Silicon (MVP)

Реализация по ADR-001 и ADR-002:

- Tauri desktop app;
- privileged helper на Rust, устанавливаемый штатным системным механизмом, владеет туннелем и правилами;
- userspace WireGuard внутри helper через utun-интерфейс;
- IKEv2: Personal VPN через NetworkExtension с мостом Swift и entitlement Personal VPN; helper снимает catch-all и ставит маршруты на `ipsecN` по логике macOS-backend `tunnel_manager` (ADR-005);
- packet filter для fail-closed;
- Keychain для секретов;
- фоновая работа helper обеспечивается самим сервисом; автозапуск приложения при входе - штатный Login Item.

Дополнительно:

`FR-210` (MUST). Приложение **MUST** подписываться и нотаризоваться, иначе Gatekeeper не даст установить его пользователю.

`FR-211` (MUST). Установка helper **MUST** идти через штатный системный механизм установки привилегированных сервисов, один запрос прав, с понятным объяснением до появления системного диалога.

`FR-212` (MUST). Приложение **MUST** подписываться на системные уведомления о смене сети и sleep/wake и реагировать на них сверкой состояния.

Запасной путь: NetworkExtension, если userspace-реализация упрется в ограничения системы (ADR-002). Переход означает Swift-компонент и отдельный entitlement, поэтому решение принимается по итогам walking skeleton в фазе 1, а не в середине фазы 3.

### 19.2. Windows 10/11 (MVP)

Базовая реализация:

- native desktop build через Tauri для x64;
- Windows-служба в роли privileged helper вместо запуска приложения от администратора;
- туннель через kernel-драйвер WireGuard и его штатную библиотеку из службы; маршруты через системные сетевые API; PowerShell допустим только на этапе прототипа и **MUST** быть заменен на прямые вызовы API до релиза;
- IKEv2: RAS-подключение из службы через RAS API со split tunneling, EAP-MSCHAPv2, маршруты на RAS-интерфейс по логике Windows-backend `tunnel_manager` (ADR-005);
- Windows Filtering Platform или firewall rules для fail-closed;
- Credential Manager или DPAPI для секретов;
- автозапуск через запись в реестре для пользовательской части и автостарт службы для helper;
- установщик MSI или NSIS с корректным uninstall cleanup.

Требования:

`FR-213` (MUST). Приложение **MUST** ставиться и работать без постоянных прав администратора у пользователя. Права запрашиваются один раз - при установке службы helper.

`FR-214` (MUST). Helper реализуется как Windows-служба с автозапуском. Канал с приложением - named pipe с ACL, ограниченным пользователем-владельцем сессии.

`SEC-024` (MUST). Служба **MUST** проверять подпись и SID вызывающего процесса перед выполнением любой команды. Anonymous impersonation на канале **MUST** быть запрещена.

`FR-215` (MUST). Установщик и исполняемые файлы **MUST** подписываться сертификатом code signing, иначе SmartScreen блокирует установку у пользователей.

`FR-216` (MUST). Приложение **MUST** подписываться на системные уведомления о смене сети и о выходе из сна и реагировать на них сверкой состояния.

`FR-217` (MUST). Fail-closed **MUST** реализовываться правилами WFP или firewall в собственной именованной группе, чтобы удаление правил не задевало чужие. Правила **MUST** переживать исчезновение tunnel-интерфейса.

`FR-218` (MUST). Uninstall **MUST** удалять службу, правила фильтрации, маршруты, tunnel-интерфейс и драйвер, записи автозапуска и данные приложения. Проверяется отдельным пунктом матрицы тестов.

`FR-219` (MUST). Приложение **MUST** корректно работать при включенном Windows Firewall и стороннем антивирусе. Конфликт с чужими правилами или чужим VPN-клиентом **MUST** давать понятную ошибку `conflicting_network_software`, а запрет со стороны политик системы или организации - `os_policy_blocked`. Молчаливый сбой недопустим.

`FR-225` (MUST). Helper обслуживает одну сессию пользователя ОС за раз: туннель и правила общие для машины. Второй экземпляр приложения в другой сессии видит состояние «подключено другим пользователем» и не может ни подключаться, ни отключать. Переключение активной сессии соединение не разрывает; выход владельца из системы - разрывает. Правило одинаково для Windows и macOS.

Известные риски платформы: сторонние VPN-клиенты и антивирусы могут владеть теми же правилами фильтрации; метрики маршрутов Windows требуют явного управления, иначе система может предпочесть маршрут по умолчанию.

### 19.3. Android

Android требует отдельного technical spike. Скорее всего нужно использовать системную модель Android tunnel service; относиться к Android как к desktop route management нельзя.

Ключевые вопросы spike:

- реализовывать ли tunnel полностью внутри приложения;
- встраивать ли существующую tunnel-библиотеку;
- как сохранить единый UX с desktop;
- как поддержать always-on behavior;
- какие требования Google Play применимы к категории приложения.

## 21. Тестирование и приемка

### 21.1. Unit-тесты

### 21.2. Интеграционные тесты

- mock backend API;
- route sync при изменении списков;
- offline startup из local cache;
- expired subscription;
- обработка invalid route list;
- отклонение списка с плохим хешем и подписью;
- anti-rollback;
- очередь error reports при недоступном backend;
- поведение при `429` и `Retry-After`;
- полный цикл connect -> sync -> drift -> repair -> disconnect на fake-адаптере;
- перебор транспортов по политике и память последнего удачного для сети;
- вход по коду связки: pending, подтверждение, истечение, отказ бота;
- пробный период и роль `admin` в профиле и токене;
- смена DNS при подключении, потере туннеля и отключении на fake-адаптере;
- старт приложения при поколении helper без туннеля (`FR-196`);
- холодный старт без backend при доступном endpoint: кеш свежий, старше TTL, старше hardExpiry, без секретов, профиль ни разу не получен (`FR-161a`);
- refresh: перезапуск, истекший access, потеря ответа ротации, падение до сохранения нового refresh, два конкурентных `401` (`FR-013a`);
- таблица переходов из всех сетевых состояний при expiry, revoke и minVersion; успешный sync при неустраненном drift; туннель восстановился, а применение маршрутов не удалось (`FR-134`);
- fixture-векторы конвейера 10.7 на fake-адаптере и mock backend.

### 21.3. Ручные платформенные тесты

Матрица M1-M24 выполняется **на каждой платформе MVP отдельно**: на чистой машине Apple Silicon и на чистой машине Windows 10 21H2+ либо Windows 11. Заполненный чеклист нужен по каждой платформе; провал на одной из них блокирует релиз обеих.

| # | Сценарий | Критерий |
| --- | --- | --- |
| M1 | Чистая установка | ставится и запускается без ручных действий |
| M2 | Вход через бота | устройство появляется в `/devices` бота и в админ-панели приложения |
| M3 | Connect/disconnect | состояние меняется, маршруты появляются и исчезают |
| M4 | Sleep/wake | восстановление без ручной чистки маршрутов |
| M5 | Смена сети | маршруты пересозданы, утечек нет |
| M6 | Backend недоступен | работа продолжается на кеше |
| M7 | Tunnel endpoint недоступен | понятная ошибка, отчет админам ушел |
| M8 | Route drift | чинится автоматически |
| M9 | Fail-closed | все проверки L1-L10 раздела 14.7 пройдены |
| M10 | Истечение подписки | отключение и снятие маршрутов |
| M11 | Отзыв устройства | немедленный выход на экран активации |
| M12 | Режим эксперта | диагностика, «почему X (не) идет через туннель», живая проба, переключатель DNS; локальные правила проверяются в 1.1 |
| M13 | Ручная отправка ошибки | сообщение пришло администраторам |
| M14 | Uninstall cleanup | маршрутов, helper и autostart не осталось, сеть работает |

| M16 | Подключение по IKEv2 при заблокированном UDP WireGuard | автопереключение, маршруты и fail-closed работают, catch-all снят |
| M17 | Ручной выбор транспорта в режиме эксперта | подключение указанным транспортом, обратное переключение без утечки |

## 22. Процесс разработки и CI/CD

`NFR-040` (MUST). CI на каждый pull request: typecheck, lint, unit-тесты, проверка на секреты и сборка приложения **на обеих платформах MVP** - macOS-раннер и Windows-раннер. Красная сборка на любой из платформ блокирует merge.

`NFR-041` (MUST). Сборка релиза выполняется из CI по одному тегу и производит артефакты для обеих платформ с одинаковой версией и указанием хеша коммита. Релиз без одного из артефактов не публикуется.

`NFR-045` (MUST). Интеграционные тесты раздела 21.2 гоняются на обоих раннерах, а не только на macOS: одинаковый набор тестов - главная защита паритета.

`NFR-046` (SHOULD). Windows-раннер **SHOULD** запускать smoke-тест установки и удаления службы helper, чтобы регресс в uninstall cleanup ловился до ручной матрицы.

`NFR-042` (MUST). Версионирование semver. Версия приложения передается в backend и отображается в UI.

`NFR-043` (SHOULD). Архитектурные решения фиксируются короткими decision records в `docs/decisions/`.

`NFR-044` (MUST). Требования этого документа трассируются в issues; каждая задача ссылается на идентификаторы требований. Исключение - фаза 1 (walking skeleton): там цель - ответ "реализуемо или нет", и формальная трассировка не требуется.

### 22.1. Тестовое окружение

Без него фазы 1, 3 и 4 нельзя проверить, поэтому окружение - результат фазы 0.

`NFR-047` (MUST). До начала native-разработки существуют:

- тестовый экземпляр зарубежного сервера: `wg0` и `client-api` на отдельной VPS или в отдельном пространстве имен, с собственными ключами и своей БД;
- staging-дашборд или mock `GET /api/routes` и статусов для него;
- тестовые коды активации с коротким сроком жизни;
- стенд для leak-тестов: машина каждой платформы с захватом трафика на физическом интерфейсе и скриптом проверок L1-L10;
- минимум одна чистая физическая Windows-машина (OQ-7).

`NFR-048` (MUST). Адреса и ключи тестового окружения **MUST NOT** попадать в репозиторий; они передаются через переменные окружения CI и локальные `.env`, исключенные из git.
