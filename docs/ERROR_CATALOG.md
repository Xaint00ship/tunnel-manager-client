# Tunnel Manager Client: каталог ошибок и правила отчетов

Версия документа: 1.1 (после проверки документации 2026-09-06)
Относится к: [Техническое задание](TECH_SPEC.md), разделы 6.11 и 16; [API_SPEC.md](API_SPEC.md), раздел 9.

Документ фиксирует, какие ошибки существуют, как они называются, что видит пользователь, что уходит администраторам и что не должно уходить никогда.

## 1. Принцип

Ошибки подключения должны быть сделаны лучше, чем сценарий "напишите в поддержку с номером ошибки". Приложение само помогает администраторам увидеть проблему: actionable сбой уходит администраторам автоматически, а пользователь видит короткое человеческое объяснение и одну кнопку.

Три правила:

1. Автоматически отправляем только то, что мешает пользователю подключиться или пользоваться tunnel.
2. Никогда не отправляем шум и повторы.
3. Никогда не отправляем секреты и данные о трафике.

---

## 2. Severity

| Severity | Определение | Автоотправка админам | Что видит пользователь |
| --- | --- | --- | --- |
| `critical` | подключение невозможно и не восстановится само | да, немедленно | экран ошибки с действием |
| `error` | операция провалилась, автоматическое восстановление не помогло | да, с rate limit | экран ошибки с действием |
| `warning` | деградация, работа продолжается | нет | мягкое предупреждение или ничего |
| `info` | нормальное событие | нет | ничего |

| `health_probe_failed` | warning | один мертвый цикл проб; второй подряд запускает пересборку, и только провал после пересборки становится `health_rebuild_failed` |

| `activation_code_invalid` | warning | ошибка ввода пользователя |
| `authorization_pending` | info | ожидание подтверждения входа в боте |
| `device_code_expired` | warning | пользователь не подтвердил вход в боте за 10 минут |
| `trial_already_used` | warning | бот отклонил повторный пробный период (`FR-272`) |

## 5. Структура отчета

Каждый отправляемый отчет содержит:

| Поле | Обязательно | Описание |
| --- | --- | --- |
| `category` | да | категория из раздела 4 |
| `fingerprint` | да | стабильный хеш для дедупликации |
| `severity` | да | `critical` / `error` / `warning` / `info` |
| `stage` | да | значение из раздела 3 |
| `platform` | да | ОС, версия ОС, архитектура |
| `app` | да | версия приложения и канал |
| `device` | да | внутренний `deviceId` или его hash |
| `ts` | да | момент возникновения в UTC |
| `occurrences` | да | сколько раз ошибка повторилась с `firstSeenAt` |
| `context` | да | redacted технический контекст |
| `diagnostics` | да | redacted сообщение и последние шаги |
| `manual` | да | отправлено пользователем вручную или автоматически |

### 5.1. Fingerprint

```text
fingerprint = hex(sha256(
  category + "|" +
  stage + "|" +
  platform.os + "|" +
  normalizedOsErrorCode + "|" +
  app.majorMinor
))[0..16]
```

Свойства:

- одинаковая проблема на одном устройстве дает один и тот же fingerprint между перезапусками;
- патч-версия приложения не меняет fingerprint, минорная - меняет;
- переменные данные (timestamp, имя интерфейса, счетчики) в fingerprint не входят.

### 5.2. Разрешенный контекст

Поля `context` формируются из типизированной структуры, а не собираются из произвольных данных:

```text
state                 состояние машины состояний
helperVersion         версия privileged helper
endpointId            идентификатор endpoint, не адрес
routeListVersion      версия route list
appliedRouteCount     число применённых маршрутов
failClosedActive      активна ли защита
networkType           wifi | ethernet | cellular | unknown
osErrorCode           числовой код ОС
retryCount            число попыток
```

### 5.3. Запрещено в отчете

В error report **никогда** не попадают:

- private keys;
- пароли;
- access и refresh tokens;
- полные tunnel credentials;
- содержимое трафика;
- история браузинга;
- произвольные пользовательские файлы;
- raw config без redaction;
- полные адреса и hostname tunnel endpoint;
- IP-адреса пользователя и его локальной сети;
- SSID сети;
- имя пользователя ОС и пути в домашнем каталоге.

## 6. Redaction

Redaction работает в два слоя.

### 6.1. Слой 1: allowlist-сериализация

Отчет собирается только из типизированной структуры с фиксированным набором полей. Произвольные объекты в отчет не сериализуются. Это основной механизм: если поля нет в структуре, оно физически не может попасть в отчет.

### 6.2. Слой 2: фильтры на свободном тексте

Сообщения от ОС и helper проходят через фильтры перед попаданием в `diagnostics.message`:

| Что ищем | Чем заменяем |
| --- | --- |
| IPv4 и IPv6 адреса | `<ip>`, кроме адресов из применённого whitelist |
| hostname endpoint | `<endpoint>` |
| строки вида `key=`, `token=`, `password=`, `secret=` | `<redacted>` |
| base64-подобные последовательности длиннее 40 символов | `<redacted>` |
| JWT-подобные строки | `<redacted>` |
| пути внутри домашнего каталога (`/Users/<имя>/…`, `C:\Users\<имя>\…`) | `~/<path>` |
| имя пользователя ОС | `<user>` |
| буквы дисков и UNC-пути Windows | `<path>` |
| GUID сетевых интерфейсов Windows | `<iface>` |

`SEC-050` (MUST). Длина `diagnostics.message` ограничена 500 символами, `lastSteps` - 10 элементами из фиксированного словаря шагов.

`SEC-051` (MUST). Фильтры покрываются unit-тестами с негативными примерами: тест подает строку с токеном, адресом и путем и проверяет, что ничего из этого не осталось.

## 7. Rate limit и очередь на клиенте

| Правило | Значение по умолчанию |
| --- | --- |
| Один fingerprint отправляется не чаще | 1 раз в 30 минут; первый `critical`/`error` уходит сразу с `occurrences: 1`, повторы копятся |
| Всего автоматических отчетов с устройства | 4 в час, 20 в сутки |
| Ручные отчеты пользователя | обходят оба лимита и окно fingerprint, но не чаще 1 раза в минуту |
| Размер очереди неотправленных отчетов | 50 записей, вытесняются самые старые |
| Хранение очереди | `queue/error-reports.ndjson`, переживает перезапуск |
| Повтор отправки из очереди | backoff 1, 5, 15, 60 минут |
| Срок жизни записи в очереди | 72 часа |

`FR-230` (MUST). Подавленные повторы не теряются: при следующей отправке того же fingerprint поле `occurrences` содержит число повторов, накопленных с предыдущей отправки, а `firstSeenAt` - момент первого появления. Отправленный отчет задним числом не меняется: агрегация - это обновление счетчика в следующем отчете, а не замена уже доставленного уведомления.

`FR-231` (MUST). Клиентский rate limit не заменяет серверный: backend дедуплицирует и ограничивает уведомления независимо (`API-082`-`API-084`).

## 8. Ручная отправка

`FR-232` (MUST). На экране ошибки есть кнопка "Отправить ошибку". Одно нажатие отправляет тот же redacted отчет администраторам через backend.

`FR-233` (MUST). Кнопка показывается, если ошибка не была отправлена автоматически, а также всегда доступна в режиме эксперта для последней ошибки.

`FR-234` (MUST). После нажатия пользователь видит один из простых статусов:

- "Ошибка отправлена" - `accepted: true, notifiedAdmins: true`;
- "Ошибка уже известна, мы работаем над ней" - `accepted: true, deduplicated: true`;
- "Отчет сохранен, администратор увидит его в списке" - `accepted: true, notifiedAdmins: false` без дедупликации: лимит уведомлений исчерпан или severity ниже порога;
- "Не удалось отправить, попробуйте позже" - отправка не удалась, отчет поставлен в очередь.

`FR-235` (MUST). Перед отправкой пользователь **MUST** иметь возможность посмотреть, что именно будет отправлено. Содержимое показывается в том же виде, в каком уйдет на backend.

## 9. Соответствие категорий и уведомлений

Единая таблица приоритетов. Строки проверяются сверху вниз, первая подходящая определяет исход; «сохранен» означает `accepted: true`, «уведомлен» - `notifiedAdmins: true`. Правила серверной стороны - `API-082`-`API-088`.

| # | Условие | Клиент отправляет | Backend сохраняет | Backend уведомляет админов |
| --- | --- | --- | --- | --- |
| 1 | устройство отозвано или подписка истекла (`API-080`) | да, если еще может | нет, `403` | нет; для `refresh_reuse_detected` уведомление создает сам backend (`API-021a`) |
| 2 | `manual: true`, любая категория | да, обходя клиентские лимиты (не чаще 1/мин) | да, обходя per-device дедупликацию | да при `severity` >= `warning`, если глобальный лимит 20/час не исчерпан; иначе сохранен без уведомления, виден в `/report`; `info` - только сохранен |
| 3 | автоматический, категория не из 4.1 (`warning`, `info`) | нет | - | - |
| 4 | автоматический `critical` из 4.1, fingerprint новый для устройства в окне 6 часов | да, сразу | да | да, с учетом глобального лимита и агрегации `API-083` |
| 5 | автоматический `error` из 4.1 (включая `route_limit_exceeded`), fingerprint новый в окне 6 часов | да, с клиентским rate limit | да | да, с учетом глобального лимита и агрегации |
| 6 | автоматический, fingerprint уже известен в окне 6 часов | да, не чаще 1/30 мин с накопленным `occurrences` | да, счетчик повторов | нет; повторы видны в карточке `/report` |
| 7 | клиентский или серверный per-device лимит исчерпан | нет / да | да с `deduplicated: true` | нет |
| 8 | глобальный лимит уведомлений 20/час исчерпан | да | да | нет; в следующем уведомлении по этому fingerprint - накопленное число |

Интервалы: окно дедупликации устройства - 6 часов; клиентское окно повторной отправки одного fingerprint - 30 минут; агрегация по устройствам - с пятого устройства за час, одно сообщение в час (`API-083`); счетчики обновляются в следующем отчете, а не в уже отправленном уведомлении. UI различает два ответа: «Ошибка отправлена» при `notifiedAdmins: true` и «Отчет сохранен, администратор увидит его в списке» при `accepted: true, notifiedAdmins: false` (`FR-234`).

## 10. Тестовые требования

`T-030` (MUST). Для каждой категории раздела 4.1 существует тест, который воспроизводит условие и проверяет, что отчет сформирован с правильными `category`, `severity`, `stage` и `fingerprint`.

`T-031` (MUST). Тест redaction подает во все текстовые поля строку, содержащую токен, private key, IP, hostname endpoint и домашний путь, и проверяет, что итоговый JSON не содержит ни одного из них. Тест выполняется дважды: с путями в стиле macOS (`/Users/имя/…`) и Windows (`C:\Users\имя\…`).

`T-032` (MUST). Тест rate limit проверяет, что 10 одинаковых ошибок подряд дают ровно один немедленный отчет с `occurrences: 1`, девять повторов подавлены, а следующая отправка того же fingerprint после окна 30 минут несет `occurrences: 9` и исходный `firstSeenAt`.

`T-033` (MUST). Тест очереди проверяет, что при недоступном backend отчеты сохраняются, переживают перезапуск и отправляются после восстановления связи.

`T-034` (MUST). Тест на шум проверяет, что сценарии раздела 4.2 без действия пользователя не создают ни одного исходящего отчета; ручная отправка (`manual: true`) из этого теста исключена и проверяется `T-035`.

`T-035` (MUST). Тест таблицы раздела 9: ручной `warning` (сохранен, уведомлен), известный fingerprint вручную (уведомлен), исчерпанный глобальный лимит (сохранен, `notifiedAdmins: false`, UI «отчет сохранен»), отзыв после переиспользования refresh (клиентский отчет отклонен `403`, уведомление создано сервером), десять быстрых повторов (`T-032`), одна ошибка с пяти устройств за час (четыре уведомления, затем одно агрегированное).
