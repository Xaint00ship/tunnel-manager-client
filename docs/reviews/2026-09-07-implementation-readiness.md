# Повторная проверка готовности документации к реализации

Дата: 2026-09-07. Исходная редакция: commit `28deeeeb87b47401ff2e307558555697e94e3f88`, TECH_SPEC 2.3 и API_SPEC 1.1. Проверка выполнена после исправлений [аудита 2026-09-06](2026-09-06-documentation-audit.md). По ее результатам документация обновлена до TECH_SPEC 2.4 и API_SPEC 1.2.

Область: восемь замечаний повторной проверки и связанные с ними требования, примеры, порядок восстановления, дорожная карта и ADR. Исправлены контракты документации; выполнение будущих тестов приложения и платформенная реализуемость этим отчетом не подтверждаются. Новое обязательное поле endpoint вводится до реализации и выпуска API 1.0; для уже опубликованного API такое изменение потребовало бы отдельного решения о совместимости.

## F01. Сетевые маршруты не зависят от выключателя защиты

Проблема: ветка снятия только fail-closed удаляла маршруты и возвращала системный DNS, хотя туннель должен был продолжать работать. API-055 задавал AllowedIPs через пустое при выключенной защите множество protected.

Исправление: в [ТЗ, конвейер 10.7](../TECH_SPEC.md#107-конвейер-от-ответа-api-до-маршрутов-allowedips-и-защиты) разделены `routes`, `appliedRoutes`, `AllowedIPs` и `protected`. Diff маршрутов использует `appliedRoutes`; фильтр — `protected`. Переключение защиты при живом транспорте идет через обычное применение с commit и последующим сужением фильтра. DNS и маршруты сохраняются. `disabled` обозначает только полное отключение. В [контракте helper 13.6](../TECH_SPEC.md#136-контракт-применения-конфигурации) отдельно описаны полное отключение и остановка с сохранением защиты; полная очистка использует журнал владения, включая маршруты режима без защиты. Незавершенное полное отключение обрабатывается до восстановления старой блокировки; незавершенное переключение защиты при живом туннеле — с обычным откатом. [API-055](../API_SPEC.md#6-get-clientv1endpoint) и ADR-001/ADR-005 согласованы с конвейером.

Приемка: on → off → on при неизменном whitelist сохраняет маршруты, DNS и AllowedIPs; обновление списка работает с выключенной защитой; полное отключение из обоих режимов удаляет собственные ресурсы. Падение до/после commit и ошибка записи/очистки проверяются отдельно. Это требования `T-002` и 21.2, а не утверждение о выполненных leak-тестах.

## F02. Запрет обхода защиты не запрещает отключение

Проблема: `failClosedUserOverride:false` блокировал и обычную кнопку «Отключить».

Исправление: `HelperPolicy`, API-032 и таблица режимов 13.6 запрещают только живой туннель без защиты. Полное отключение пользователем и штатный выход доступны независимо от этой политики. Причины отзыва, истечения доступа и обязательного обновления разрешают полное отключение, но не дают обойти запрет работы без защиты. FR-062 согласован с этими источниками разрешения.

Приемка: кнопка отключения и выход работают при override=false; запрос живого туннеля без защиты отклоняется, в том числе с подмененной причиной; при override=true снятие только защиты требует подтверждения пользователя.

## F03. Однозначная матрица поколений

Проблема: после A committed / B held запрос сверки A одновременно подпадал под разрешение сверки committed и запрет любого номера меньше lastGeneration.

Исправление: матрица 13.6 проверяется сверху вниз. Занятость helper проверяется первой; текущий committed разрешено сверять даже при более новом held/aborted. Повторяется только последняя held/prepared-попытка с исходным запросом; новое применение получает lastGeneration+1. Изменение committed, старые held и пропуски номеров отклоняются. Rebuild текущего committed требует нового поколения. В псевдокоде 10.5 результат сверки обрабатывается так же, как результат нового применения, включая потерю ответа и занятость helper; сравнение учитывает policy и probeAddress.

Приемка: A=10 committed, B=11 held — сверка 10 сохраняет объединенную защиту, повтор 11 допускает только исходный запрос, новая попытка получает 12. Watchdog не снимает защиту B. Изменение полей и rebuild проверяются отдельно.

## F04. Аутентифицированный и ограниченный доступом повтор refresh

Проблема: API-024 возвращал кеш по deviceId/Idempotency-Key до проверки токена и не согласовывал replay с обязательной проверкой текущего доступа и роли.

Исправление: [API-020–026](../API_SPEC.md#3-post-clientv1authrefresh) задают атомарную сериализацию, привязку повтора к отпечатку исходного refresh token и устройству, проверку статуса и роли до выдачи результата. Повтор сохраняет выданный refresh token и его абсолютный срок; истекший access или access с прежней ролью заменяется актуальным. Ответ содержит оставшийся TTL. Исчерпанное окно восстановления дает `refresh_recovery_expired`, неверный токен — `invalid_refresh_token`, конфликт запроса — `idempotency_conflict`; ключ операции сам по себе доступа не дает. История операций позволяет отличить поздний корректный повтор от reuse с другим ключом. FR-013a задает прекращение автоматического refresh и сохраненный признак необходимости повторного входа, блокирующий новые подключения и admin-действия.

Приемка: потеря ответа, конкурентные refresh, неверный/чужой токен при известном ключе, отзыв, истечение подписки, смена роли, истечение access, следующая ротация refresh и поздний повтор. Replay не продлевает refresh и не возвращает прежние права. Корректный повтор не создает ложного reuse-отзыва.

## F05. Явная серверная цель проверки живости

Проблема: при отсутствии dnsResolver серверный адрес предлагалось вычислять из assignedAddresses, хотя там адреса клиента /32 и /128.

Исправление: endpoint содержит обязательный для WireGuard `probeAddress` (API-056a). Адрес сервера сохраняется в офлайн-профиле, передается helper, получает host-маршрут и AllowedIPs независимо от DNS и переключателя защиты. Сервер отвечает на TCP 53; helper засчитывает только соответствующий пробе ответ через tunnel-интерфейс. Клиентские адреса не используются как цель. FR-057 явно относится к отдельным TCP 443-пробам продуктовых направлений. Тестовый сервер Phase 0 предоставляет достижимую цель.

Приемка: отдельные IPv4/IPv6, отсутствие DNS, совпадающий resolver/probe, невалидное или отсутствующее поле, молчание сервера, запрет fallback пробы на физический интерфейс даже с выключенной защитой. Неизменные сетевые настройки после переключения fail-closed проверяются с учетом служебных маршрутов.

## F06. Точные границы офлайн-подписки

Проблема: FR-161a неоднозначно сравнивал expiresAt и graceUntil; таблица профиля использовала неопределенное expiresAt+grace.

Исправление: [FR-161a](../TECH_SPEC.md#117-старт-офлайн-и-офлайн-профиль-подключения) задает `accessDeadline = graceUntil ?? expiresAt`, проверку корректности grace и строгое `now < accessDeadline` при статусе active. `graceUntil` — абсолютная дата backend; null означает отсутствие grace. Grace кеша не продлевает подписку. Некорректный профиль не заменяет последнюю валидную копию. API profile и перечень сохраняемых данных согласованы.

Приемка: до, на и после expiresAt/graceUntil; null, ранний и невалидный grace; expired/suspended при будущих датах. Офлайн-таймер запрещает новое подключение на границе и не разрывает работающее.

## F07. IPv6-векторы соответствуют политике

Проблема: fixture требовал отклонить IPv6 /24 при минимуме /16.

Исправление: конвейер 10.7 требует явную политику в каждом векторе: публичный /24 принимается при минимуме 16, отклоняется при 32; /15 отклоняется при 16, /16 принимается. Проверки приватных и остальных запрещенных диапазонов сохраняются независимо от длины префикса.

Приемка: одинаковые входы и политика дают одинаковые результаты backend/core/helper; отдельные векторы покрывают изменение minPrefixLength, служебные адреса, дедупликацию и итоговый maxRoutes.

## F08. Тестовая авторизация доступна до Phase 3

Проблема: минимальный backend Phase 0 не имел auth, Phase 3 уже требовала вход через бота, а серверная работа была описана только в Phase 6.

Исправление: в [ROADMAP](../ROADMAP.md) добавлена зависимость Phase 2 → 3: расширение тестового client-api и подключение тестового бота для обоих способов входа, refresh, профиля, endpoint, подтверждения IKEv2 и отвязки устройства. Есть критерий готовности перед интеграцией. Phase 6 переиспользует этот код и доводит production-интеграцию; Phase 1 продолжает работать на фиксированных устройствах. Приложение A ТЗ отражает зависимость.

Приемка: контрактные auth-тесты на тестовом backend и оба способа входа проходят до интеграционной приемки Phase 3, без зависимости от незавершенной Phase 6.

## Статус и дальнейшая работа

Все восемь замечаний отражены в документации и сценариях приемки. Выполнена текстовая сверка связок режимы helper → журнал → восстановление, поколения → watchdog, refresh → доступ → офлайн-профиль, endpoint → пробы → маршруты, roadmap → зависимости.

Перед коммитом проверены 12 Markdown-файлов: 109 локальных ссылок (включая новые якоря разделов), 19 JSON-примеров, баланс блоков кода и сохранение существующих идентификаторов требований относительно исходного commit. Проверки прошли; `git diff --check` не выявил ошибок форматирования. Исторические ссылки вида `файл.md:строка` из исходного аудита проверялись по существованию файла; старые номера строк не переинтерпретировались как актуальные.

Можно приступать к Phase 0 и walking skeleton с этими контрактами. Путь macOS в ADR-002 остается проверяемым предположением. Реальные leak-тесты, запуск на двух ОС, подпись сборок и производительность подтверждаются реализацией на стендах; этот отчет не заменяет их и не объявляет проект готовым к релизу.
